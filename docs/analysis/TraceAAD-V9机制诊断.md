# TraceAAD V9 机制诊断

> 诊断对象：V9-Core，正式批次 `20260807_123753`。
> 本文区分科学主张、机制事实、机制推断和待验证假设。V9 的模型层下一步决策始终只有一个：生成新的 `Idea + Code`。

## 1. 核心判断

V9 已经证明这套完整方法具有竞争力，但还没有证明“历史本身有效”，也没有形成稳定的跨任务机制。十三方法同场 15 个测试设置的平均名次为 `4.167`，略高于 MCTS-AHD 的 `4.200`；单版本上场平均名次为 `1.867`。这个优势很小，重复数只有 3，置信区间高度重叠，因此应理解为“V9 是目前最强的 TraceAAD 版本”，而不是已经得到稳定的 SOTA 结论。

V9 最明显的不妥是：

1. **持续搜索几乎退化成单根深挖。** 固定根、递归选择、`subtree-best` 的永久 `max-backup`、较小且随预算衰减的探索项共同造成根级预算垄断。
2. **单步上下文是有损历史加动作化提示。** 模型看到的是最近一段来时路、部分直接分支和完整代码，而不是可完整核对的历史；算子提示又把唯一的生成任务写成了 `correction / interact / adapt` 等动作类别。
3. **两部分相互放大缺陷。** 搜索只围绕少数路线分配预算，单步生成就只能反复看到少数路线的历史；新候选的分数再通过 `max-backup` 抬高这些路线，形成闭环。

因此，V9 当前应优先做机制收敛：先使历史呈现忠实、算子语义正确，再单独调整起点覆盖和持续预算分配。暂不增加更多算子、记忆层或复杂信用公式。

## 2. 当前机制的两个层次

### 2.1 单步生成

搜索机制选出程序节点后，V9 构造当前程序、来时路、直接分支摘要和可选参考轨迹，LLM 一次生成新的 `Idea + Code`。这一层回答的是：给定一个起点，当前上下文是否改变了下一次生成的质量和方向。

### 2.2 持续搜索

树调度决定下一次从哪个已有程序开始生成，并分配有限的 evaluator 预算。它不替代 LLM 生成，只决定哪些程序会继续成为生成起点。V9 的当前配置为 10 个初始根、根级不再扩展、递归 UCT、自适应 `new_child`、每批最多两个子代和 `subtree-best max-backup`。

### 2.3 两层的耦合

搜索选中的起点决定模型能看到哪条历史；模型产生的候选及其 fitness 又决定该起点和祖先分支的后续价值。最终测试分数不能单独区分两层，但过程日志可以分别检查“给定起点的父子生成质量”和“起点覆盖及预算分配”。

## 3. 单步上下文诊断

### 3.1 来时路呈现不完整

`formation_history` 只呈现当前节点祖先边的最近 8 条。V9 实验中树深中位数约为 14–52，最大深度约为 54–130，因此深树的早期思想和早期结果会永久离开 prompt。直接分支最多呈现 8 个：先取 subtree-best 较高的 4 个，再用最近创建的分支补齐，其余尝试不可见。

这满足了“历史进入上下文”的接口要求，但不等于模型看到了完整的来时路。当前摘要包含 `Idea`、父子 fitness、结果类别、代码变化比例和 LOC，却不包含实际代码差异；其中 `Idea` 是模型自述，不是系统验证的机制事实。`不要重复已测试变化` 在历史被截断时也无法严格执行。

**判断：运行正常，但指导信息不完整。** 这是比“历史完全没有用”更准确的表述。当前工件能证明历史字段被构造并发送，不能证明模型读懂并利用了历史。

### 3.2 直接结果和后续结果混在同一摘要

每个直接分支同时显示 immediate fitness、subtree-best fitness 和到 subtree best 的深度。这样保留了“一个直接尝试后来可能发展出价值”的事实，但在自然语言中容易让模型把后代最高分误归因于直接边上的 Idea。V9 明确没有因果信用，因此提示呈现也不应制造这种因果暗示。

### 3.3 当前代码、历史和参考代码争夺注意力

单步 prompt 同时包含任务契约、历史、当前完整程序、目标函数骨架和算子约束；双轨迹生成还加入参考程序和参考形成历史。正式运行未记录 `context_overflow`，但实际 prompt 长度约为中位 2.9k–4.5k、最高约 6.4k–14.9k tokens，并随代码增长和双轨迹情况变化。超限时先删除参考历史，再删除直接分支摘要，导致同一个算子在不同样本中实际看到的历史范围不同。

这不是上下文窗口工程故障，而是信息优先级尚未明确：当前代码是执行对象，来时路是生成证据，参考代码是可选视角，三者现在以长文本并列出现。

### 3.4 算子提示没有形成可审查的生成差异

四个算子最后都输出同一种 `Idea + Code`，但提示分别要求“new direction”“focused correction”“让两个 principle interact”“adapt exactly one supported idea”。这些词要求模型先自行判断什么是 weakness、supported principle 或可交互原则，而轨迹中并没有系统验证的原则或因果标签。

12 路运行中四个算子调用量大致均衡，改善率约为 `9.1%–11.3%`，下降率约为 `71.8%–78.1%`，没有稳定的算子赢家。这个事实不能证明算子无效，但说明当前四种提示约束尚未产生清晰、跨任务稳定的单步差异。继续增加算子数量很可能只增加语义噪声。

### 3.5 双轨迹参考并未等价于多样化指导

双轨迹算子按其他根分支的 subtree quality softmax 采样参考，主要依据是质量，不是与当前来时路的相关性或互补性。由于根级搜索已经锁定，主轨迹通常来自一个根，双轨迹只是偶尔加入另一个高质量根的最近历史；它不能替代多条主路线的持续生成。

### 3.6 单步侧的根因排序

高可信机制问题：历史窗口和分支摘要有损；算子文本引入了未验证的动作类别；直接结果与后代结果的呈现边界不够清楚。

中可信机制推断：长代码、历史和参考代码并列，降低了有效历史信号的相对权重；双轨迹按质量而非关系采样，使参考更像高分示例而非可解释的来时路。

待验证假设：完整早期历史、代码差异或单一生成提示是否能提高父子改善率和跨规模泛化。现有日志没有保存完整 prompt 内容，暂时只能证明“历史被送入”，不能证明“历史被使用”。

## 4. 持续搜索诊断

### 4.1 根级预算覆盖已经失衡

12 个正式 run 全部完成 1000 次 evaluator、约 493–500 个 expansion batch。根分支访问占比为：CVRP 三次 `100%`；TSP 约 `99.8%–100%`；OP 约 `99.8%–100%`；OBP 为 `90.3%–97.4%`。树很深，但深度主要来自同一根的连续扩展，而不是多根之间的持续比较。

这直接解释了用户观察到的“太集中在一个分支上利用”。它也说明 10 个初始化根已经能够建立，但初始化后其余根几乎没有机会形成自己的迭代历史；问题首先是根级预算分配，不是根的数量。

### 4.2 `max-backup` 使用了错误的价值代理

V9 用

\[
G(n)=\max\bigl(y(n),\max_{c\in Children(n)}G(c)\bigr)
\]

作为节点和根分支价值。它表达“这条路线曾经达到过的最高质量”，但持续搜索实际需要判断的是“从这个起点继续生成，是否仍有机会产生有价值的新 Idea + Code”。一次幸运后代会永久抬高整条祖先路线的 `G`，后续访问不会因为连续无效生成而下降。

根级 UCT 还使用全树 fitness 的动态 midrank，并将探索项乘以 `0.1 × 剩余预算比例`。因此高 `G` 根的质量项很快压过探索项，低访问根无法追回机会。动态秩还使同一个节点的分数随全树新样本加入而变化，价值解释不稳定。

**高可信根因推断：** V9 把“历史最高成果”当成了“未来生成潜力”。这两个量在 LLM 生成中并不等价：已经很好的父代可能接近局部平台，较弱父代也可能产生高价值的新生成。当前搜索没有记录或估计这种持续产出能力。

### 4.3 `new_child` 与 `descend` 的竞争没有解决根级问题

在选中的节点内部，V9 比较继续开新子代和访问已有子代；日志显示每个 batch 最终都执行了 `expand`。这能决定路线内的横向或纵向访问，却不能补偿根级选择已经造成的覆盖缺失。先解决根级覆盖，再讨论树内扩展信用，才能知道问题来自哪一层。

### 4.4 算子和初始化的证据边界

四算子调用大致均衡，10 个根也都能建立；目前没有直接证据表明算子数量不足或初始化数量不足。候选 evaluator 失败约占 4.3%，主要为生成程序运行时错误、维度错误、未定义变量和 timeout。这属于生成可靠性和任务契约问题，不能直接作为搜索机制退化的解释。

### 4.5 搜索侧的任务分化

V9 在 OP50、OBP capacity=100 的 1k/5k 取得列最佳，但 TSP、CVRP 三规模和 OBP capacity=500 弱于 V8 或其他基线。由于大多数预算沿早期胜出的根路线展开，不同任务的初始根归纳偏置和早期随机突破会被放大，最终形成“某些任务很好、某些任务差”的分化。这个解释与过程证据一致，但仍应通过根覆盖的受控变化验证，不能仅凭最终测试分数定案。

### 4.6 搜索侧的根因排序

高可信事实：根级访问极端集中，探索压力小且递减，树深增长不代表多路线探索。

高可信机制推断：固定根 + 永久 max-backup + 衰减探索造成早期分支锁定。

待验证假设：增加根级最低覆盖或使用能反映后续产出稳定性的价值统计，能够提高后半程突破率、跨任务稳定性和 held-out 泛化。

## 5. 两部分如何共同造成 V9 的不足

```text
早期某个根或后代偶然得分较高
        -> max-backup 抬高整条根路线
        -> 后续预算继续集中在该路线
        -> LLM 反复看到同一条路线的局部历史
        -> 算子提示要求在有限、动作化的语义框架内生成
        -> 候选质量和新颖性受限
        -> 新分数继续强化原根的价值
```

这个闭环同时解释三种表象：探索不足、跨任务不一致和泛化性弱。双轨迹参考只能提供少量旁支材料，不能改变主起点长期单一的问题。

## 6. 最小机制改进路线

### 阶段一：先收紧单步生成语义

保持四个入口数量不变，先把提示中的动作类别收回到同一个科学任务：

> 基于当前程序和真实来时路，生成一个新的 `Idea + Code`。

差异只表述为“使用单条来时路”或“同时参考另一条真实来时路”，不再要求模型寻找未经验证的 principle、weakness 或 interaction。`Idea` 只需忠实描述代码中实际实现的变化。

### 阶段二：让历史事实可核对

将 prompt 明确分为“历史事实”和“本轮生成”。形成历史采用早期摘要 + 最近摘要的压缩，而不是只保留最近 8 条；直接分支明确显示“本次直接结果”和“该分支后续最好结果”是两个不同字段，并标注尚有多少条尝试未展示。先提升历史可读性，不急于引入自动总结或全局记忆。

### 阶段三：先解决根级覆盖

在保持单步 prompt、算子和树内选择不变的前提下，只改变根级预算协议。最小候选是：

1. 初始化后的每个根先获得固定的少量生成机会，再进入质量竞争；或
2. 根级探索项不随全局剩余预算快速衰减，设置温和的最低覆盖。

两者只选一个做下一版。目标不是让根均匀访问，而是避免一次早期结果永久决定全部生成起点。

### 阶段四：再检验起点价值代理

记录每个根在每个预算分段的有效候选率、子代 fitness 分布、严格 global-best 更新数、最近若干次生成质量和后续突破间隔。只有证据表明 `max-backup` 与持续产出能力不一致，才用一个简单统计量替换它；不要一次加入趋势、路线信用、算子信用和概率控制器。

### 阶段五：最后再考虑算子调度

当单步语义和根级覆盖稳定后，比较四个现有提示的父子结果、后续突破率和跨任务表现。若仍无稳定差异，再决定是否减少为两个清晰视角；目前不应通过增加算子数量来补偿搜索覆盖问题。

## 7. 当前不应做的事情

- 不要把 V9 的平均名次直接写成历史有效的因果证据。
- 不要同时改历史窗口、算子集合、根选择、信用公式和初始化协议，否则仍无法知道哪项改变了行为。
- 不要先增加更多记忆、反思调用或复杂多维信用。
- 不要把生成失败、timeout 或 parser 差异直接解释成轨迹机制失败；先区分机制未运行、运行但无改善和运行后有害。
- 不要把根覆盖率本身当成目标；最终门槛仍是 best-so-far、held-out 质量、后半程突破和跨重复稳定性。

## 8. 当前结论

V9 的骨架是可用的，结果也足以支持继续沿 TraceAAD 路线迭代；但它目前更像“带局部历史提示的单根深度生成器”，还不是能稳定利用多条改进历史的轨迹方法。最先要改变的是机制职责：让单步上下文忠实回答“以前做过什么、效果如何”，让搜索机制负责提供不被早期偶然结果锁死的生成起点。完成这两个最小调整后，才有资格判断历史输入是否真正提高了下一次 `Idea + Code` 的质量与泛化。
