# TraceAAD V9.6 设计审查报告

> 用途：供专家审查的设计快照，冻结于 2026-08-12（实现完成、冒烟前）。
> 机制定案见 [RQ-009](../research/RQ-009-锚点历史上下文.md)，实现规范见
> [V9.6 完整机制设计](../methods/TraceAAD-v9.6完整机制设计.md)，
> 代码在 `llm4ad/method/traceaad_v9_6/`。

## 1. 一句话定位

V9.6 检验 TraceAAD 主张的"生成指导"一半：**把锚点的改进轨迹整理成模型容易读的
上下文，是否比 V9.5 的做法产生更好的单步修改与搜索结果。** 它在 V9.5 上只改两处
——历史上下文（挑法 + 写法）和预算单位；初始化、锚点选择、状态身份、输出契约、
去重与 cache 全部不动。

## 2. 为何需要历史（科学主张）

算法改进是逐步引入思想、试错和修正的过程。TraceAAD 主张把这段来时路——从什么方案
出发、引入了什么思想、得到什么结果——作为下一步生成的主要信息来源。V9.6 面对的
具体问题是：锚点周围的真实历史通常有 30–150 多条（正式批次 11,102 次生成时刻统计：
CVRP 均值 152.9、TSP 66.9、OP 26.2、OBP 20.6，89%–97% 的时刻可用历史多于 8 条），
而上下文只放 8 条。**挑哪 8 条、每条怎么写**，就是本版的全部设计内容。

## 3. 历史包含什么（挑法）

数据来源只有两类真实事实，均来自运行内的完整审计记录：

- **父代轨迹（formation）**：当前算法沿形成链的每一步修改；
- **子代尝试（direct attempts）**：从当前锚点已经发生过的每一次生成。

选择规则（`history.py: select_history`）：

1. 子代取**最近的改进至多 2 条 + 最近的退步至多 2 条**；完全相同的代码（按
   evaluator 输入哈希）只算一次；持平和无效不入选；没有子代就不取。
2. 剩余名额（至少 4 条）用**最靠近锚点的父代修改**填满；不足 8 条就全给，不凑数。
3. 全部入选事件按发生顺序排列。形成步必然早于子代尝试，时间线天然是
   "怎么来的 → 试过什么"。

设计取舍的说明：

- **取"最近"而非"最好/最差"**：避免按幅度挑选引入的展示偏置，保持"只陈述事实、
  不做评价"；
- **子代封顶且成功失败都露面**：直接修正 V9.5 实测缺陷——V9.5 子代优先、装满为止，
  在同一算法被反复尝试的任务上使模型看到的结果分布严重失真（OP 真实改进占 22.9%、
  退步 26.3%，模型看到的是 8.2% 与 49.0%；CVRP/TSP 无此偏差）；
- **持平/无效不进入上下文**：池统计显示部分任务持平与无效占多数，逐条展示会淹没
  有区分度的事件。这是实现选择，正式运行若显示有害可回调。

## 4. 历史怎样写给模型（写法）

历史块只含入选事件，不放总览统计。每条事件统一四行，父代标 `Formation step`，
子代标 `Attempt from current algorithm`：

```text
[Recent Algorithm Improvement History]

[History 2] Attempt from current algorithm
Idea: Anneal temperature
Change: +2/-1 lines; removed: `tau = 1.0`; added: `tau = max(0.2, 1.0 - 0.01 * step)`
Result: regress
Fitness: 12.58 -> 12.3
```

三个字段各回答一个问题，并且都是确定性事实：

- **Idea**（想做什么）：模型当时自报的声明，单行 300 字符封顶；
- **Change**（实际做了什么）：从记录的 parent→child unified diff 确定性摘要——
  加删行数 + 每侧至多 2 行真实改动代码（首行与末行），整行 520 字符封顶。
  Idea 可能缺失或与实际不符，Change 是每条事件唯一的事实锚定；
- **Result / Fitness**（做完怎么样）：improve/regress/plateau 与 parent→child 分数。

整个 prompt：Task → Current Algorithm（分数 + 完整代码）→ 历史块 → Instruction
（与 V9.5 逐字相同，含输出契约）。prompt 超限时从最早事件逐条丢弃重渲染，没有任何
字符级截断阶梯。

与 V9.5 写法的差异：V9.5 每条历史携带压平成单行的 raw diff（1200 字符，超限时按
1200/600/300/0 阶梯降级），历史块约 3.1–3.4K token；V9.6 每条 Change 不超过 520
字符，8 条历史合计约 1K token。

## 5. 支撑机制（不变部分与预算）

- **初始化**：8 个独立根 + 每根一次 bootstrap，optimism scale 取 bootstrap 有效
  |Δq| 的中位数（与 V9.5 相同）；
- **锚点选择**：所有状态按 `q + s/sqrt(n+1)` 取最大（与 V9.5 相同）；
- **状态身份、去重、cache、checkpoint**：与 V9.5 逐字相同；
- **预算单位**：按**真实评价次数**计（`evaluator_call_budget`），固定 1000 次评价，
  对所有任务与重复统一。解析失败与 cache 命中不消耗预算。

## 6. 证据链（按四层区分）

**实验事实**（全部可复核）：

1. 第一轮 432 次固定锚点配对（Code Only vs Idea+Result+Fitness）：历史确实改变
   生成行为；CVRP 配对 Δq 有明确正信号，OP/TSP 正向不确定，OBP 负向不确定；TSP
   valid rate 下降 16.7 个百分点（[实验页](../experiments/TraceAAD-V9.5简洁历史生成识别实验.md)）。
2. 第二轮 432 次配对（简洁历史 vs 再加紧凑 Change）：CVRP 配对 Δq +0.237
   [0.088, 0.409]，改进率 13.9%→33.3%；OP/TSP 正向不确定，OBP 负向不确定
   （[实验页](../experiments/TraceAAD-V9.5紧凑实际修改识别实验.md)）。
   V9.6 的 Change 写法即此轮处理组的形式。
3. 两轮一致的行为效应：历史给得越多，修改幅度越小（约 0.85 → 0.53 → 0.45）。
4. 池统计与失真数字见第 2、3 节（脚本
   `experiments/analysis/analyze_v95_local_history_pool.py`）。

**机制设计推断**（由上述事实支持但未直接验证）：修正展示失真 + 更易读的写法会
改善持续搜索的质量。这正是 V9.6 要检验的命题，不作为前提。

**明确不放进上下文的信息**：子树最优、后代未来结果、谱系标签、轨迹价值、突破标记、
自动失败归因、LLM 反思。理由：要么不是下一步决策所需，要么是人为归纳而非事实。

## 7. 已知风险与边界

1. **修改幅度收缩**：四任务一致，历史越丰富模型改得越小。在局部已改不动的锚点上
   可能有害。正式运行持续报告修改幅度。
2. **单步证据 ≠ 搜索证据**：两轮 probe 只覆盖"已积累局部历史的锚点"的单步生成；
   连续搜索中历史由本机制自身生成，存在反馈回路，最终以完整搜索 + held-out 为准。
3. **OBP 方向为负**（两轮均不确定）：若正式运行 OBP 显著变差，是"历史价值依赖
   任务的算法改进几何"这一假设（研究认识 [待验证]）的一个检验点。
4. **未入选历史不进入上下文**：大量持平/无效尝试与更早的轨迹被省略，其中可能有
   信息，本版不试图表达。

## 8. 自审结果

对照核心主张（历史为主、其余机制从属）与"事实不做结论"原则逐文件复查，发现并
已修正四处：

1. `select_history` 在 `max_events` 小于已选子代数时保留最旧而非最近事件
   （默认 8 时不触发）——已改为保留最近，并加边界测试。
2. 渲染器保留了"无效事件"的展示分支，但挑法保证无效永不入选，属死代码且与挑法
   自相矛盾——已删除，改为不变量断言；RQ-009 写法一节的对应描述同步修正。
3. `Result: unknown` 回退不可达（入选事件必有结果）——已删除。
4. 代码行示例的插值公式在每侧 2 条的设定下等价于"首行 + 末行"——已按等价形式
   简化。

复查后仍保留、并说明理由的设计点：

- **Change 字段保留**：它是接口中唯一被直接 A/B 验证过的增量（第 6 节事实 2），
  且是 Idea 缺失或失真时唯一的事实锚定；"去 Change"作为后续单变量消融（改动一行）。
- **`history_built` 审计记录完整池与入选 id**：本次失真诊断正是靠该口径完成，
  保留以支持 V9.6 的同类分析。
- **冻结 policy id 常量**：服务于 run_config 可追溯与跨版本 diff，非机制代码。

未解决、留给数据回答的问题：持平/无效完全不进入上下文是否损失信息；子代 2+2 封顶
在改进密集的锚点上是否过紧；修改幅度收缩在何种锚点上转为有害。

## 9. 验证计划

1. **冒烟**：单任务小预算，确认模型调用、评价方向与 profiler 一致、历史块内容
   与运行事实一致（抽查 `history_built` 与 prompt 全文）、分数有区分度。
2. **正式**：四任务 × 3 重复，预算 1000 次真实评价，Qwen3.6-27B。
3. **报告**：搜索结果、测试集结果、过程证据（有效率、修改幅度、展示分布 vs 池
   分布）分开报告；重复与测试评估全部完成后才更新结果页。
