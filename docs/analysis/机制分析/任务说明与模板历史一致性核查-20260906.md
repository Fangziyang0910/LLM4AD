# 任务说明与模板历史一致性核查

日期：2026-09-06。范围：五个主表基线、TraceAAD V9.16、V10.1–V10.6 的任务说明与函数模板来源、展示方式及历史变更。本次未修改运行源码、评价器、实验进程或历史结果。

后续落实：用户随后授权恢复公共任务文本并修改V10.6生成协议，相关代码现已更新。本文与同名JSON保留修改前的核查快照；当前实现见[机制设计](../../methods/TraceAAD-V10.6完整机制设计.md)。旧实验记录未被覆盖。

## 核心结论

五个基线使用同一公共任务说明和模板定义，但各方法呈现模板的方式不同，完整 Prompt 并不相同。V9.16 在当时也直接使用公共定义。V10.6 则新增专用 `TASK_CONTEXTS` 覆盖公共任务说明、改写模板中的一句话，并将具体评测时限加入 Prompt。中间还有一次公共 VRPTW 说明变化，发生于 2026-08-29，早于 V10 系列。

因此，要继续与既有主表比较，应恢复**基线历史批次使用的共同任务信息**，不能只改成读取今天的公共文件，也不能继续给 V10.6 单独补充任务知识。

## 核查对象与证据强度

- 五个基线：EoH、ReEvo、MCTS-AHD、PathWise、CALM (w/o GRPO)。TSP/CVRP/OP/OBP 采用主表的 `20260824_rerun` 批次；VRPTW 为 `20260822_142500` 批次。
- 读取五方法 × 五任务 × 三重复共 75 路 `logs/llm_calls.jsonl` 的第一条记录，与历史公共说明比较；字符串匹配只归一化空白。75/75 包含对应历史任务说明。这证明这些已核对请求的任务文本一致，未宣称已逐条审读全部请求。
- 基准文本取提交 `a144f601`（2026-08-22）五个 `llm4ad/task/optimization/*/template.py` 的 `task_description` 与 `template_program`。通过运行日志匹配确认该文本用于指定基线批次，不单凭提交日期推断。
- V9.16：核对 `a144f601` 中实现、模板及正式运行配置。该批未找到完整请求日志，结论属于源码路径与当时配置重建，不能宣称完成了其全部真实 Prompt 的逐条匹配。
- V10.4/V10.5/V10.6：各核对 15 路正式运行第一条请求，结合 Prompt 构造源码验证。
- V10.1–V10.3：核对构造源码与共享模板变更历史，本次未找到同形态的正式请求日志。

原文、每个请求的路径、匹配结果和首条基线请求 SHA256 均保存在[核查数据](任务说明与模板历史一致性核查-20260906.json)。

## 五个基线：同源不等于逐字相同的完整提示

| 方法 | 首条请求包含历史任务说明 | 首条请求包含历史模板 docstring | 模板使用方式 |
| --- | ---: | ---: | --- |
| EoH | 15/15 | 15/15 | 初始化展示去掉函数体的目标函数；演化使用候选程序及接口 |
| ReEvo | 15/15 | 15/15 | 初始化展示种子函数，包括实现；后续使用父代与反思 |
| MCTS-AHD | 15/15 | 15/15 | 初始化展示目标函数，附方法自身的输入输出说明 |

## V9.16 当时如何做

`a144f601` 的 `traceaad.py` 直接读取 `evaluation.task_description`，通过 `evaluation.template_program` 解析唯一待进化函数。初始化把函数体置空，保留签名和 docstring；后续请求使用同一任务描述、当前算法与历史。

它没有 V10.6 的五任务专用说明表，也没有在常规任务说明里统一追加“正式评价时限为 X 秒”。它有独立的失败修复提示，超时反馈中的通用效率建议属于修复协议，不能与每次额外注入具体运行时限混为一谈。

当前实现仍可查看这些路径：[`traceaad.py`](../../../llm4ad/method/traceaad_v9_16/traceaad.py)、[`prompt.py`](../../../llm4ad/method/traceaad_v9_16/prompt.py)。8 月 31 日提交 `41c38007` 的 `_task_intro` 提取没有改变任务文本来源；本次针对历史结论使用的是 8 月 22 日源码，而非仅凭当前文件。

## 中途实际改变了什么

### 2026-08-29：公共 VRPTW 文本被加强

提交 `517d6cc6` 修改 [`vrptw_construct/template.py`](../../../llm4ad/task/optimization/vrptw_construct/template.py)：

- 输入说明追加“返回客户必须来自给定可行集合”。
- 返回说明从“下一个节点或 depot”改为“可行集合中的节点，或在当前不处于 depot 时返回 depot”。
- 任务描述同步明确“已经位于 depot 时不能再次返回 depot”。

这属于同一个接口约束的更明确表述，但仍是模型收到的信息变化。旧基线 VRPTW 与 V9.16 运行在 8 月 22 日；后续版本读取到了更明确的新文本。

其他四个任务的公共 `task_description` 和 `template_program`，当前与 `a144f601` 逐字一致。

### V10.1–V10.5：仍读取公共定义，但呈现和额外要求改变

V10.1–V10.3 的 `build_task_contract` 拼入公共任务说明与完整 `template_program`，并增加 fitness 方向、只使用接口可用信息等通用要求。V10.4/V10.5 复用 V10.3 的任务构造。这与 V9.16 初始化只展示空函数接口有所区别，不应称为整个输入协议完全相同。

V10.4 和 V10.5 各 15 条实测首请求：12 条非 VRPTW 请求匹配历史说明；3 条 VRPTW 请求匹配 8 月 29 日修改后的说明。均未出现 V10.6 的 `formal evaluation runtime limit` 句子。

### V10.6：新增方法专用覆盖

提交 `2eb0fea4` 引入 [`prompts.py`](../../../llm4ad/method/traceaad_v10_6/prompts.py)：

1. `TASK_CONTEXTS` 为五任务各写一份说明；构造时优先使用该字典，覆盖 `evaluation.task_description`。
2. TSP 新增候选按当前距离排序、框架补最后节点等说明；CVRP 写出 ACO 权重公式；OBP 写出单调变换保持排序、整数输入与浮点计算建议等。这些不是单纯调整算子措辞，而是改变共同任务信息。
3. 将模板中的 `Design a novel algorithm to select the next node in each step.` 替换为 `Select the next node for the constructed solution.`，实际命中 TSP 和 VRPTW 的 docstring。
4. 读取 `evaluation.timeout_seconds`，追加具体正式运行时限。

V10.6 的 15 条正式首请求均确认使用覆盖后的说明并包含时限句。这些变化已实际进入实验，不能说只是尚未落实的讨论建议。

## 当前应如何对齐

按用户要求沿用既有比较协议：

1. 以本次从基线日志核实的历史共同文本为任务信息基准，保存可核对的版本；其中 VRPTW 使用旧批次文本。仅删除 `TASK_CONTEXTS` 并读取当前共享文件还不够。
2. 移除 V10.6 专用任务改写、模板句子替换、具体评测时限注入；评价器继续执行原来真实的时间限制。
3. 以 V9.16 的模板呈现原则对齐初始化：保留签名和 docstring，函数体由模型生成。已有父代仍使用完整代码；Idea→Code→二次实现 Idea 是本轮明确研究的机制变化。
4. 两次调用均使用这份共同任务信息；校准阶段增加的是读代码的任务职责，不额外提供只有 TraceAAD 获得的求解器内部知识。
5. 现有 V10.6 结果保留为原配方结果，不能在事后修改文本后将旧成绩改称已对齐。下一次运行需明确标识配方。

本次审计不等于核查所有公平性维度。运行记录中旧基线/V9.16 的模型标签为 Qwen3.6-27B 系列，V10.6 当前配置为 Qwen3.8-27B 系列；实际权重一致性需结合后端快照判断，不能仅凭同一服务地址或别名确认。预算计数、初始化与方法原生采样也有各自协议，本次没有把任务文本对齐等同于整体实验完全可比。
