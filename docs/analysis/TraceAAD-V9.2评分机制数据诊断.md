# TraceAAD V9.2 评分机制数据诊断

> 冻结说明：本文是 2026-08-09 00:24（Asia/Shanghai）的中期过程快照。V9、旧 V9.1 与新 V9.1 各有 12 路产生了可分析事件，新 V9.1 仍在运行；这里的数字用于机制诊断，不是正式结果。
>
> 后续设计收口：本文提出的“为每个精确 `(锚点,窗口)` 独立维护 `Q_window`”是中间候选。相关工作综合发现 full-path / 高阶上下文信用存在明显样本稀疏问题，最终 V9.2 改为每个锚点一个确定性的规范局部窗口，并在锚点层聚合真实生成结果。过程统计与评分目标判断继续有效；最终规范见 [TraceAAD V9.2 完整机制设计](../methods/TraceAAD-v9.2完整机制设计.md)。

## 核心判断

现有实验足以否定 V9.1 的核心代理目标：**“超过路线历史最好”不能代表一个锚点值得继续获得预算。** 它系统性偏爱从低质量位置产生的局部回弹。V9.2 应改为评价：

> 给定当前可执行代码锚点和实际送入模型的局部轨迹窗口，下一份预算预计能生成多高质量的有效代码。

这个目标使用有向原始 fitness 的绝对质量，不使用全局 min–max，不把后代最好值回传给祖先，也不把趋势、波动或路线推进率预先线性加权成价值。

现有数据还不能回答“同一锚点的哪条窗口因果上更好”。旧运行没有在固定锚点下随机切换多个窗口，因此窗口规则必须通过专门对照实验识别，不能从相关性直接定案。

## 数据与分析口径

分析脚本为 `experiments/analysis/analyze_v92_scoring.py`。它读取 V9、旧 V9.1 和轨迹中心 V9.1 的 `candidates.jsonl`、`decisions.jsonl` 与 `edges.jsonl`，按每次预算发生前的状态重建：

- 锚点有向 fitness、当时全局差距和排名；
- 最多 8 节点的形成路径窗口及其水平、趋势、波动和转折；
- 当时已经存在的直接下游结果；
- 该锚点此前已经获得的预算及结果；
- 本次生成的最佳有效子代质量、路线推进、全局推进，以及深度 3 内可观察的延迟挽救。

新 V9.1 的路线推进标签由脚本重新计算并与日志逐事件断言一致。统计先在每个 run 内计算，再汇总中位数；预测检验在同一 task 内按 run 留一，避免同一运行的相邻事件同时进入训练和测试。

这仍是观察性分析：只看到历史策略实际选择过的锚点；延迟后代只在后来获得预算的子树中可见；跨协议差异包含选择机制变化。因而下面的关联用于排除错误目标、形成待验证机制，不构成离线策略收益估计。

## 一、路线推进制造了错误的“成功”

| 协议 | 预算事件 | 路线推进率 | 全局推进率 | 路线推进转为全局推进 |
| --- | ---: | ---: | ---: | ---: |
| V9 | 5,958 | 4.4% | 3.0% | 69.6% |
| 旧 V9.1 | 10,909 | 18.5% | 0.5% | 2.6% |
| 新 V9.1（运行中） | 2,324 | 8.4% | 4.2% | 50.0% |

旧 V9.1 看上去最容易“推进路线”，但几乎不能推进全局。它 88.9% 的预算落在当时排名 10 名以外的锚点：这些锚点的路线推进率为 19.5%，全局推进率只有 0.27%。差起点只需回到该路线旧水平就能得到成功信用，这正是局部回弹偏差。

新 V9.1 已明显改善这一点，但又出现另一种集中：70.3% 的预算落在排名第 1 的锚点，其全局推进率约 2.9%；排名 2–3 的锚点仅得到 11.8% 预算，已观察全局推进率约 10.2%。后者受选择偏差和当前样本量影响，不能解释为真实反事实优势，但足以说明“几乎一直选第一名”没有得到过程证据支持。

因此 V9.2 的评分标签不能是：

- 是否超过锚点；
- 是否超过该路线历史最好；
- 某条路线过去的推进成功率。

它们都只表示相对一个局部基线的变化，未回答新代码在当前搜索空间中是否真的有竞争力。

## 二、稳定信号是绝对锚点质量与绝对下游质量

以“本次最佳有效子代相对当时全局最优的差距”为目标，逐 run Spearman 中位数如下：

| 决策前信号 | V9 | 旧 V9.1 | 新 V9.1 |
| --- | ---: | ---: | ---: |
| 锚点相对全局最优的差距 | 0.460 | 0.374 | 0.152 |
| 已测试直接子代最好值相对全局差距 | 0.404 | 0.366 | 0.153 |
| 已测试直接子代均值相对全局差距 | 0.307 | 0.346 | 0.172 |

符号在三个协议中一致。锚点 fitness 是下一步完整代码的质量基础；已有直接子代的绝对质量提供这个局部是否能持续产生好代码的证据。两者都比“有没有相对改善”更接近预算的真实目的。

无需拟合的候选分数也给出同一警告：直接使用锚点 fitness 预测下一次有效子代质量的逐 run Spearman 中位数分别为 0.527、0.384、0.622；用锚点初始化并平均既往预算结果的候选公式则为 0.469、0.360、0.491。加入固定趋势或简单子代均值也未稳定提高。数据支持保留锚点质量为评分地基，却还不支持声称历史修正已经带来预测增益。

## 三、趋势和波动目前只能作为上下文事实

窗口形态与后续结果的方向跨协议不稳定。例如，窗口波动对路线推进的相关中位数在 V9、旧 V9.1、新 V9.1 中分别约为 -0.03、-0.22、+0.17；改进比例对下一次绝对子代质量的关系也会变号。趋势通常略偏正，但增量小且不能稳定击败锚点 fitness。

这不是说趋势和波动没有意义。它说明同一种形态可能对应不同机制状态：正趋势可能是优质局部精炼，也可能是差路线回弹；高波动可能包含突破，也可能只是修改失控。首版若把这些量用人工权重相加，得到的只是跨任务漂移的代理目标。

所以 V9.2-Core 应当：

- 在 prompt 中忠实展示水平、趋势、波动、Idea 与结果，让模型解释其语义；
- 在日志中继续记录这些量，供后续条件分析；
- 不在在线评分中预设“上升加多少、波动扣多少”的通用权重。

## 四、延迟价值存在，但不支持祖先最高分回传

在确实得到后续扩展的事件中，直接未推进、但深度 3 内后来超过原路线最好者约占 7%–13%。这证明暂时退步不应被立即删除，也支持保留完整失败历史和有限质量区域内的基本验证。

该比例存在严重的选择性随访：只有被继续选择的子树才可能出现延迟挽救。它不能证明差节点应得到高预算，更不能把一个优秀后代的 fitness 复制给全部祖先。后代本身已经成为更好的新锚点；祖先的价值在于保存它如何产生后代的形成证据。

## 五、中间评分候选（已由后续设计替代）

所有 task 先将 fitness 转为统一的有向原始分数 `q`，越大越好，但不做跨个体归一化。对精确状态 `(a, W)`，其中 `a` 是锚点，`W` 是实际送入模型的窗口，记录它此前完成的 `n` 次真实使用。第 `i` 次使用产生的事件结果为：

```text
z_i = q(本次最佳有效新代码)    若至少生成一个有效代码
z_i = q(a)                    若本次没有有效代码，表示没有产生新质量
```

若 V9.2 每次只生成一个节点，`z_i` 就是该节点 fitness。首版窗口分数采用最小的锚点初始化经验均值：

```text
Q_window(a, W) = [q(a) + Σ z_i] / [1 + n(a, W)]
```

它没有贝叶斯含义，`q(a)` 只是未测试窗口的评分起点。公式的含义是：先由当前可执行代码质量给出保守估计，再只用这个精确上下文实际生成过的代码质量修正。它具备以下不变量：

- 未使用窗口的评分就是锚点 fitness；
- 其他锚点的极端值不会改变本窗口分数；
- 差锚点的小幅回弹仍然保持较低绝对分数；
- 单次幸运结果会被后续真实结果平均，而不是永久 max-backup；
- 只有实际送入 prompt 的精确窗口获得直接生成信用。

无有效代码的事件不虚构一个 task 相关的极差 fitness：它按锚点分数记为一次无进展并单独更新有效率；无论结果是否有效都算已经尝试，窗口在其他候选获得基本验证前不重复消费预算。若正式实验发现无效率足以影响排序，再预先定义有效性门槛，而不是事后引入全局最差值作为惩罚。

每个锚点只向全局选择器暴露：

```text
W*(a)       = argmax_W Q_window(a, W)
Q_anchor(a) = Q_window(a, W*(a))
```

这样轨迹没有成为第二类个体：系统仍然选择锚点，但锚点分数是“该代码配上当前最好可用局部历史后，实际产生高质量新代码的经验能力”。

这只是首个可证伪候选，不是现有日志已经验证的最优公式。观察数据中，简单锚点—子代均值没有稳定超过纯锚点 fitness；采用它的理由是目标正确、尺度一致、更新闭环清楚，并且能用受控实验直接推翻。

## 六、中间预算候选（已由后续设计替代）

首版不再增加 UCB、概率后验或动态探索控制器。使用一个固定的两阶段规则：

1. 按 `Q_anchor` 保留前 10 个质量候选锚点。现有三个协议中，排名 10 以外锚点的全局推进明显更低；`10` 是首版实现常数，不是理论常数。
2. 候选区内尚未完成一次 `(a, W)` 预算验证的锚点先各获得一次基本验证，无论结果是否有效都算已经尝试；之后选择 `Q_anchor` 最高者。较差的实际输出会拉低经验均值，使预算自然转向其他已验证锚点。

这套规则同时避免两个极端：旧 V9.1 把大量预算给低质量回弹路线，新 V9.1 又把大多数预算压在当前第一名。探索只表示在优质候选区内完成最小事实收集；利用表示在相同绝对质量目标下继续选择经验分数最高者。

窗口内部也采用同一原则：已验证窗口按 `Q_window` 比较，未验证窗口从 `q(a)` 起步。候选窗口集合、同分次序和新增下游节点后的窗口身份更新仍需由下面的固定锚点实验确定，当前数据不能诚实地替我们选择。

## 七、该数据快照提出的验证要求

### 评分不变量测试

实现前先用确定性单元测试固定：方向转换、无全局归一化、精确窗口信用隔离、运行均值更新、单次幸运不会永久保留、无关新节点不改变既有窗口分数、后代不向祖先做最高分回传。

### 固定锚点窗口对照

当前长跑结束后，从四个 task 预先抽取同时具备足够上下游历史的锚点。在相同锚点代码、模型、温度、token 配置和 evaluator 下，随机分配三种上下文：

1. 只有锚点代码，不给轨迹；
2. 固定最近形成历史；
3. V9.2 候选窗口规则选出的历史。

主要终点是新代码有向 fitness，次要终点是有效率、相对锚点变化和代码重复率。分析必须按 task 分层，并报告同一锚点内的配对差异。只有这项实验能回答轨迹窗口是否改变单步生成分布，以及哪种窗口选择优于固定最近历史。

### 在线闭环消融

窗口对照通过后，再比较：纯锚点 fitness、`Q_anchor` 经验评分、以及 V9.1 路线推进 Wilson。保持初始化、单算子、每次候选数和总 evaluator 预算一致，评价后半程全局推进、最终搜索质量、测试质量及预算集中度。

## 结论边界

该数据快照确定了评分的**对象与目标**：对象是锚点化状态，目标是下一次有效代码的绝对质量；它也排除了路线推进率、全局 min–max、祖先 max-backup 和固定形态权重。

快照本身不能确定某种窗口形态天然更好，也不能声称轨迹评分已经优于纯锚点 fitness。后续相关工作综合据此取消了多窗口竞赛，改为唯一规范窗口和锚点层结果聚合；这一设计决定及其仍需完成的因果验证以 V9.2 完整机制规范为准。
