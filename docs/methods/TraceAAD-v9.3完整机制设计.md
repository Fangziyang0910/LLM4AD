# TraceAAD V9.3-Core 完整机制设计

> 状态：冻结的历史实验版本。V9.3 已完成独立实现并产生实验数据，但后续审查确认其把“轨迹提供多步历史”误实现为“一次全局选择后固定连续做三次决策”。当前单步修正版为 [V9.4](TraceAAD-v9.4完整机制设计.md)；本文件保留 V9.3 当时的真实协议，不追溯改写。

## 1. 科学问题

V9.2 每分配一次预算，只观察从锚点直接产生的一个候选，并立即把有效子代变成新的竞争单元。这会使暂时退步的路线过早中断，也使父锚点的一步生产均值与有限预算下寻找最好程序的目标不完全一致。

V9.3-Core 检验：

> 如果把一次全局资源分配从“生成一个子代”改为“连续发展一段短轨迹”，让模型在每一步读取最新局部历史，并以整段轨迹达到的最好程序质量给起始锚点结算信用，是否能够更有效地利用延迟改善和多步修正？

树仍只是保存程序与事件的事实结构。全局选择对象仍是程序锚点，但一份全局预算的实际执行和信用时间尺度变成一段短轨迹。

## 2. 三个时间尺度

V9.3 明确区分三件此前容易混在一起的事：

1. **程序时刻**：每一步都有一份完整可执行代码及其 fitness；
2. **局部轨迹时刻**：连续三次生成构成一次 rollout，后一步从前一步的真实结果继续；
3. **全局分配时刻**：rollout 结束后才更新起始锚点价值，并重新选择下一锚点。

因此，一次全局选择不是承诺某个子代一定优秀，而是允许一个局部算法思想经历三次提出、实现、评价和修正。

## 3. 事实对象

### 3.1 程序锚点

有效程序节点 `a` 保存完整代码、Idea、fitness、父节点、形成事件和创建次序。方向统一后的绝对质量为：

```text
q(a) = fitness(a)       最大化任务
q(a) = -fitness(a)      最小化任务
```

始终是越大越好，不做全局 min–max 或百分位归一化。

### 3.2 局部证据窗口

每一步仍从事实图为当前可执行锚点确定性构造唯一窗口：最多 8 个 `Idea—结果` 事件，优先包含 4 个形成事件和 4 个深度 3 内的近期下游事件，一侧不足时由另一侧补足。

窗口只展示 Idea、有效性、fitness、时序和分支位置，不展示历史程序代码。当前锚点完整代码始终单独提供。V9.3 暂不改变 V9.2 的窗口构造，以便把实验差异集中在轨迹执行和信用时间尺度上。

### 3.3 短程 rollout

从全局选中的起始锚点 `a_0` 出发，固定执行三步：

```text
a_0 --e_1--> a_1 --e_2--> a_2 --e_3--> a_3
```

有效结果无论改善、持平还是退步，都成为下一步的可执行锚点。这样，一次暂时退步不会立即终止该局部发展过程。若某一步解析或评价无效，失败事件进入事实图，下一步继续使用此前最后一个有效锚点。

rollout 的每个事件都记录稳定的 `rollout_id`、步号和起始锚点，以便恢复真实轨迹和审计信用。

## 4. 两阶段生成

轨迹的作用首先是辅助下一步算法决策。V9.3 将每个 rollout 步骤拆成两个模型调用。

### 4.1 轨迹决策

模型读取：

```text
任务
+ 当前可执行锚点的 fitness 与完整代码
+ 与该锚点对应的规范局部证据窗口
+ 初始化阶段的路线策略（仅 bootstrap）
```

只输出一个具体、自包含、可从当前代码实施的 `Idea`，不输出代码，不总结整棵搜索树，不预测 fitness，也不把某次具体实现的成败绝对化为抽象思想的真伪。

### 4.2 代码实现

第二次调用只读取：

```text
任务
+ 当前可执行锚点的 fitness 与完整代码
+ 已批准的唯一 Idea
```

它不再读取轨迹窗口，只负责准确实现该 Idea，并只输出完整代码。这个分离让历史负责路线判断，让代码阶段集中于实现一致性，避免模型在长历史中同时重新解释决策和改写程序。

生成代码必须无注释、无 docstring。解析后继续通过 AST 删除表示噪声并规范化，只有规范化代码进入 evaluator、事实图、工件和后续上下文。

轨迹决策调用不产生候选、不调用 evaluator，因此不计 evaluator 搜索预算；代码响应一旦返回就消耗一份预算，解析失败和评价无效同样计数。运输层失败不计科学预算，但受连续失败上限约束。

## 5. rollout 代表程序与信用

一次 rollout 经过的有效程序集合包括起始锚点及三步中产生的全部有效子代。其代表程序为其中绝对质量最高者；fitness 完全同分时依次选择代码更短、创建更早者。

第 `j` 次从锚点 `a` 完成 rollout 后，结果为：

```text
r_j(a) = max q(x),  x 属于该 rollout 的起点和有效结果
```

起始锚点的预算价值定义为：

```text
Q(a) = [q(a) + Σ_j r_j(a)] / [1 + m(a)]
```

其中 `m(a)` 是从 `a` 完成的 rollout 数。`q(a)` 是价值初始化，不是概率先验。

关键边界：

- 三个步骤只在 rollout 结束时给起始锚点结算一次；
- 中间节点的单步结果不逐次修改起始锚点价值；
- 信用只回到本次被选择的起始锚点，不向祖先传播；
- 代表程序按真实质量参加后续竞争，但不把它的最高分无条件复制给整个谱系；
- 正式预算在第三步之前耗尽时，以已经完成的部分结算；正常运行的非末尾 rollout 固定为三步。

该价值表达“给这个锚点一段连续发展机会后，实际能达到什么绝对质量”，而非一步改进率、趋势奖励或不确定性估计。

## 6. 全局选择与合格锚点

全局选择沿用 V9.2 的最小规则：

1. 按 `Q(a)` 取最多 10 个合格锚点；
2. 其中存在尚未完成任何 rollout 的锚点时，选择 `Q` 最高者进行基本验证；
3. 否则选择 `Q` 最高者；
4. 完全同分按 `q(a)`、代码长度和创建次序确定。

完成正式 rollout 后，只有该段轨迹的代表程序成为新的合格锚点；其他中间程序继续保留为真实历史和最终最好程序候选，但不会各自作为新 arm 立即竞争预算。原有起始锚点不会被删除。

这使“事实节点”和“预算单元”分开：系统可以记录所有过程，又不会因一段三步轨迹生成三个从自身 fitness 重新起步的竞争者。

## 7. 初始化

V9.3 把初始化也改成同一短程轨迹逻辑：

1. 模型根据任务和函数契约提出 8 个互补算法策略；
2. 每个策略独立实现一个有效根程序；
3. 每个根完成一个三步 bootstrap rollout；
4. 每条路线取根与 rollout 有效结果中的最好程序作为代表；
5. 按根经过整段 rollout 后的 `Q` 排序，选出 6 条路线的代表程序进入正式候选集。

理想无失败路径消耗 `8 × (1 + 3) = 32` 次 evaluator 预算，占 1000 总预算的 3.2%。这比 V9.2 的 16 次初始化更贵，但每个初始方向不再只用一次反馈决定去留。

未入选路线和非代表程序全部留在事实图与工件中，不进入正式预算集合。初始化根之间仍保持独立，后生成根不读取先前根的代码或结果。

## 8. 完整闭环

```text
规划 8 个互补策略
    -> 各自生成一个有效根
    -> 各自完成三步短程 rollout
    -> 按 rollout 价值选 6 条路线的最好代表
    -> 全局按 Q 选择一个锚点
    -> 轨迹上下文决定一个 Idea
    -> 锚点代码 + Idea 生成 Code
    -> evaluator 返回真实结果并更新事实窗口
    -> 沿最新有效结果继续，直到三步完成
    -> 选择整段最好代表并给起始锚点结算一次
    -> 代表程序加入全局候选集
    -> 直到 evaluator 预算耗尽
```

最终答案仍是全部有效程序中原始有向 fitness 最好者，同分择简；`Q` 只服务预算分配。

## 9. V9.3-Core 明确没有解决的问题

- 窗口仍按拓扑近期性构造，没有做到语义相关的轨迹选择；
- Idea 仍是模型自述，没有验证 Idea 与真实代码差异完全一致；
- evaluator 仍主要返回标量 fitness，没有提供任务行为层反馈；
- 不同路线之间没有知识迁移；
- rollout 长度固定为 3，没有根据路线状态动态决定停止；
- best-of-rollout 信用偏向“短程能到达的最好质量”，不能代表更长时间的发展上限；
- 全局候选仍以锚点为载体，尚未显式比较完整的可变知识状态；
- 两阶段生成增加一次不计 evaluator 预算但真实消耗推理资源的模型调用。

因此 V9.3 是从“一步历史条件化个体进化”迈向“短程轨迹驱动分配”的最小实验版本，不是 RQ-008 中完整 SOTA 目标的终点。

## 10. 必须保持的机制不变量

1. 一次正常全局分配固定对应三个 evaluator 候选，而不是三个独立全局决策。
2. 有效退步节点必须成为下一步可执行锚点，不能自动回退到较好父代。
3. 轨迹窗口只进入 Idea 决策阶段，代码阶段只接收锚点和已定 Idea。
4. 每个 rollout 只给起始锚点结算一次 best-of-rollout 绝对质量。
5. 中间程序不自动获得全局预算资格，整段代表程序才可加入。
6. 不做祖先回传、全局归一化、趋势加权或访问奖励。
7. 所有真实尝试，包括无效和退步，都进入事实图与后续可见窗口。
8. 初始化与正式搜索使用同一三步 rollout 和两阶段生成机制。
9. evaluator、轨迹和后续上下文只接收规范化的无注释可执行代码。
10. 最终最好程序只按原始 fitness 和同分简洁性确定。

## 11. 实验判据

V9.3 联合版本的短期比较至少同时观察：

- 同 evaluator 样本预算下的过程 best 与最终 best；
- rollout 内第一、第二、第三步分别产生改善和全局突破的比例；
- 先退后进的真实轨迹比例及其最终贡献；
- 每个起始锚点的 rollout 次数、代表质量与预算集中度；
- 新代表程序相对全部中间程序的筛选损失；
- 两阶段提示的解析成功率、Idea—Code 一致性抽样和模型调用成本；
- 四任务三重复完成后的 held-out 结果和稳定性。

V9.3 优于 V9.2 只能说明这一联合闭环更有效，不能单独证明三步长度、best-of-rollout 信用或两阶段提示中的任何一个组件是唯一原因。
