# TraceAAD V9.4 完整机制设计

> 状态：已实现。V9.4 是对 V9.3 决策粒度错误的机制修正：一次全局选择只产生一个 `Idea + Code`、一次评价和一次事实更新。V9.3 保留为固定三步 rollout 的历史实验版本，不在原实现上改写。

## 1. 科学问题

TraceAAD 要解决的是：在有限 evaluator 预算下，选择一份可执行程序作为锚点，把与它对应的算法改进历史组织为局部证据，帮助模型完成下一次算法修改，再根据真实结果更新后续预算分配。

轨迹的作用是保存和提供“这份程序如何形成、附近已经试过什么、实际结果如何”。它并不要求系统选定锚点后连续替模型做多次决策。V9.3 把轨迹的多步历史误等同于一次分配内固定执行三次马尔可夫决策，又从三次结果中选最好者结算。这改变了基本预算单元，也把轨迹证据、连续决策和 best-of 选择绑成了一个不可分辨的联合机制。

V9.4 回到最小而完整的闭环：

```text
选择一个锚点
    -> 为锚点构造一份局部轨迹证据
    -> 一次模型调用联合生成一个 Idea + Code
    -> 一次 evaluator 评价
    -> 更新事实、锚点信用和候选集合
    -> 重新全局选择
```

这里的一步是一次真实搜索决策，不是把三步 rollout 缩短为长度一的特殊情况。

## 2. 搜索状态

### 2.1 可执行锚点

程序节点 `a` 保存完整可执行代码、Idea、fitness、父节点、形成事件和创建次序。方向统一后的绝对质量为：

```text
q(a) = fitness(a)       最大化任务
q(a) = -fitness(a)      最小化任务
```

`q` 始终越大越好。V9.4 不使用全局 min–max、百分位归一化或随搜索总体变化的相对坐标。

### 2.2 锚点局部轨迹

每次锚点选定后，系统从事实图确定性构造唯一局部窗口，最多保留 8 个 `Idea—结果` 事件：

- 最多 4 个形成事件，说明当前程序怎样从祖先逐步形成；
- 最多 4 个深度 3 以内的近期下游事件，说明锚点附近已经测试过什么；
- 一侧不足时由另一侧补足；
- 事件按真实发生次序展示，不按 fitness 事后挑选；
- 下游事件可能来自不同真实分支，提示中明确标注，不伪造成一条线性链。

历史事件只展示 Idea、有效性、fitness、分支位置和必要失败反馈。历史代码不进入窗口；模型只读取当前锚点的一份完整代码。图只负责恢复真实谱系、识别当前窗口可见的有限祖先，并执行下述轨迹信用更新；它不使用子树最大值定义节点价值。

## 3. 单次联合生成

一次正式预算事件只进行一次模型调用。模型同时读取：

```text
任务与 fitness 方向
+ 锚点对应的局部轨迹窗口
+ 当前锚点 fitness
+ 当前锚点完整代码
```

然后只输出：

    Idea: <准确概括本次实现的一个算法思想>
    Code:
    ```python
    <一份完整可执行实现>
    ```

Idea 与 Code 必须在同一次响应中共同形成。系统不先生成多个 Action，不另开一次调用实现 Idea，也不在同一次锚点选择后自动继续第二、第三步。下一份预算开始前必须重新进行全局锚点选择和局部窗口构造。

代码在评价前经 AST 解析与规范化，删除注释和 docstring。后续 evaluator、事实图、工件和提示上下文只使用规范化的可执行代码。

## 4. 结果进入轨迹的方式

### 4.1 有效结果

解析成功且 evaluator 返回有限 fitness 时，新程序成为锚点的真实子节点。改善、持平和退步节点都保存在事实图中，也都获得后续全局选择资格。系统不因为一次退步就删除程序或禁止它继续发展。

### 4.2 候选无效

模型响应已返回后，解析失败或评价无效都会消耗一份搜索预算，但不会生成伪程序节点。它们作为生成事件挂在本次锚点上，局部窗口保存：

- 失败类别，例如 `parse`、`runtime_error`、`timeout`；
- 异常类型；
- 单行、截断后的 evaluator 反馈；
- 模型声明的本次 Idea。

完整失败代码只保留在离线候选工件中，不放入后续提示。这样模型能看到足以避免重复错误的局部证据，又不会让无效代码冒充可执行状态或占据上下文。

仅靠局部窗口仍会遗漏跨锚点重复发生的系统性错误。因此 V9.4 另维护一份有界的“已验证失败反馈”：汇总本次 task 运行中解析器或 evaluator 真正返回的失败类别、异常类型、精简消息和出现次数，每次最多向模型展示频次最高的 5 类。它从根生成阶段即开始积累，所以尚未形成可执行节点的失败也不会被遗忘。该信息是任务内的外部反馈，不是模型自行总结出的全局经验；提示明确要求只在实现风险相同时使用，不能把一次失败解释为对宽泛 Idea 的否定。

模型服务运输失败不属于算法尝试，不消耗 evaluator 搜索预算，也不进入轨迹；它只进入运行日志并受连续失败上限约束。

## 5. 有限多步折扣信用

一次生成决策仍然只有一步，但它产生的结果可能成为一段真实多步改进过程的新证据。V9.4 因而把“生成几步”和“价值看几步”分开：每次只生成一个子代，信用可以沿实际形成的轨迹有限回传。

从某个锚点生成有效程序 `x` 后，对 `x` 的祖先 `a`，令 `d(a,x)` 为二者的边距离。仅当 `1 <= d <= 3` 时记录：

```text
credit(a, x) = 0.5 ^ d(a,x) * [q(x) - q(a)]+ 
[y]+ = max(0, y)
```

这里的三层与局部窗口可见的下游深度一致。直接父代经过一层折扣，祖父代经过两层，曾祖父代经过三层；更远祖先的上下文看不到这次结果，也不更新信用。解析或评价无效以及有效但没有超过某祖先的结果，对该祖先记为零信用，但仍记作一次已经消耗的轨迹证据。

设 `N(a)` 是进入该锚点三层局部轨迹范围的预算事件数，`C(a)` 是上述折扣信用之和，则：

```text
Q(a) = q(a)                              N(a) = 0
Q(a) = q(a) + C(a) / N(a)                N(a) > 0
```

`q(a)` 始终是当前可执行代码的绝对质量；`C/N` 表示在该锚点附近已经观察到的有限多步增益。直接被选次数与进入轨迹信用的事件数分别记录，祖先收到回传不会被误写为“祖先又被直接调用了一次”。

这个定义有五个边界：

1. 不再使用 `max(q(a), q(x))` 作为一次结果，后代绝对分数不会原样复制给父代；
2. 同一优秀后代对不同祖先的影响由各自质量差和距离共同决定，不会使所有祖先同分；
3. 暂时退步节点若后来产生强后代，会获得直接而较强的信用，更早祖先只获得逐层衰减的信用；
4. 退步或无效结果记零而非虚构一个全局最差值，连续零结果会把此前偶然成功的平均增益稀释回 `q(a)`；
5. 信用只覆盖当前规范窗口能表达的三层局部过程，不做无限 full-path backup。

新子代拥有自己的 `q(x)` 和后续生产证据。回传只在优秀后代真正出现后发生，不提前猜测未知未来，也不宣称某个祖先或 Idea 对后代成功具有严格因果作用。

## 6. 严格突破只作为真实过程事实

V9.4 显式记录严格全局突破：新程序的有向 fitness 严格超过生成前的全局最好值。相同 fitness 下因代码更短而替换最终代表不计严格突破。

严格突破率用于离线分析搜索是否持续找到新的质量边界。它暂不以额外权重加入 `Q`。原因是突破事实与在线预算价值相关，但仅凭这一点不能确定一个跨任务稳定的加权公式；V9.4 先保留正确、可分析的事实定义，不再引入新的复合评分。

## 7. 全局预算选择

正式搜索时：

1. 按 `Q(a)` 从全部合格锚点中取前 10 个质量候选；
2. 每 5 次选择中的前 4 次，候选若存在尚未获得一次正式生产证据的锚点，则选择其中 `Q` 最高者完成基本验证，否则取 `Q` 最高者；
3. 第 5 次从同一前 10 质量区中选择直接尝试次数最少的锚点，次数相同时优先等待更久的早期锚点；
4. `Q` 完全同分时依次比较 `q(a)`、代码长度和创建次序。

一次事件结束后先更新所选锚点及窗口可见祖先的轨迹信用，再立即回到该规则。没有固定三步承诺、rollout 起点、rollout 代表程序或 best-of-rollout 筛选。所有有效子代都可以参与竞争。周期性覆盖只发生在轨迹评分筛出的优质局部内，不为低质量全局节点保留平均配额；它避免确定性第一名永久吞掉预算，也使得到多步信用的非终点锚点有真实重访机会。`4:1` 是尺度无关、可单独消融的实现常数，不是已证明的最优比例。

## 8. 初始化

初始化沿用 V9.2 的两节点微轨迹，避免恢复为孤立随机根，也不使用 V9.3 的三步强制 rollout：

1. 模型仅根据任务和函数契约提出 8 个互补算法策略；
2. 每个策略独立生成一个有效根程序；
3. 每个根按正式单步协议完成一次 bootstrap；
4. 每条路线在根与有效 bootstrap 子代之间选择绝对质量更好的可执行端点；
5. 按端点绝对质量选出 6 条路线进入正式候选集合。

理想无失败路径使用 `8 x 2 = 16` 份 evaluator 预算。未入选路线和无效事件仍保留在事实与工件中，但不进入正式预算集合。初始化完成时的 6 个锚点单独记录；正式搜索新增子代不会污染初始化数量统计。

## 9. V9.4 与 V9.2、V9.3 的准确差异

相对 V9.2：

- 保留一次锚点选择、一次联合 `Idea + Code`、一次评价的正确骨架；
- 信用从“被选锚点的直接子代绝对质量均值”改为“三层内正向后代增益的逐层折扣均值”；
- 失败从局部粗粒度类别扩展为局部精确反馈与任务内频次化的有界失败记忆；
- 严格全局突破获得无歧义的独立记录；
- 修正初始化锚点数量在搜索后被合格节点总数覆盖的观测错误。

相对 V9.3：

- 删除固定三步连续决策；
- 删除轨迹 Idea 决策与代码实现的两阶段调用；
- 删除 rollout 起点、步号、代表程序和 rollout 级结算；
- 初始化由每路线三步恢复为每路线一次 bootstrap；
- 有效子代不经过 best-of 代表筛选，全部成为真实候选锚点。

因此 V9.4 不是在 V9.3 上把 `rollout_length` 从 3 改成 1，而是删除错误抽象后重新定义一次搜索决策。

## 10. 完整闭环

```text
规划 8 个互补策略
    -> 各生成一个有效根
    -> 各完成一次联合 Idea + Code bootstrap
    -> 每条路线选更好的可执行端点，保留 6 条
    -> 按 Q 选择一个锚点
    -> 构造该锚点唯一的局部轨迹窗口
    -> 一次调用联合生成一个 Idea + Code
    -> 一次 evaluator 返回有效结果或已验证失败证据
    -> 更新事实图、三层局部轨迹信用、失败记忆和有效子代资格
    -> 在 Q 前 10 中按 4 次利用 / 1 次质量区覆盖重新选择锚点
    -> 直到 evaluator 预算耗尽
```

最终答案始终是全部有效程序中原始有向 fitness 最好者，同分时选择代码更短、创建更早者。`Q` 只服务在线预算分配，不替代最终任务目标。

## 11. 必须保持的机制不变量

1. 一次正式全局选择只对应一个候选和一次 evaluator 预算。
2. Idea 与 Code 必须由同一响应联合生成。
3. 每次候选结束后重新进行全局锚点选择，不能隐式继续固定后续步骤。
4. 历史完整代码不进入提示，当前锚点完整代码必须进入提示。
5. 有效退步节点进入事实图并获得锚点资格；无效候选只形成失败事件。
6. 失败反馈只来自真实解析或 evaluator 结果，不加入系统运输错误、失败代码或无来源建议。
7. 信用使用绝对任务尺度上的正向增益，按 `0.5^d` 最多回传三层，不做全局归一化、无限回传或最大值复制。
8. 基本验证后每 5 次选择必须包含 4 次最高 `Q` 利用和 1 次前 10 质量区内的最低访问覆盖。
9. 严格突破必须是全局 fitness 严格改善，同分择简不计突破。
10. 初始化和正式搜索使用相同的单步联合生成协议。
11. evaluator、事实图和后续上下文只接收规范化的无注释可执行代码。

## 12. 当前仍未解决的问题

- 固定 `4 + 4` 窗口仍是拓扑近期视图，不保证是对下一步最相关的算法知识；
- Idea 仍是模型对代码的自述，没有完成可靠的语义差异验证；
- 大多数 evaluator 仍只给标量 fitness，不能说明具体行为改善或退化；
- 路线之间没有可追溯的知识迁移；
- `Q` 表达锚点质量与三层内已观察到的折扣增益，固定 `0.5` 与三层边界是否合适仍需实验；
- 前 10 与 `4:1` 质量区内利用—覆盖比例仍是固定搜索协议，其跨任务最优性未知；
- 初始化每条路线只有一次 bootstrap，延迟显效方向仍可能被过早淘汰。

这些问题不在 V9.4 中用趋势权重、UCB、摘要器或新算子一次性填补。V9.4 首先恢复正确的决策单位和信息闭环，再用真实过程与 held-out 结果决定下一版应改哪一层。

## 13. 实验判据

V9.4 与 V9.2、V9.3 比较时至少报告：

- 相同 evaluator/sample 预算下的过程 best、最终 search best 和 held-out test；
- 每一份正式预算的有效率、局部改善率和严格全局突破率；
- 锚点及初始谱系的预算集中度；
- 退步节点后来产生改善或严格突破的比例；
- 重复失败类别是否在进入局部窗口或任务内失败记忆后下降；
- 初始化 16 份预算内的质量分布、bootstrap 改善率和 8 到 6 的筛选结果；
- V9.3 三步中的中间最好值在同预算口径下是否只是 best-of 机会增加，而非轨迹机制本身改善。

V9.4 的联合结果只能说明这一整套闭环是否有效，不能单独证明保留价值信用、失败反馈或单步联合提示中的某一个组件是唯一原因。
