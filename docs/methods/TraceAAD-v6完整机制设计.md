# TraceAAD V6：简约的轨迹进化

> 正式版本：Occam V6（2026-08-03）。实现位于 `llm4ad/method/traceaad_v6/`。
> 质量门控历史版已归档，见 [V6 开发复盘](../archive/development/TraceAAD-V6开发复盘.md)。
> V4、V5 继续由各自文档和实现独立维护。

## 1. 研究问题

LLM 自动算法设计面对的是稀疏、昂贵且带有较大生成不确定性的搜索：多数尝试不会突破，单次失败也不足以说明某个方向无效。进化搜索的价值正是在大量真实评价中逐步积累算法的来时路，让 LLM 可以从已有程序继续利用、换向探索或借鉴另一条路线。

TraceAAD 的核心问题是：**如何用算法改进历史帮助下一步生成，同时不过早用人工代理规则限制 LLM 与进化搜索的自由度？**

V6 的核心主张是：

> 保存真实的程序、修改和评价历史；用结果质量与随机探索选择下一条路线；把相关历史直接交给 LLM；让 evaluator 决定哪些算法真正有效。

V6 不要求每次尝试都产生突破，也不把过程分析指标变成优化目标。局部改进率、程序长度、代码差异、算子命中率和活跃程序唯一率用于理解搜索，不用于在线拒绝候选或强制改变搜索。

## 2. 从 V4 与 V5 保留什么

V6 保留 V4 的简单搜索骨架：固定规模轨迹种群、单结构父代、endpoint 与路线最好共同表示路线质量、UCB 保护低访问路线、扩张后再收缩种群。它也保留 V5 中已明确有用的细节：四种轨迹语义算子、双轨迹直接参考、Action 与 Code 共享同一上下文、fitness-first 且完全同分时择短。

以下机制因缺少独立因果证据而不进入当前协议：成熟度门槛、路线差异门槛、固定算子比例、强制删减、路线信用、在线程序去重、多层精英与差异保留、按结果标签筛选历史、初始化新颖性指令。删除这些规则不是断言它们永远无效，而是把举证责任还给后续受控实验。

## 3. 搜索状态与真实证据

候选程序记为 $p$，evaluator 返回 $f(p)$；内部统一为数值越大越好。只有成功解析、执行并得到有限评价值的候选才形成程序节点。

一条轨迹是从初始程序到当前程序的单父路径，包含：

- **endpoint**：当前继续延伸的位置；
- **compact best**：路径上 fitness 最好、完全同分时非空 LOC 最少的程序；
- 按时间排列的修改边：算子、Action、Implemented Idea、评价结果、相对父程序的变化、LOC 与代码变化。

`global best` 按相同的程序比较规则独立保存。参考路线只提供知识，不成为第二个结构父代。active 轨迹只保留最多 8 个在线节点，完整派生图仍保存全部事实。

模型声明的 Action 和 Idea 是上下文材料，不是经过证明的解释。解析、执行、超时和无效评价继续写入运行日志与 profiler，用于可靠性诊断和停止保护；它们不再经过在线排序后塞回提示词，也不形成第二套“尝试记忆”。

## 4. 上下文管理

每次 Action 请求包含：任务与待优化组件说明、主锚点完整程序、锚点形成历史和本轮算子说明。形成历史按时间展示 Action、Implemented Idea、fitness 与真实 outcome，不重复中间程序的完整代码。

双轨迹请求额外包含参考路线的 compact-best 完整程序及其形成历史。Action 与 Code 请求共享相同的主轨迹和参考轨迹上下文，Code 阶段再加入指定 Action，避免决策与实现断层。

历史不按“成功”“支持”“失败价值”等人工优先级重排。超过显式 context token 上限时，按确定规则从较早历史开始裁剪；任务契约、主锚点代码、本轮指令和 Code 阶段的指定 Action 始终保留。若双轨迹的 Action 或实际 Code prompt 无法放入上限，本批重新选择单轨迹算子并重新生成 Action，保证 Action 与 Code 看到一致历史。这是模型输入的物理边界，不是算法质量门控。

Action 使用最小传输契约：编号单行建议。解析器接收至多本批所需数量的有效 Action；数量不足只减少本批候选，不让整批有效输出作废。Code 必须满足目标函数签名、输入输出和 evaluator 契约。

## 5. 四个语义算子

| 算子 | 给 LLM 的方向 |
| --- | --- |
| `trace_ideate` | 从任务与历史出发尝试一个有希望的新方向 |
| `trace_refine` | 继续改进或修正当前算法 |
| `trace_transfer` | 考虑把参考路线中有用的思想迁移到主程序 |
| `trace_synthesize` | 考虑把两条路线的思想组合成一个更好的方案 |

这些名称表达搜索意图，不是硬约束。提示词不要求“只能改一个机制”“必须最小修改”“必须引用已支持证据”，也不强迫删除、保留或组合特定部分。

没有其他 active 路线时，`ideate` 和 `refine` 等概率可用；存在其他路线时，四个算子等概率可用。V6 不根据短期 plateau、LOC 增长、成熟度或历史命中率动态改写比例。算子仍完整记录，后续可以用受控实验判断某种调度是否真的改善最终算法质量。

## 6. 路线评分、父代与锚点

路线质量只表示它已经得到多好的程序：

$$
Q_i = 0.7 Q_{\mathrm{endpoint},i} + 0.3 Q_{\mathrm{best},i}.
$$

两项分别是 active endpoint 和 compact best 的并列感知 fitness 百分位。这里不混入父子增量、路线信用、代码长度或差异代理。

父代选择加入 UCB：

$$
A_i = Q_i + 0.25\sqrt{\frac{\log(1+N)}{1+n_i}},\qquad
P(\tau_i)=\operatorname{softmax}(A_i/0.2).
$$

$N$ 是已发起的主轨迹批次数，$n_i$ 是该路线被选为主轨迹的次数。新路线访问数从 0 开始；即使本批没有得到可评价代码，一次已发起选择也计入访问。

选中主轨迹后，endpoint 与 compact best 等概率成为结构锚点。endpoint 允许继续修复尚未成功的分支，compact best 允许从路线已知最好位置重新发展；V6 不用短期恢复规则预判哪一条必须被延续。

双轨迹算子从全部其他 active 路线中按 $Q$-softmax 选择参考。程序哈希和路线相似度不构成候选资格门槛。

## 7. 生成、评价与更新

每批先冻结 active、路线与 global-best 状态，再为同一主轨迹和锚点生成至多两条 Action。每条 Action 分别生成代码并调用 evaluator。所有有效子程序都从同一个结构锚点分支，使用同一批次前基线记录结果，避免 Action 顺序改变历史语义。

`positive_threshold` 只把父子变化标记为 improve、plateau 或 regress，供日志和后续分析使用；它不改变原始 fitness 排序、父代选择、程序接纳或生存。

代码解析失败不消耗评价预算。只要 evaluator 被调用，无论成功、超时、执行错误或结果无效，都消耗一次预算。只有有限有效结果进入派生图和 active frontier。

任何严格更优 fitness 都优先；只有 fitness 完全相同时，compact best 与 global best 才选择非空 LOC 更少的程序。V6 不设置 LOC 惩罚、长度上限或强制 trim。

## 8. 扩张与收缩

active frontier 目标规模为 $M=30$。有效子程序产生新的 active 轨迹；规模达到 $2M$ 时收缩回 $M$：

1. 强制保留包含当前 global best 的 active 路线；
2. 其余位置按路线 $Q$-softmax 无放回抽样；
3. 退出 active 的路线转为 archived，完整派生事实不删除。

相同 endpoint 代码可以属于不同来时路，因此不在线去重。V6 也不预留固定精英层、成熟路线层或差异席位。质量偏好由 $Q$ 表达，探索由随机抽样、UCB、多路线扩张和四种 LLM 语义变化共同产生。

## 9. 完整流程

```text
1. 在预算内生成最多 M 条有效初始轨迹。
2. 重复直到终止：
   a. 计算 Q + UCB，随机选择主轨迹；
   b. 在 endpoint / compact best 中随机选择锚点；
   c. 根据是否存在其他路线，从可用算子中等概率选择；
   d. 双轨迹时按参考路线 Q 随机选择一条参考；
   e. 生成 Actions、代码并调用 evaluator；
   f. 统一写入有效子节点，更新路线、global best 与日志；
   g. active 达到 2M 时按 global-best + Q-softmax 收缩到 M；
   h. 按周期原子保存 checkpoint。
3. 返回 global best。
```

预算耗尽、外部终止、active 为空、连续 20 次生成/解析失败或连续 20 个批次没有候选进入 evaluator 时停止。初始化不要求候选必须不同于此前思想。

## 10. 工程护栏与可复现性

以下约束用于保证搜索真实、可恢复和可审计，不用于塑造算法方向：

- 单结构父代和有限评价值不变量；
- evaluator 预算、失败计数与停滞停止；
- 函数接口、parser/validator 和 context hard limit；
- 实际 prompt/response、候选、评价和种群事件日志；
- 原子 checkpoint、随机数状态、global best 与完整图状态；
- 严格的配置一致性检查。

当前协议标识为 `traceaad-v6-v1`，checkpoint schema version 为 8。checkpoint 同时核对完整搜索配置以及任务描述、模板、evaluator 类型、模型类型/名称和服务地址的非秘密身份；正式 runner 另外核对完整 task/evaluator 参数。质量门控版 V6 的旧 checkpoint 不允许静默续跑到当前协议；旧实验只保留为历史工件，见 [V6 开发复盘](../archive/development/TraceAAD-V6开发复盘.md)。

## 11. 默认协议

| 配置 | 默认值 |
| --- | ---: |
| 评价预算；active 目标/收缩阈值 | 1000；30 / 60 |
| 每批 Action；在线轨迹节点 | 2；8 |
| Q 的 endpoint / compact best | 0.7 / 0.3 |
| UCB 系数；softmax 温度 | 0.25；0.2 |
| 无参考时算子 | `ideate/refine` 等概率 |
| 有参考时算子 | 四算子等概率 |
| 主锚点 | endpoint / compact best 等概率 |
| 参考路线 | 其他 active 路线按 Q-softmax |
| Action / Code 输出上限 | 1024 / 8192 token |
| checkpoint 周期；连续停滞上限 | 10 个完成批次；20 |

上下文输入上限由模型与实验配置显式给出。随机种子、模型、任务 evaluator、预算和所有搜索参数必须记录。

## 12. 评价边界

V6 的成败首先由训练搜索得到的算法质量、重复实验稳定性和独立测试表现判断。过程分析用于回答机制是否实际运行、在哪些状态下有效以及哪里浪费预算，不能反过来成为搜索必须追逐的分数。

需要由候选、轨迹和种群事件直接统计或重放计算的指标包括：父子改善、route/global-best 更新、后半程突破、算子条件结果、active 代码重复率、程序 LOC、代码变化、有效候选率和达到目标质量的 evaluator 调用数。任何新门控或调度规则都需要独立消融证明其提高最终算法质量，不能只因为它改善某个过程指标就进入主协议。
