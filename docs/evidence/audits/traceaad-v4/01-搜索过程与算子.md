# TraceAAD v4 搜索过程与算子审计

> 状态：2026-07-24 冻结过程证据，不承担当前方法设计。

## 1. 快照范围与核心判断

本页是对 TraceAAD v4 搜索候选、父子修改边和算子行为的冻结快照。统计读取时间为 **2026-07-24 15:26:52（Asia/Shanghai）**。当时 15 个 run 中，Online Bin Packing 和 OP-ACO 的 6 个 run 已到 1000 次评估预算；TSP Construct、CVRP-ACO 和 Knapsack Construct 的 9 个 run 仍在运行。因此：

- 完整 run 可以用于观察全程阶段变化；
- 未完成 run 只代表截至快照时已经发生的过程，不能作为最终结果；
- 跨 task 不直接平均原始 fitness，只比较 `method_events.jsonl` 已经按优化方向记录的父子 `delta/outcome`、成功率和比例。

当前证据支持三个阶段判断。

1. **基于轨迹的搜索确实能够形成连续、多步的有效改进链。** TSP 和 CVRP 中都观察到了同一思想路线经 `trace_ideate` 引入、再由 `trace_refine` 连续改进并多次刷新全局最好。这说明 v4 并非只靠彼此独立的随机程序撞出结果。
2. **轨迹价值初步表现出“把预算放到更可能产生全局最好解的路线”的区分力。** 五个 task 中，选中价值最高四分位的候选，其直接父子改进率都低于最低四分位，但全局 best-update yield 都最高。高价值路线更难继续改，却更可能在成功时推进搜索前沿。
3. **搜索效率仍有明显问题。** 直接改进率随预算推进普遍下降；KP 在前 25% 预算后几乎停滞；大多数候选使代码变长，且变短候选在多数条件下并不更差；`trace_ideate` 和 `trace_refine` 的有效性具有明显 task 依赖，而当前调度仍是均匀随机。

这里的“支持”表示观测行为符合机制预期；完整方法的有效性由最终质量、held-out、重复稳定性和方法比较共同判断，过程统计用于解释机制怎样工作。

## 3. 统计口径

后续表格使用以下定义：

- `LLM 解析成功率`：`llm_calls.jsonl` 中对应 `stage=code`、operator 的 `status=ok / 全部调用`；
- `评估成功率`：已解析程序中 `program_evaluated.status=ok` 的比例；
- `直接改进率`：成功子节点相对当次所选锚点的 directed delta 大于 `1e-6`；
- `best yield`：成功子节点触发 `best_updated` 的比例；
- `变长率`：子程序非空物理行数高于父程序的比例；
- `阶段 Q1–Q4`：按 `sample_order / 1000` 分为 `(0,25%]`、`(25%,50%]`、`(50%,75%]`、`(75%,100%]`；
- `轨迹深度`：选择发生时保留的 edge 数，受 `max_trajectory_length=8` 限制，最大为 7。

成功的 `program_evaluated` 按事件顺序对应连续 node id；初始化的 `trajectory_created` 和每个 `child_accepted` 用于重建轨迹节点序列。父子代码来自 `logs/samples/samples_*.json`。每个成功评估的子节点都会进入派生图，因此日志中的 `child_accepted` 不表示“质量筛选通过”，只表示有效程序被保存。

## 4. 两个搜索算子的行为

### 4.1 解析、评估与产出

| Task | Operator | 成功子代数 | LLM 解析成功率 | 评估成功率 | 直接改进率 | Best yield | 变长率 | LOC 增量中位数 |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| CVRP-ACO | ideate | 947 | 99.9% | 93.1% | 18.2% | 2.96% | 76.2% | +23 |
| CVRP-ACO | refine | 925 | 99.7% | 95.4% | 15.9% | 2.49% | 58.8% | +4 |
| Knapsack | ideate | 1020 | 96.9% | 97.2% | 4.61% | 0.10% | 78.3% | +20 |
| Knapsack | refine | 1184 | 98.5% | 98.0% | 3.04% | 0.17% | 70.7% | +8 |
| Online Bin Packing | ideate | 1247 | 98.4% | 84.1% | 8.90% | 1.36% | 73.9% | +12 |
| Online Bin Packing | refine | 1396 | 99.7% | 97.8% | 9.89% | 1.50% | 62.0% | +2 |
| OP-ACO | ideate | 1367 | 99.8% | 92.9% | 9.14% | 1.76% | 62.7% | +10 |
| OP-ACO | refine | 1375 | 100.0% | 95.6% | 11.6% | 1.24% | 56.4% | +3 |
| TSP Construct | ideate | 1097 | 98.4% | 93.7% | 11.5% | 2.28% | 70.7% | +19 |
| TSP Construct | refine | 1186 | 99.3% | 97.2% | 19.2% | 3.71% | 60.3% | +3 |

【观测事实】

- 两个 operator 的 LLM 解析成功率整体很高，最低仍为 KP ideate 的 96.9%。主要损失发生在程序评估而非格式解析。
- `trace_refine` 在五个 task 上都具有更高的评估成功率。OBP 差距最大：97.8% 对 84.1%。OBP ideate 共有 235 个已解析程序评估失败。
- TSP 中 refine 的直接改进率和 best yield 都明显高于 ideate，而且三个 run 分别为 18.8% 对 10.7%、19.6% 对 12.7%、约 19.4% 对 11.4%，方向一致。
- CVRP 中 ideate 的直接改进率和 best yield更高；KP 中两个算子都已接近停滞；OP-ACO 中 refine 更常改善父节点，但 ideate 的全局 best yield 更高。
- 每次迭代理论上可产生两个程序。各 task/operator 的平均有效子代为 1.65–1.93。OBP ideate 的空迭代率为 2.92%，其他组合均不超过约 1.01%。

【机制解释】

- ideate 更偏向结构性扩张，refine 更偏向局部修改：前者在所有 task 上都更容易使代码变长，LOC 增量中位数也明显更大。这与两个算子的提示约束一致，说明算子名称并非只有表面差异。
- TSP 需要围绕已形成的强启发式持续调节权重、动态阶段和局部结构，refine 因而更合适；CVRP 中仍可能需要引入新的容量与几何结构，ideate 保持较高价值；OP-ACO 中“更常修好父节点”和“更常刷新全局最好”分别落在两个算子上，显示二者具有互补角色。
- OBP ideate 的高评估失败率表明大幅结构创新更容易破坏运行约束或超出评估边界。由于 `method_events` 没有记录具体失败原因，这一解释仍需结合 evaluator 的异常类型验证。

【值得改进】

当前 operator 每次由均匀随机选择。统计已经显示 operator 效率随 task、搜索阶段和目标不同而变化，固定 1:1 会把预算分给当前低收益或高失败的 operator。v5 可以记录“有效子代、相对轨迹最好增益、全局 best-update、失败”四类 operator 信用，先做离线 replay，再决定是否引入轻量的 task/阶段自适应调度。

## 5. 搜索是否持续有效

### 5.1 随预算推进的产出

| Task | Q1 改进 / best | Q2 改进 / best | Q3 改进 / best | Q4 改进 / best |
|---|---:|---:|---:|---:|
| CVRP-ACO | 24.5% / 4.03% | 16.2% / 3.51% | 约 9.7% / 0.19% | 尚未覆盖 |
| Knapsack | 11.0% / 0.46% | 0.82% / 0% | 约 0.6% / 0% | 部分覆盖，约 0.6% / 0% |
| Online Bin Packing | 15.5% / 3.79% | 7.41% / 1.02% | 8.70% / 0.88% | 6.38% / 0.16% |
| OP-ACO | 20.5% / 3.62% | 11.2% / 2.24% | 7.21% / 0.14% | 3.50% / 0.15% |
| TSP Construct | 19.0% / 3.59% | 16.7% / 4.03% | 13.2% / 1.49% | 部分覆盖，约 10.1% / 2.53% |

【观测事实】两个完整 task 都呈现明显的后期收益衰减。OBP 的 best yield 从 Q1 的 3.79% 降至 Q4 的 0.16%；OP-ACO 从 3.62% 降至 0.15%。KP 在 Q1 以后几乎不再产生直接改进，且本快照中仅三个非初始化子代刷新过全局最好。

【机制解释】有限任务上的算法改进本来会随前沿提高而变难，下降本身不能证明机制失效。但 KP 大量 plateau 与代码持续增长共同出现，更符合“当前路线已形成等价实现簇，生成仍在改写或叠加结构，却没有获得新的行为”的解释。OBP 和 OP-ACO 后期仍有少量改进，但全局推进已很稀疏。

【证据不足】阶段同时混合了父节点变强、轨迹变深、程序变长和上下文变长。需要以同一个锚点做 early/late prompt replay，或做 matched-history 对照，才能区分“问题已接近上限”和“上下文/搜索机制后期退化”。

| Task | 深度 0 改进率 | 深度 1–2 | 深度 3–4 | 深度 5–7 | 深度 5–7 的占比 |
|---|---:|---:|---:|---:|---:|
| CVRP-ACO | 30.8% | 23.6% | 约 27.1% | 约 15.4% | 约 85% |
| Knapsack | 38.1% | 7.14% | 4.06% | 约 1.2% | 约 61% |
| Online Bin Packing | 15.5% | 8.54% | 6.67% | 9.52% | 84% |
| OP-ACO | 11.1% | 22.7% | 11.1% | 9.58% | 86% |
| TSP Construct | 23.1% | 19.3% | 14.9% | 约 14.9% | 81% |

【观测事实】搜索的大部分预算发生在保留深度 5–7 的轨迹上。KP 深度 5–7 的候选中 82.7% 是 plateau，直接改进率只有约 1.2%，没有刷新全局最好。

【机制解释】8 节点滑动窗口在真实运行中很快成为常态。深轨迹能够保存连续的来时路，但“轨迹已满”本身没有触发换路、压缩或整合。KP 表明搜索可以长期在深而同质的路线中继续消耗预算。

【证据不足】深度与搜索时间、父节点强度高度相关，不能据此认定“更长历史导致更差生成”。必须比较同一父程序下 0、2、4、8 步历史的配对生成，才能判断历史长度的边际价值。

## 6. 轨迹价值与锚点的初步交叉检查

这部分只使用已经保存的 `selected_value` 和可重建锚点，完整评分、UCB 和种群结论由独立审计页给出。

### 6.1 高价值路线是否带来更有价值的子代

每个 task 内将有有效子代的选择事件按 `selected_value` 分为四分位：

| Task | 最低价值 V1：直接改进 | 最高价值 V4：直接改进 | V1：best yield | V4：best yield |
|---|---:|---:|---:|---:|
| CVRP-ACO | 23.3% | 12.2% | 0.22% | 6.20% |
| Knapsack | 8.11% | 4.57% | 0% | 0.55% |
| Online Bin Packing | 19.3% | 8.73% | 0.75% | 3.22% |
| OP-ACO | 18.2% | 9.53% | 0.29% | 3.67% |
| TSP Construct | 22.5% | 11.7% | 1.38% | 5.24% |

【观测事实】五个 task 的方向完全一致：弱价值路线更容易相对父节点改善，高价值路线更容易刷新全局最好。V4/V1 的 best-yield 倍数约为 CVRP 28.8 倍、OBP 4.3 倍、OP-ACO 12.7 倍、TSP 3.8 倍；KP 的 V1 为零，不能计算倍数。

【机制解释】直接改进率奖励“从弱父节点反弹”，并不能衡量预算是否推进搜索前沿。当前轨迹价值更像是在识别强而有潜力的路线：其局部改进更困难，但成功结果更有全局意义。这是 v4 轨迹评分目前最强的正向过程证据之一。

【证据不足】`selected_value` 是动态种群内的相对值，且这里只观察被选中的路线；没有完整记录同一时刻所有路线的选择概率和反事实产出。该关联不能单独证明 quality/trend 权重或 UCB 的因果贡献。

### 6.2 endpoint 与轨迹历史最好锚点

在 endpoint 与该轨迹历史最好节点不同的情况下，可以明确区分两类随机锚点。

【观测事实】

- 从较弱 endpoint 出发的直接改进率很高：CVRP 37.4%、KP 49.3%、OBP 28.6%、OP-ACO 30.6%、TSP 27.5%。
- 但这些子代达到或超过该轨迹历史最好分数的比例只有 CVRP 12.3%、KP 26.1%、OBP 10.6%、OP-ACO 5.06%、TSP 7.56%；真正超过轨迹历史最好的比例进一步降至 1.45%–8.98%。
- 从历史最好节点出发的全局 best yield 在 CVRP、OBP、OP-ACO、TSP 上分别为 4.08%、1.48%、1.09%、4.20%，对应 endpoint 锚点为 1.20%、1.30%、0.21%、1.94%。KP 两者均没有刷新全局最好。

【机制解释】endpoint 锚点的高“直接改进率”主要是从一次退步中部分恢复，不能与从强锚点继续突破等价。内部 best 锚点更符合利用历史执行回退并重新开发强路线的设计，尤其在 TSP 和 CVRP 上表现明显。endpoint 仍可能携带失败边界后的新结构，是否值得继续应取决于它能否恢复轨迹最好，而不应只看相对 endpoint 的正 delta。

【值得改进】日志和 operator 信用应同时记录：

1. `delta_parent`：相对当前锚点，判断动作是否修复局部状态；
2. `delta_path_best`：相对轨迹历史最好，判断是否真正恢复或推进该路线；
3. `delta_global_best`：相对全局最好，判断是否推进搜索前沿。

只用第一层会系统性高估从退步 endpoint 出发的产出。

## 7. 程序长度与评估成本

【观测事实】

- ideate 的变长率为 62.7%–78.3%，refine 为 56.4%–70.7%。变短候选的直接改进率在绝大多数组合中与变长候选相当或更高。例如 OBP refine 为 13.6% 对 7.75%，OP-ACO refine 为 12.9% 对 10.6%，KP refine 为 4.68% 对 2.16%。
- 演化候选的 LOC 中位数已经达到 CVRP 244–248、KP 144–147、OBP 144–145、OP-ACO 171–182、TSP 185–198；对应初始化程序的中位数只有 74、39、29、53.5、54。
- LOC 与评估时间的 Spearman 相关在 OBP 为 0.80–0.82、TSP 为 0.42–0.46、KP 为 0.36–0.40；OP-ACO 只有 0.14–0.17，CVRP 反而约为 -0.44。LOC 不是跨任务统一的运行复杂度代理。
- OBP 成功候选的评估时间中位数约 3.1–3.2 秒，P90 约 17.7–18.7 秒；TSP 中位数约 2.1–2.4 秒，P90 约 10.9–11.1 秒。程序增长已经在部分 task 上形成可见预算成本。

【机制解释】当前两个 operator 都具有“在父程序上继续添加结构”的生成惯性，ideate 尤其明显。短程序仍能产生有效改进，说明复杂度增长不是搜索质量的必要代理。该现象会同时拉长代码提示、生成响应和部分 task 的评估时间，从而降低单位墙钟时间内的有效尝试数。

【证据不足】CVRP 的负相关说明 LOC 可能与程序是否提前退出、计算路径及机器并发负载共同变化。v5 应直接记录单次函数调用数、超时、CPU 时间和 AST/圈复杂度，不能用 LOC 取代真实成本。

## 8. 连续改进链：轨迹机制怎样表现出作用

### 8.1 TSP 的动态 regret 路线

在 `tspc_v4_rep1` 中观察到同一条可追溯路线：

1. `p15 → p36`，ideate 引入 dynamic regret，`delta=+0.22596`，刷新全局最好；
2. `p36 → p55`，refine 将未来成本改为加权平均，`delta=+0.02662`，再次刷新；
3. `p55 → p79`，refine 引入随剩余节点数变化的动态温度，`delta=+0.00891`，再次刷新。

后续同一思想家族还继续引入 destination alignment、局部密度和动态邻域规模等修改。证据位于：

`experiments/tsp_construct/traceaad/version4/20260723_181743_tspc_v4_rep1/logs/method_events.jsonl`

### 8.2 CVRP 的几何—容量路线

在 `cvrp_v4_rep1` 中观察到：

1. `p127 → p139`，refine 平滑角度 sector density，`delta=+0.47422`；
2. `p139 → p144`，ideate 加入密度自适应 detour penalty，`delta=+0.24758`；
3. `p144 → p172`，refine 加入 capacity slack，`delta=+0.08857`；
4. `p172 → p192`，refine 加入 radial alignment 并归一化 detour，`delta=+0.00811`。

四步都刷新了当时的全局最好。证据位于：

`experiments/cvrp_aco/traceaad/version4/20260723_204526_cvrp_v4_rep1/logs/method_events.jsonl`

【观测事实】有效结果可以沿同一父子链连续出现，并且 ideate 与 refine 会交替承担“引入结构”和“细化结构”的角色。

【机制解释】这些链条符合 TraceAAD 的核心主张：历史保存了思想从何而来，后续动作能够在已有机制上继续细化，而不是每一步重新开始。它们也解释了为何高价值路线即使直接改进率较低，仍值得继续获得预算。

【证据边界】案例证明这种基于来时路的连续工作方式确实发生过，但不能由单个案例判断其中哪个提示成分贡献最大。若后续需要解释组件贡献，可以在固定状态下做局部对照；这不影响用完整 TraceAAD 的整体结果评价方法。

## 9. 种群管理的已知事实与可观测性缺口

【观测事实】截至快照，五个 task 分别触发了 CVRP 59、KP 71、OBP 86、OP-ACO 88、TSP 73 次 population management。每次通常在 active pool 达到 60 或 61 时压回 30，并预留 3 条 elite 和 3 条 diversity route。机制稳定执行，没有观察到 active pool 无界增长。

【证据不足】`population_management` 事件只记录 before/after、数量和模式，没有记录：

- 哪些 trajectory 以 elite、diversity 或 softmax 身份存活；
- 哪些 trajectory 被归档；
- 管理前后的 quality、trend、scalar value、相似度和访问次数；
- global-best route 是否因特殊保护而存活；
- 新路线是否在第一次获得访问机会前就被淘汰。

因此当前日志只能证明“有界种群管理被执行”，不能从历史事件可靠判断“管理保留了正确路线”或“差异性 reserve 有效”。`latest.json` 只能给最终时刻状态，不能恢复每次管理的反事实候选集。

## 10. 综合判定

### 10.1 已有支持

- **多步轨迹能够承载连续算法改进。** 多个 task/run 中存在清晰的连续 best-update 链，且两个 operator 在链中承担不同角色。
- **轨迹价值与搜索前沿推进具有稳定关联。** 五个 task 的最高价值四分位均具有最高 best yield；这个结论比“直接改进率更高”更符合预算分配目标。
- **内部最好锚点具有实际价值。** 当 endpoint 已退步时，从历史最好位置重新分支更常产生全局最好解。
- **两个算子具有可辨别行为。** ideate 更激进、更长、更容易评估失败；refine 更保守、更可靠。二者的相对收益随 task 变化。

### 10.2 部分支持或值得改进

- **endpoint 延续只获得部分支持。** 它经常改善弱 endpoint，但多数结果仍没有恢复轨迹历史最好。应使用 `delta_path_best` 区分真正修复与表面反弹。
- **均匀 operator 调度缺乏效率依据。** TSP、CVRP、OBP 和 OP-ACO 已出现稳定的 task-specific 差异；KP 则需要停滞检测，而不是继续均匀抽样。
- **深轨迹后期存在停滞。** 轨迹深度 5–7 占绝大多数预算，KP 尤其形成大量 plateau。应检验历史压缩、换路和整合触发。
- **复杂度增长没有被收益约束。** 变短候选并不更差，部分任务的运行成本与 LOC 明显相关。

### 10.3 当前无法判断

- 不同历史表达方式分别怎样影响整体搜索；
- quality、trend 和 UCB 各自贡献了多少；
- 失败/退步历史是否真的帮助模型避开重复错误；
- diversity reserve 和 softmax survivor 是否保留了正确的路线；
- ideate 评估失败究竟来自语法、运行异常、超时还是任务契约破坏。

## 11. 下一步最小验证

1. **历史表达案例 replay。** 固定同一 task、父程序、action 和模型条件，比较近期原始轨迹与加入全局搜索认识等候选表达。主要观察评估成功、`delta_parent`、`delta_path_best`、best-update 和是否重复已失败方向，用于选择更适合整体搜索的知识表达。
2. **轨迹价值校准与消融。** 保存每次 active pool 全量 `quality/trend/scalar/visit/UCB/selection_probability`；比较 v4、无 trend、无 UCB，并用后续一批候选的 `delta_path_best` 和 best-update 做校准。
3. **operator 离线信用。** 不立即增加复杂 bandit。先按 task、阶段、轨迹状态统计四类信用，验证一个简单的滑动窗口成功率调度是否会优于 1:1。
4. **锚点配对实验。** 对 endpoint 已低于 path best 的同一轨迹，同时从 endpoint 和 path best 生成；分别报告局部修复、恢复 path best、超过 path best 和刷新 global best。
5. **KP 停滞实验。** 在 Q1 后触发换路、历史压缩或 consolidation，与继续原策略配对，检查能否减少 plateau 而不损失 best。
6. **补齐 population 事件。** 每次管理记录候选与存活 trajectory id、角色、价值、相似度、访问次数和是否含 global best，使种群机制第一次具备可审计性。

复现时应先复制或冻结仍在运行的日志，并记录读取时间。统计过程按以下顺序进行：

1. 以 `program_evaluated.status=ok` 的事件顺序建立 `node_id → sample_order`；
2. 用 `trajectory_created`、`operator_selection` 和 `child_accepted` 重建每次选择时的轨迹与锚点；
3. 用 `best_updated.new_best_node_id` 标记全局最好产出；
4. 从 samples 文件读取父子程序，按非空物理行统计 LOC；
5. 在 task 内按 selected value、sample 阶段、轨迹深度和锚点类型分层；
6. 所有父子 `delta` 直接使用日志中的 directed delta，不混合或重新缩放不同 task 的原始 fitness。
