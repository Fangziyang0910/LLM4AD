# TraceAAD v4 机制审计

> 状态：v4 搜索过程的冻结审计与证据索引。各页中的 v5 建议保留其形成时的研究判断，不作为当前设计规范；当前实现与下一版本分别见[TraceAAD v4](../../../methods/TraceAAD-v4完整机制设计.md)和[TraceAAD v5](../../../methods/TraceAAD-v5完整机制设计.md)。

## 1. 审计目标

TraceAAD 的核心假设是：算法改进历史包含当前程序本身没有的决策信息，搜索应当利用这条来时路决定下一步延续、修复、回退或换向。v4 的算子、轨迹价值、父代与锚点选择、上下文构建和种群管理都是支撑这一假设的机制，不能分别看到一个正相关就各自宣称有效。

本轮审计围绕一条完整因果链展开：

> 历史被正确记录 → 有用历史进入提示 → LLM 的下一步决策受历史影响 → 搜索把预算分给值得继续的路线 → 种群保留质量、潜力和路线覆盖 → 有限预算内更稳定地产生高质量程序。

现有运行工件用于验证这条链上的行为是否出现、各环节是否具有区分度，以及哪些现象与最终改进相关。TraceAAD 作为完整机制的主要证据来自公平协议下的最终质量、held-out 泛化、重复稳定性和 SOTA 表现；过程审计与后续消融负责解释各组成部分为什么有效、适用边界在哪里。所有过程结论仍须标明证据等级。

## 2. 结论书写协议

每项结论按下面四层记录：

1. **观测事实**：日志、程序、提示词或统计直接显示了什么，给出 task、run、sample、node/trajectory 和口径。
2. **关联判断**：两个已观测量是否共同变化，例如某类锚点之后的直接改进率更高。
3. **机制解释**：结合实现与研究主张，对现象提出因果解释。统一使用“支持”“更符合”或“可能”，不写成已经证明。
4. **待验证假设**：指出需要怎样的 replay、配对生成或消融才能区分竞争解释。

“代码按某种方式实现”只证明机制存在，“日志中某个事件发生”只证明机制被执行，“后续结果更好”才说明它可能有用；真正的因果有效性还需要反事实对照。

## 3. 数据范围与分析单位

当前主分析范围是 `experiments/*/traceaad_v4/version4/` 下保存 `method_events.jsonl` 的 15 个 run，覆盖 TSP Construct、CVRP-ACO、Knapsack Construct、Online Bin Packing 和 OP-ACO，每个 task 三个重复。先逐 run 核对预算、终止原因、样本完整性和配置；未完成 run 只进入其实际覆盖区间，不与完整 run 直接比较最终结果。

分析使用四种单位：

- **候选程序**：观察解析/评估成功、分数、长度、运行成本和是否刷新全局最好；
- **父子修改边**：观察一次 action 相对所选锚点的直接收益，是判断算子和上下文效果的主要单位；
- **轨迹选择事件**：观察价值、访问次数、锚点和下一批结果，是判断预算分配是否有效的主要单位；
- **种群管理周期**：观察管理前后的路线质量、覆盖、访问机会和 global-best route 是否仍可继续扩展。

跨 task 聚合时使用方向统一的相对量、分位数或分别报告，不直接平均不同尺度的原始 fitness。

## 4. 机制问题矩阵

| 核心环节 | 首要问题 | v4 可观测指标 | 当前证据边界 |
|---|---|---|---|
| 轨迹记录 | 历史是否完整、顺序正确、能表达成功/停滞/退步和分支位置 | edge/node 对齐率、delta/outcome 一致性、截断情况、选中锚点位置 | 可直接核对 |
| 上下文构建 | 提示中是否提供了对下一步有用且匹配的历史 | 历史步数、prompt 占比、锚点前后信息、失败边界是否出现、长度增长 | 可判断“提供了什么”，不能直接证明模型因它而改变 |
| 历史利用 | LLM 是否延续有效思想、避开失败、修复退步或从内部节点回退 | action/idea/code 人工编码，一致性和重复试错率 | 需要透明抽样；语义判断保留不确定性 |
| 搜索算子 | `trace_ideate` 与 `trace_refine` 是否产生可辨别且互补的行为 | 直接改进率、delta 分布、best-update、失败率、代码变化、阶段表现 | 随机算子分配支持关联比较，仍受父代状态混杂 |
| 轨迹价值 | quality/trend 是否预测被选路线的下一步产出 | 分量分布、并列率、校准分箱、与子代改进/best-update 的关系 | 需从 checkpoint/state 重建；selected value 单字段不足时标记缺口 |
| 父代调度 | softmax + UCB 是否兼顾高价值路线和访问公平 | 访问集中度、低访问路线获选率、重复选择间隔、选择概率 replay | 没有同 run 的 `ucb_c=0` 反事实 |
| 锚点选择 | endpoint/best 内部锚点是否分别支持延续和回退修复 | 锚点类型、距 endpoint 距离、后续 delta、回退后是否超过旧 endpoint | 随机二选一提供较好的自然比较，但仍需分层控制 |
| 种群管理 | `2M→M` 是否给新路线试错时间，并保留质量与路线覆盖 | 管理频率、管理前后质量/相似度、路线寿命、首次被访问前淘汰率、best route 活性 | 当前事件若未记录保留 ID/角色，只能用 checkpoint 近似并登记可观测性缺口 |
| 整体搜索 | 上述环节是否共同带来有效的 anytime search | best 曲线、AUC、达到阈值样本数、重复稳定性、held-out 结果 | 只能说明 v4 整体表现；各组件贡献需要消融 |

## 5. 三条并行证据链

### 5.1 搜索过程与算子

逐 task、逐 run 统计初始化和两个语义算子的调用数、有效候选数、解析/评估失败、父子 directed delta、改进/持平/退步比例、best-update yield、程序长度增量和评估时间。进一步按搜索早中晚期、轨迹深度、锚点类型分层，判断算子差异是否稳定，而不是由某个 task 或搜索阶段造成。

### 5.2 轨迹评分、选择与种群

重建每次选择时的 active pool、质量/趋势/标量价值、访问次数与 UCB 调整，检查价值是否有区分度及其对下一步收益的校准性。单独分析内部 best 锚点相对 endpoint 的作用，以及每次 `2M→M` 管理对质量、路线差异和后续可改进性的影响。

### 5.3 上下文与轨迹案例

使用预先声明的分层抽样，而不是只挑成功故事。每个 task 至少抽取明显改进、明显退步、长期停滞、内部锚点回退和端点延续案例；同时抽取若干随机事件作基线。对 action、response idea 和代码进行人工编码：

- 是否明确使用了历史中的有效思想；
- 是否识别并避开已经失败的方向；
- 是否真的执行了 operator 约束；
- action、idea 与代码是否一致；
- 是否重复过去已经测试过的尝试；
- 历史信息是否被长代码或重复文本淹没。

案例只能说明机制怎样工作或怎样失效；只有编码比例和跨任务重复出现后，才上升为一般性现象。

## 6. 综合判断方式

最终不按“算子有效、评分有效、种群有效”简单罗列，而按核心因果链给每个环节判定：

- **已有支持**：实现被执行，过程行为符合设计，而且在多个 task/run 中与预期结果稳定关联；
- **部分支持**：机制被执行，但效果只在部分条件出现，或存在明显竞争解释；
- **当前无支持**：机制虽然存在，却没有观察到其预期行为或区分度；
- **无法判断**：日志缺字段或缺反事实，需要新增 instrumentation 或消融。

随后形成最小后续实验表。优先级由“是否解释整体 SOTA 机制的关键行为、是否修复已经观测到的搜索浪费”决定；单独调整 trend、UCB、内部锚点、差异 reserve 或延迟管理时，每次只改变一个职责。组件对照用于贡献解释与机制收缩，不作为完整 TraceAAD 方法成立的前置条件。
