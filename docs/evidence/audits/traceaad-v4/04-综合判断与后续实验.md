# TraceAAD v4 机制审计：综合判断与后续实验

> 状态：基于 2026-07-24 冻结审计形成的阶段判断；后续方法取舍以当前方法规范为准。

## 1. 总体结论

TraceAAD v4 已经在真实运行中形成了轨迹驱动搜索，而不是只把“轨迹”写在方法名称里。轨迹参与了质量与趋势计算、父代调度、内部锚点回退、两阶段 LLM 上下文和种群生存；TSP 与 CVRP 也出现了沿同一思想路线连续多步刷新全局最好的案例。五个 task 中，高 `selected_value` 路线都更容易产生 global-best update，UCB 确实把更多概率分配给未访问路线，global-best route 在 15/15 个冻结 checkpoint 中保持 active 并继续被使用。

这些证据说明 v4 的支撑机制真实运行，其中一些信号与搜索前沿推进具有稳定关联。TraceAAD 的首要方法证据来自完整机制在公平协议下的训练、held-out、重复稳定性和 SOTA 表现；当前过程审计用于理解这套机制为什么能够工作、哪些环节仍在浪费预算，以及下一版应怎样收缩或加强。

当前最准确的阶段结论是：**轨迹搜索的实现形态成立，历史能够承载渐进改进与回退经验，轨迹价值能够把稀缺的全局突破集中到高价值区域；失败知识传承、趋势定义和种群资源分配仍有明确改进空间。**

本页综合三个冻结审计。读取时间为 2026-07-24 15:26–15:30（Asia/Shanghai）；当时 OBP、OP-ACO 的 6 个 run 已完成 1000 次预算，TSP、CVRP、KP 的 9 个 run 仍在运行。未完成 run 的数字都是过程快照。

|---|---|---|---|---|
| 历史被正确记录 | 已有支持 | checkpoint 中 node/edge/trajectory 与日志一致 | v4 具备审计“来时路”的基本载体 | 更早历史因 8 节点窗口被删除 |
| 匹配历史进入提示 | 已有支持 | 6,299 次 action-stage、12,582 次 code-stage 可重建调用未发现错轨迹或错锚点 | action 与实现阶段之间没有明显上下文断链 | 字符串出现不能证明模型使用 |
| LLM 利用历史决定下一步 | 部分支持 | 有利用退步边修订或换向后成功的 TSP/CVRP 案例；五个 task 也都出现原样重复失败 action | 历史能够形成有效边界，但当前表达还不能稳定阻止重复试错 | 将 action 与所依据的历史边、延续/修复/回退/换向关系显式化 |

## 3. 为什么一部分机制能够工作

### 3.1 轨迹价值更适合看“是否推进前沿”

高价值路线的 local-improve 比例反而较低，但 global-best yield 更高。弱父代更容易获得相对自身的小幅改善，强父代更难改善；一旦强路线成功，才更可能推进全局前沿。因此，直接改进率不能单独评价父代调度。v4 的质量信号目前最有力的证据，是它在五个 task 上都把稀缺的全局突破集中到了高价值区域。

这个结果支持 quality 的大方向，不足以证明 `0.6Q+0.4P` 的具体权重。当前趋势只看相邻边的正负，会把“从退步 endpoint 部分回弹”完整记成正趋势；实际从退步 endpoint 出发的 local-improve 为 27.4%–49.3%，超过路线历史最好的比例却只有 1.4%–9.0%。趋势可能奖励围绕旧最好点振荡的路线。

### 3.2 内部锚点实现了有实际价值的回退

内部最好锚点不是死代码。TSP 和 CVRP 中都出现了模型看到锚点后退步尝试，随后从强锚点重构或换向并取得明显改进的案例。内部锚点的意义不是提高普通 local-improve，而是避免让已经退步的 endpoint 成为唯一代码落点。

它也暴露了一个结构问题：action prompt 会展示锚点之后的失败边，新 child trajectory 却只保存锚点前缀和新边。图保存了失败事实，下一代搜索不一定再读取这些事实。轨迹作为严格路径与旁支失败经验之间还缺少明确的知识接口。

### 3.3 两个算子形成了粗粒度分工

五个 task 上，`trace_ideate` 都产生更大的 LOC 增量和更低的父子代码相似度，`trace_refine` 更接近局部修改。算子提示确实改变了生成分布。它们的收益具有明显 task 依赖：TSP 的 refine 稳定优于 ideate，CVRP 的 ideate 更强；OBP ideate 的评估成功率只有 84.1%，refine 为 97.8%；KP 两者在早期后都接近停滞。

因此，算子分工能够 work，均匀 1:1 调度缺少效率依据。语义边界也不是严格的：refine 会整体替换算法，ideate 会做局部追加，两个算子都会复制历史 action。后续信用应判断 action 与历史的关系及其结果，不能只按 operator 名称累计。

## 4. 当前最值得改进的地方

### 4.1 “完整历史”与实际处理不一致

v4 实际提供最多 7 条边的近期后缀。45.7%–73.1% 的选择已经达到该上限，早期来时路不再进入提示，而 prompt 仍称其为 complete history。当前实验真正检验的是“有界近期历史”。下一步需要在科学表述和实现之间作出明确选择：将主张收窄为近期历史，或为全程历史增加有界摘要。

### 4.2 历史可见不等于历史被利用

五个 task 都观察到了原样复制已经 plateau/regress action 的情况，保守计数至少 39 次。TSP 的一个案例把两条失败 action 原样返回，生成后仍分别 plateau/regress。另一方面，也存在同一思想换定义后转败为胜的案例。因此不能建立“失败 action 禁止重试”的硬规则，更合理的是要求重试说明与旧实现唯一的机制差异，并用实际结果核验。

### 4.3 声明思想与代码机制可能分离

OBP sample 92 要求奖励低 index 的旧 bin，生成代码实际奖励高 index，文字仍声称偏好旧 bin。程序分数改善只能证明整个实现更好，不能证明自然语言中的那条思想获得了正信用。轨迹边若只保存 action、idea 和 fitness，可能把结果归因给错误的机制。

### 4.4 新路线数量远大于可验证机会

每轮通常生成两条 child trajectory，但只选择一个父代；再加上周期性 `2M→M`，多数新路线还没有产生自己的子代就进入生存筛选。UCB 已经明显偏向零访问路线，仍只有约六分之一的新路线能在下次管理前获得一次扩展。这不是简单调大 UCB 就必然解决的问题，而是“分支生成率、父代选择率、管理周期”三者共同决定的资源结构。

### 4.5 种群机制缺少运行证据

现有日志只能证明池子被限制在 30–61 条轨迹，不能证明 diversity reserve 比普通 softmax 保留了更有价值的路线，也不能逐次核对 best-anchor replacement。没有 survivor ID、角色和管理时价值，继续讨论这些子机制的优劣会停留在代码意图。

## 5. 后续分析与实验顺序

### 阶段 A：先补可观测性，不改变搜索行为

在下一批 v4-compatible run 中增加：

- 每次选择前所有 active trajectory 的 `Q/P/V`、visit、UCB、概率和 selected 标记；
- `delta_parent`、`delta_path_best`、`delta_global_best`；
- 锚点类型以及内部回退会丢弃的 edge IDs；
- 每次管理的候选、keep/archive、`quality_elite/best_anchor/diversity/softmax` 角色；
- action 与历史关系、evidence edge、生成 idea、代码机制摘要及一致性状态；
- 评估失败类型，而不只记录失败计数。

这一阶段不改善算法分数，但能让评分、UCB、种群和思想信用首次具备完整审计条件。

### 阶段 B：围绕整体表现解释机制

继续完成 v4 的训练与 held-out 评估，先确定完整机制在各 task 上的最终质量、重复稳定性和 anytime search 表现。从现有工件冻结一组分层 anchor，覆盖：

- 强 endpoint；
- 已退步 endpoint；
- 内部最好锚点及其后续失败边；
- 连续改进路线；
- 长期 plateau 路线；
- 短/长程序和早/晚搜索阶段。

围绕这些状态检查 action 是否承接有效思想、是否重复已失败方向、action–code 是否一致，以及 `delta_parent`、`delta_path_best`、`delta_global_best` 和每单位 token/墙钟的有效进展。必要的局部 replay 与组件消融用于解释竞争机制，不作为评价完整 TraceAAD 方法是否成立的前置条件。

### 阶段 C：按因果链做最小在线消融

在核心历史价值得到支持后，依次验证：

1. 当前局部趋势、route-best-relative 趋势、无 trend；
2. `ucb_c=0` 与当前 UCB；
3. 已退步轨迹上的 endpoint/internal-best 随机化 A/B；
4. 当前失败后缀截断与有界 `tested_actions` 传承；
5. elite+softmax、加入 diversity reserve、加入 best-anchor；
6. uniform operator 与基于近期有效子代/route-best/global-best 信用的轻量调度。

每次只改变一个职责，固定模型、task、预算和其余搜索配置。评价同时报告 anytime AUC、达到质量阈值的样本数、route-best improvement、global-best update、谱系覆盖、重复失败率、程序复杂度和 held-out 质量。

### 阶段 D：再决定 v5 改什么

v5 不应一次吸收所有观察。优先保留已经有过程支持的部分：轨迹级选择、质量信号、内部强锚点、best route 可复用和两个粗粒度语义算子。优先修复失败边不能持续传承、局部回弹与路线进展混淆、action 与代码机制信用错配、管理决策不可观测等已观察断点。operator 自适应、历史压缩、全局搜索认识和复杂度整合等机制应围绕整体搜索表现逐项进入。

## 6. 轨迹定义与搜索视野

一条轨迹应定义为从起始程序到当前程序的严格祖先改进路径。它解释当前算法怎样形成，与当前修改具有最高的直接相关性，因此承担主要的局部指导作用。原始旁支不属于这条来时路，不应为了扩大信息量直接混入轨迹。

跨分叉得到的经验属于另一种视野：全局搜索认识。它从多条路线中凝练反复有效的思想、有条件成立的规律、常见失败和未充分探索的方向，为下一步提供整个搜索空间的高层地图。祖先轨迹回答“这个算法怎样走到这里”，全局搜索认识回答“整个搜索已经学到了什么”。

后续值得研究的重点因此从“给多少原始分叉”转为“怎样形成简洁、可靠、带适用条件的全局认识”。这使 TraceAAD 保持清晰的轨迹个体，同时获得接近人类研究者全局认知的更宽搜索视野。
