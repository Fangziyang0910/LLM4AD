# TraceAAD v4 上下文与轨迹案例审计

> 状态：2026-07-24 冻结过程证据，不承担当前方法设计。

## 1. 核心判断

本页检查 TraceAAD v4 的核心因果链中最靠近 LLM 的一段：

> 轨迹历史被正确写入提示 → 模型根据历史决定延续、修复、回退或换向 → action 被忠实实现为代码 → 新程序获得相应结果。

截至 2026-07-24 15:30（Asia/Shanghai）的冻结读取，现有证据支持以下判断。

1. **上下文装配机制正常工作。** 在 checkpoint 能完整重建的 6,299 次 action-stage 调用和 12,582 次 code-stage 调用中，所选轨迹的保留边、锚点代码和节点编号均正确出现，没有发现错轨迹、错锚点、乱序或 action/code 两阶段历史不一致。
2. **“完整历史”实际上是最多 8 个节点、7 条边的近期后缀。** 五个 task 中，45.7%–73.1% 的选择已经顶到 7 条边。更早的形成过程不再进入提示，因此当前实验检验的是“有界近期轨迹上下文”，不能直接表述成利用完整根到当前节点的历史。
3. **内部锚点能让模型在本次生成中看到锚点之后的失败尝试，但这些失败边不会持续传给新分支。** 五个 task 共观察到 1,837 个这种截断分支，其中 638 个新分支后来又被选为父代；后续提示只保留“锚点前缀 + 新边”，不再包含曾经指导该次分支的锚点后失败边。这是实现行为，不是偶发日志缺失。
4. **历史利用获得部分支持，同时存在明确失效。** TSP 和 CVRP 都有从内部最好锚点出发、看到后续退步后改换或重构方向并取得明显改进的案例；但五个 task 都出现了 action 原样复制提示中已经失败或停滞的 action。输出协议又禁止 action rationale，因此仅凭当前日志无法判断模型为何重试、是否理解失败原因。
5. **两个算子在代码变化幅度上可辨别，但语义职责没有严格成立。** `trace_ideate` 在五个 task 上都产生更大的代码增量和更低的父子代码行相似度，`trace_refine` 更像局部修改；与此同时，refine 会整体替换算法，ideate 也会做局部参数修改，甚至复制历史 action。
6. **action 到代码通常能看出实现对应关系，但仍有语义反转。** 例如 OBP sample 92 要求奖励低 index 的旧 bin，生成代码却把正奖励加给高 index，文字仍声称它偏好旧 bin。评估分数提升不能消除这一实现语义错误。
7. **长提示与后期低改进率共同出现，但不能据此断言历史被淹没。** 锚点代码几乎总比历史段长，最长 action prompt 达 61,875 字符；五个 task 的提示长度最高四分位直接改进率均低于最低四分位。提示长度同时与搜索阶段、父代质量、程序膨胀和任务天花板混杂，因果判断需要配对 replay。

因此，对 v4 最准确的阶段判定是：

- **历史记录与提示装配：已有支持；**
- **近期历史影响下一步行为：部分支持；**
- **失败边界能跨分支持续成为知识：当前机制不成立；**
- **完整方法价值：由最终 SOTA、held-out、重复稳定性和过程表现共同判断；本页负责解释上下文怎样参与其中。**

## 2. 数据范围、抽样与编码规则

### 2.1 数据范围

分析覆盖 `experiments/*/traceaad_v4/version4/` 下五个 task、每个三个重复：

- TSP Construct：`20260723_181743_tspc_v4_rep1~3`；
- CVRP-ACO：`20260723_204526_cvrp_v4_rep1~3`；
- Knapsack Construct：`20260723_204526_kp_v4_rep1~3`；
- Online Bin Packing：`20260723_204526_obp_v4_rep1~3`；
- OP-ACO：`20260723_204526_opaco_v4_rep1~3`。

TSP、CVRP 和 KP 在读取时仍是未满预算快照。为避免把日志末尾已写入、checkpoint 尚未保存的对象错误拼接到旧图状态，本页的轨迹结构统计只使用同时存在于 `checkpoints/latest.json`、`method_state.jsonl`、`method_events.jsonl` 和 `llm_calls.jsonl` 的记录。OBP 和 OP-ACO 已到 1000 次评估预算。当前计数是过程快照，不是最终实验结果。

字段来源固定为：checkpoint 提供 node/edge/trajectory 的最终可重建状态，`method_state.jsonl` 提供 iteration、selected trajectory、endpoint、anchor 和 operator，`llm_calls.jsonl` 提供两阶段 prompt/response/sample order，`method_events.jsonl` 提供 child、child trajectory、directed delta 和 outcome。下文给出的 run、iteration、sample、trajectory 和 node 可按这四类文件交叉复核。

### 2.2 两层取样

本页没有用少数成功故事替代总体统计。

第一层是全部 checkpoint-consistent 选择和父子边，用于核对：

- action-stage 与 code-stage 是否收到正确轨迹、锚点和边；
- 保留历史长度、内部锚点比例、上下文字符数；
- 内部锚点后的失败边是否进入子轨迹；
- 两个算子的 LOC 增量和父子代码行相似度；
- action 是否精确复制锚点后的既有尝试。

第二层是目的性案例审计。每个 task 至少选择一种明显改进、明显退步或停滞、内部锚点或端点延续现象；另选每个 task 的最长 action prompt 和内部锚点后精确重复失败 action 的案例。目的性案例用于解释机制怎样成功或失效，不用于估计总体发生率。

### 2.3 人工编码定义

action-stage 和 code-stage 分开判断：

| 编码项 | 判定口径 |
|---|---|
| 历史正确呈现 | 保留轨迹中的每条 edge action、operator、fitness 变化与 outcome 顺序一致；锚点节点和代码一致 |
| 明确利用历史 | 新 action 或代码对历史中某个成功/失败机制做了可辨别的延续、替换、修复或回退，且该信息不能只从锚点代码直接读出 |
| 与历史相容但无法归因 | 修改没有重复已知失败，但从当前代码和任务描述也足以独立提出 |
| 重复失败 | action 与锚点后某条 plateau/regress action 规范化文本完全相同；近义重试只作为案例，不计入精确重复率 |
| action–idea 一致 | `parsed_idea` 描述了 requested action 的主要机制 |
| idea–code 一致 | 代码中的计算方向、变量作用和选择方向实现了 idea，而不只是注释复述 |
| operator 一致 | ideate 引入可辨别的新主要机制；refine 保留已有主要思想并做聚焦修改 |

模型按 prompt 被要求只返回 action 行或完整代码，不得输出 rationale。因而“response 没有解释历史”是输出协议的结果；本页不把模型复述 `preserve`、`fix regression` 等词语自动编码为历史利用，只看实际修改和结果。

## 3. 上下文是否按设计呈现

### 3.1 action-stage 和 code-stage 的一致性

| Task | action-stage 核对数 | 缺失/错配 | code-stage 核对数 | 缺失/错配 |
|---|---:|---:|---:|---:|
| TSP | 1,210 | 0 | 2,417 | 0 |
| CVRP | 1,000 | 0 | 1,995 | 0 |
| KP | 1,162 | 0 | 2,319 | 0 |
| OBP | 1,470 | 0 | 2,938 | 0 |
| OP-ACO | 1,457 | 0 | 2,913 | 0 |

【观测事实】`context.py` 在 action-stage 写入任务、保留的有序 edge、每步 fitness/delta/outcome、锚点 idea 与完整代码、operator constraint 和函数契约。`prompt.py` 在 code-stage 再次写入同一历史、当前锚点代码、具体 requested action 和同一 operator constraint。全部可重建调用都与 checkpoint 中的轨迹和节点一致；内部锚点提示也都包含 `[selected anchor]` 标记。

【机制解释】v4 已经消除了“action 阶段看到历史，代码阶段只看到一句 action”的明显断链。后续观察到的 action 重复、实现偏差或失败，不能归因于历史根本没有进入某个阶段。

【证据不足】字符串和节点对齐只能证明信息被提供，不能证明模型注意、理解或使用了这些信息。

### 3.2 “完整历史”是有界近期后缀

| Task | 可重建选择数 | 7-edge 上限占比 | 历史 edge 均值 | 内部锚点占比 |
|---|---:|---:|---:|---:|
| TSP | 1,210 | 65.7% | 5.87 | 约 23.2% |
| CVRP | 1,000 | 71.4% | 6.10 | 约 17.0% |
| KP | 1,162 | 45.7% | 4.99 | 约 2.8% |
| OBP | 1,470 | 66.5% | 6.03 | 17.7% |
| OP-ACO | 1,457 | 73.1% | 6.16 | 16.7% |

【观测事实】`TrajectoryMemory.branch_from` 把轨迹限制为 8 个节点，因此提示最多出现 7 条边。发生溢出时，早期节点和边从 trajectory 对象中删除；`trajectory_history` 只能渲染剩余后缀。提示仍写着 `Use the complete history`，也不会告诉模型 Step 1 之前已有前缀。

【机制解释】当前 prompt 里的 Step 1 经常不是算法的真实起点。模型可能把一个中途状态误读为整条路线的开端，也无法知道当前代码中的某个旧机制曾在哪一步加入、当时带来什么结果。这削弱了“完整来时路”这一科学表述与实际实验处理之间的一致性。

【证据不足】早期历史未进入提示不等于它一定有用。需要比较 7-edge 后缀、压缩的全程摘要和真正全程记录，才能判断应扩大窗口还是压缩历史。

## 4. 内部锚点：本次可见与持续传承是两件事

### 4.1 全量结构计数

| Task | 从内部锚点产生、且锚点后存在旧边的子分支 | 子分支后来再次被选中 | 后续仍含旧的锚点后边 |
|---|---:|---:|---:|
| TSP | 524 | 180 | 0 |
| CVRP | 320 | 114 | 0 |
| KP | 61 | 22 | 0 |
| OBP | 472 | 172 | 0 |
| OP-ACO | 460 | 150 | 0 |

【观测事实】选择内部最好节点时，本次 action/code prompt 会展示该锚点之后通向旧 endpoint 的 plateau/regress 尝试。生成 child 后，`branch_from` 构造的是：

```text
旧轨迹截至 anchor 的前缀 + 当前新 edge + child
```

旧轨迹中 anchor 之后的边不属于新 child trajectory。上表 1,837 个子分支全部如此；其中 638 个后来确实又被选为父代，后续 prompt 均不再含先前被截断的失败边。

【机制解释】内部锚点实现了“看着失败记录再重走一次”，却没有实现“把失败边界作为路线知识持续带走”。如果新分支后来再次接近同一问题，它只能依赖代码或新边间接保留经验，无法直接看到那个失败记录。这是轨迹知识传承的结构断点。

【证据不足】旧失败边是否应该永久附着在新分支仍需控制信息量。完整复制所有旁支会迅速膨胀上下文；更合适的对象可能是锚点的已测试 action/outcome 摘要，而不是把旧 endpoint 继续当作新路线组成部分。

### 4.2 成功案例：TSP 对失败方向做了实质性重构

证据位置：

- run：`experiments/tsp_construct/traceaad_v4/version4/20260723_181743_tspc_v4_rep1/`
- iteration 4，action/code sample 39；
- selected trajectory 34，anchor `p15`，旧 endpoint `p34`；
- 新 child `p36`，child trajectory 36，operator=`trace_ideate`。

【观测事实】旧边 `p15→p34` 尝试以 dynamic regret 替代 centrality，结果为 regress。内部锚点 prompt 展示了这条失败边。本次 action 没有简单回避 regret，而是把定义改成“其他未访问节点到 candidate 的平均未来到达成本减去当前到达成本”；代码确实实现了这个新定义。新边 `p15→p36` 的 directed delta 为 `+0.225959`，随后 trajectory 36 在 iteration 11、14、54 等再次被选中。

【关联判断】同一个 anchor 上，regret 思想的第一种实现退步，看到该记录后的第二种定义取得改进。这个案例符合“失败历史帮助模型修订同一思想，而非简单删除整个方向”的预期。

【机制解释】这是 v4 核心思想成立的一个强案例：退步边可以成为重新定义 action 的边界，历史的价值不只来自成功路径。

【证据边界】action 和 `Idea` 没有明确说明“前一种 regret 为什么失败、新定义修复了什么”，因为输出协议禁止 rationale。这个案例支持完整 TraceAAD 中的回退修订机制能够工作；若后续需要解释具体信息来源，可再做局部对照。

【传承断点】trajectory 36 后续被选中时，prompt 只包含 `p15→p36`，不再包含 `p15→p34 regress`。本次生成看到了失败边，后续路线没有继承这条边界。

### 4.3 成功案例：CVRP 从容量惩罚退步切换到路线连续性

证据位置：

- run：`experiments/cvrp_aco/traceaad_v4/version4/20260723_204526_cvrp_v4_rep1/`
- iteration 10，sample 52；
- selected trajectory 34，anchor `p32`，旧 endpoint `p34`；
- 新 child `p48`，child trajectory 48，operator=`trace_ideate`。

【观测事实】旧的 `p32→p34` 用 distance-scaled capacity penalty，结果 regress。新 action 改为 depot radial distance difference 构成的 route-continuity term，代码实现了相应径向连续性惩罚，directed delta 为 `+1.031599`。trajectory 48 后来在 iteration 13、15、18 等继续被选。

【关联判断】模型没有重复旧容量惩罚，而是从同一 anchor 换到几何连续性，直接结果明显改善。这符合内部锚点支持回退换向的设计。

【证据不足】新 action 没有明确引用旧失败，换向也可能来自 operator 的“genuinely new idea”约束。它支持机制可行，却不能证明失败历史是必要条件。

### 4.4 停滞案例：KP 长失败后缀没有产生可辨别修复

证据位置：

- run：`experiments/knapsack_construct/traceaad_v4/version4/20260723_204526_kp_v4_rep1/`
- iteration 34，sample 97；
- selected trajectory 90，anchor `p40`，旧 endpoint `p90`；
- 新 child `p95`，child trajectory 95，operator=`trace_refine`。

【观测事实】锚点后提示包含一次 dynamic DP threshold plateau 和一次 residual gap penalty regress。新 action 再次修改 DP threshold，要求用 `sqrt(remainder) * min(n_items, 100)` 决定是否执行 DP；代码按要求实现，结果仍为 plateau。trajectory 95 后来在 iteration 37、70、81 等被选，但旧 plateau/regress 两条边已经不在其历史中。

【机制解释】在接近任务天花板的 KP 上，提示列出多个失败 outcome 并没有自动形成“停止微调同一 DP 家族”的决策。失败历史的结构化呈现仍不足以保证换向或停止。

【证据不足】plateau 可能来自训练 fitness 已饱和，而不是模型没有利用历史。应同时查看 held-out 行为差异，并加入“等分时停止叠加/触发整合”的决策规则。

## 5. 已知失败是否真的改变下一步

### 5.1 精确重复计数

只统计内部锚点场景，并把新 action 与 prompt 中锚点之后旧边的 action 做去空白、忽略大小写的全文比较：

| Task | 可比较新子边 | 精确重复旧 action | 其中旧 outcome 非 improve |
|---|---:|---:|---:|
| TSP | 524 | 11（2.1%） | 11 |
| CVRP | 319 | 6（1.9%） | 5 |
| KP | 61 | 5（8.2%） | 5 |
| OBP | 472 | 7（1.5%） | 7 |
| OP-ACO | 460 | 16（3.5%） | 11 |

【观测事实】五个 task 都存在原样重复；精确文本只是保守下界，近义改写没有计入。多数精确重复对象是已经 plateau 或 regress 的边。

【机制解释】prompt 中的 outcome 标签没有形成可靠的“不要无修改重复失败 action”约束。尤其 `trace_refine` 容易把历史中的一条具体修改直接当作新 action 返回。

【证据不足】重复 action 不必然等于重复实现。TSP sample 39 表明同一思想家族换定义后可以转败为胜。合理约束应要求重试时说明相对旧 action 的机制差异，而非设置绝对去重。

### 5.2 五个可复核的原样重复案例

| Task / run | Iteration / sample | Anchor → old endpoint | 被原样复制的旧结果 | 新结果 |
|---|---|---|---|---|
| TSP `tspc_v4_rep3` | 437 / 899–900 | `p623→p789` | vectorized local-cycle plateau；global MST regress | plateau；regress |
| CVRP `cvrp_v4_rep3` | 81 / 193 | `p131→p147` | dynamic capacity scaling regress | regress |
| KP `kp_v4_rep3` | 341 / 694–695 | `p50→p644` | 两个 tie-break action 均 plateau | plateau；plateau |
| OBP `obp_v4_rep3` | 296 / 617 | `p212→p546` | bin-closure incentive regress | regress |
| OP-ACO `opaco_v4_rep3` | 105 / 240 | `p210→p216` | O(n²) accessibility approximation regress | regress |

TSP iteration 437 是最完整的失败示例。action-stage 返回的两行分别与提示中锚点后两条旧 action 完全相同。sample 900 的 code-stage `Idea` 写了“re-introduce ... but fix the regression”，代码确实改了归一化和组合方式，但新结果仍 regress。这里可以分别得到三个事实：

1. action-stage 没有产生可观察的新修改；
2. code-stage 尝试对同一 action 做不同实现；
3. 自述“fix”没有被评估结果支持。

这也说明不能只读 response 文本判断历史是否 work，必须把 action、代码差异和评估结果连起来。

## 6. `trace_ideate` 与 `trace_refine` 是否形成可辨别行为

父子代码相似度使用非空代码行的 `SequenceMatcher` ratio，只作为结构改动代理，不解释为真正语义距离。

| Task | Ideate：LOC 增量中位数 / 行相似度中位数 | Refine：LOC 增量中位数 / 行相似度中位数 |
|---|---:|---:|
| TSP | +19 / 0.764 | +3 / 0.857 |
| CVRP | +23 / 0.867 | +4 / 0.892 |
| KP | +20 / 0.731 | +8 / 0.857 |
| OBP | +12 / 0.804 | +2 / 0.912 |
| OP-ACO | +10 / 0.772 | +3 / 0.869 |

【观测事实】五个 task 的方向完全一致：ideate 改动更大、与父代码更不相似；refine 改动更小、更接近父代码。对应的 outcome 则有 task 依赖：TSP 的 refine 改进率明显更高，CVRP 的 ideate 更高，KP 两者都接近停滞，OBP 和 OP-ACO 的 refine 略高。

【机制解释】两个 operator constraint 不是纯标签，至少对生成改动幅度形成了稳定区分。ideate 负责扩张、refine 负责局部利用的粗粒度分工能够 work。

【反例】语义边界并不严格：

- OBP rep1 iteration 23、sample 77 的 `trace_refine` 从 `p19` 出发，action 要求整体替换成标准 Best Fit，directed delta `+90.4`。这是非常有效的回退/替换，却不符合“保留一个已有价值思想并聚焦细化”的字面定义。
- OBP rep1 iteration 30、sample 92 的 `trace_ideate` 只是在现有 priority 上增加 bin-age bonus，更接近 refine；下节还显示其代码方向与 action 相反。
- 精确复制历史 action 的案例同时出现在两个 operator 中，说明“genuinely new”与“focused refinement”都不是硬约束。

【机制解释】成功的 Best Fit 回退提示一个设计张力：从失败复杂机制回到简单可靠基线可能非常有价值，但 v4 没有独立的回退/整合语义，只能借 ideate 或 refine 偶然完成。比起只加强算子措辞，更值得把“延续、修复、回退、换向”编码为 action 与历史证据的关系。

【证据不足】代码行相似度不能判断算法思想是否新。需要对 action–history 关系做人工标签或结构化输出，再验证不同关系的收益。

## 7. action、Idea 与代码是否一致

### 7.1 正向案例

抽查的成功案例中，主要 action 通常能在 `parsed_idea` 和代码中找到对应实现：

- TSP rep1 sample 39：action 定义 average-future-cost regret；Idea 给出相同公式，代码计算其他未访问节点到 candidate 的平均距离并减去当前距离。
- CVRP rep1 sample 52：action 要求 radial route continuity；Idea 和代码使用节点到 depot 距离差构造连续性惩罚。
- OP-ACO rep1 sample 55：action 要求 residual-budget effective reachability；代码按从 candidate 可达的高 prize 邻域计算潜力，directed delta `+0.226`。
- KP rep1 sample 97：action 要求动态 DP threshold；代码确实根据 remainder 和 item 数决定执行 DP 或退化为 greedy，虽然结果 plateau。

【观测事实】这些案例说明 action-stage 与 code-stage 的双重历史传递没有妨碍模型完成具体实现；“action 已提出但代码完全忽略”不是普遍现象。

### 7.2 明确语义反转：OBP bin age

证据位置：

- run：`experiments/online_bin_packing/traceaad_v4/version4/20260723_204526_obp_v4_rep1/`
- iteration 30，sample 92，trajectory 76，anchor=endpoint=`p76`；
- child `p82`，operator=`trace_ideate`，directed delta=`+5.6`。

【观测事实】action 要求“增加对 older bins（lower index）的奖励”。Idea 写“positive value proportional to bin index”却仍声称偏好 older bins；代码为：

```python
indices = np.arange(len(bins))
aging_bonus = indices * 1e-4
priority_scores = base_priority - penalty + aging_bonus
```

在 priority 越大越优先的契约下，这段代码奖励的是更高 index，而不是更低 index。action、自然语言结论与代码的实际方向相反。

【机制解释】LLM 可以生成语法正确、分数改善的程序，同时误解或反转自己描述的机制。fitness 改善只能证明整个程序在训练评估上更好，不能证明声称的历史思想是改进原因。对轨迹做思想信用时，若直接把 `Idea` 当成代码真实机制，会产生错误 credit。

【值得改进】对可结构验证的方向性陈述增加轻量 consistency 检查，例如“更大/更小 index”“奖励/惩罚”“maximize/minimize”的符号核对；无法自动检查的 action 至少在分析数据中区分“声明思想”和“代码实现机制”。

## 8. 长上下文是否淹没历史

### 8.1 上下文规模

| Task | Action prompt 中位 / P90 / 最大字符数 | 历史段中位 | 锚点代码中位 | 锚点代码长于历史 |
|---|---:|---:|---:|---:|
| TSP | 15,428 / 21,807 / 32,266 | 3,229 | 10,339 | 100% |
| CVRP | 19,265 / 27,702 / 40,902 | 3,257 | 13,544 | 100% |
| KP | 11,340 / 30,690 / 61,875 | 2,457 | 6,966 | 99.6% |
| OBP | 12,540 / 18,706 / 29,355 | 3,032 | 7,846 | 98.8% |
| OP-ACO | 15,462 / 21,689 / 29,570 | 3,214 | 9,806 | 100% |

code-stage 还要求输出完整函数，因此 response 中位字符数为 8,843–14,273；action-stage response 中位仅约 604–637 字符。

【观测事实】历史段的绝对大小受 7-edge 上限控制，程序代码却可以持续增长。几乎所有 action prompt 中，锚点代码都比有序历史更长。KP 最长 prompt 的 anchor 是 endpoint `p611`，两个 action 都产生 plateau。

### 8.2 提示长度与直接结果

按每个 task 的 action prompt 字符数将父子边分为四等份：

| Task | 最短四分位：prompt 中位 / 改进率 | 最长四分位：prompt 中位 / 改进率 |
|---|---:|---:|
| TSP | 8,357 / 17.2% | 20,641 / 12.4% |
| CVRP | 10,453 / 23.9% | 27,185 / 10.2% |
| KP | 6,323 / 9.2% | 27,383 / 0.4% |
| OBP | 7,552 / 12.0% | 18,337 / 9.1% |
| OP-ACO | 10,672 / 15.3% | 21,248 / 6.3% |

【观测事实】除 OBP 的降幅较小外，长 prompt 区间的直接改进率明显更低；KP 同时出现大量 plateau。最长提示仍能正常返回可解析 action，TSP 的最长 prompt 两个候选中还有一个 improve，因此没有观察到简单的格式崩溃或必然失效。

每个 task 的最长 action prompt 案例如下：

| Task / run | Iteration / sample | Operator / anchor | 字符数 | 有效子代结果 |
|---|---|---|---:|---|
| TSP `tspc_v4_rep2` | 310 / 641 | refine / endpoint `p610` | 32,266 | regress；improve |
| CVRP `cvrp_v4_rep2` | 291 / 613 | ideate / endpoint `p573` | 40,902 | regress；regress |
| KP `kp_v4_rep1` | 318 / 650 | refine / endpoint `p611` | 61,875 | plateau；plateau |
| OBP `obp_v4_rep3` | 317 / 657 | ideate / endpoint `p575` | 29,355 | regress；另一 action 未形成有效子代 |
| OP-ACO `opaco_v4_rep3` | 271 / 572 | ideate / endpoint `p451` | 29,570 | regress；regress |

【机制解释】程序膨胀使“当前代码”逐步占据远多于“来时路”的上下文，可能降低有限注意力下历史 outcome 的显著性。精确重复既有失败 action 与这一风险方向一致。

【证据不足】不能从该表推出“长上下文导致低改进”。搜索后期同时具有更强父代、更少剩余改进空间、更深轨迹、更长程序和更多同质 action；这些变量没有被分开。字符数也不是模型 tokenizer 的精确 token 数。

【待验证】固定同一个 anchor、operator 和模型条件，比较：

1. 当前祖先轨迹；
2. 祖先轨迹 + 结构化全局搜索认识；
3. 祖先轨迹的全程压缩摘要；
4. 简化后的等质 anchor + 同一知识上下文。

这种配对 replay 用于选择更有效的知识表达，并判断长代码是否淹没历史。

## 9. 面向 v5 的最小改进建议

以下建议直接来自本页观察，不把未经验证的复杂机制提前写成结论。

### 9.1 把 action 变成“与历史的关系”，而不只是修改文本

建议 action-stage 返回轻量结构：

```text
relation: continue | repair | rollback | redirect
evidence_edges: [e12, e15]
change: <本次具体修改>
novel_difference: <若重试旧方向，说明与旧 action 的唯一关键差异>
```

这样可以直接检查：

- refine 保留的是哪条已有价值边；
- ideate 相对历史新在哪里；
- repair 为什么不是原样重复失败；
- rollback 回到哪个锚点、放弃了哪些机制。

它同时改善可观测性：目前“不输出 rationale”的协议让核心历史利用假设只能通过结果间接猜测。

### 9.2 让失败边界附着于锚点，而不必复制整条旧旁支

内部锚点后的旧边不应强行并入新 trajectory 路径，否则会破坏单父代路径语义。更小的改动是为锚点维护有界的 `tested_actions` 摘要：

```text
anchor p15 tested branches:
- dynamic regret v1: regress, key definition=...
- centrality refinement: plateau, key definition=...
```

新 child trajectory 仍是严格路径，但从该 anchor 分支时能持续看到已经测试的边界。摘要应有容量上限，并通过消融比较“无旁支记忆 / 只保留失败 / 失败与成功都保留”。

### 9.3 区分声明思想与实际代码机制

轨迹边当前保存的是 action 文本和结果。至少增加：

- requested action；
- generated idea；
- 可提取的代码机制摘要；
- action–code consistency 状态；
- 若不一致，信用归给实际代码行为而不是声明。

第一版无需额外 LLM judge，可先做可判定的符号、方向、函数契约和关键变量检查，并保留人工审计样本。

### 9.4 将“完整历史”改成准确可证伪的处理

有两个可选方向：

- 科学主张明确收窄为“有界近期轨迹历史”，把 7-edge 窗口作为可比较参数；
- 保留全程事实，但把早期边压缩成阶段摘要，近期 7 条边保留原文。

当前 prompt 把截断后缀称为 complete history，会让论文主张、实现和实验处理发生不必要的错位。

## 10. 后续实验优先级

| 优先级 | 实验 | 首要回答 |
|---|---|---|
| P0 | 祖先轨迹 + 全局搜索认识 | 更宽的高层视野是否减少跨路线重复并改善搜索方向 |
| P0 | 内部锚点：当前截断 vs 有界 tested-actions 传承 | 失败边持续传承是否减少重复失败 |
| P1 | 自由 action vs relation+evidence 结构化 action | operator/history 关系是否更可观察、重复率是否下降 |
| P1 | 7-edge 原文 vs 全程压缩摘要 | 早期来时路是否仍有增益 |
| P1 | 代码原样 anchor vs 质量近同的紧凑 anchor | 长代码是否淹没历史或诱导叠加 |
| P2 | action–code consistency 检查开/关 | 语义反转检查是否改善可信度和 held-out 表现 |

最优先的问题是怎样在保持祖先轨迹清晰性的同时，为模型提供整个搜索已经形成的高层认识。原始分叉不直接进入轨迹；跨路线经验先经过归纳，再以全局搜索认识扩大下一步决策的视野。
