# 自动算法设计与 TraceAAD：核心研究认识

> **核心判断**
>
> 从第一性原理看，本项目研究的并不只是“基于轨迹的自动算法设计”，也不只是“改进一种 LLM 进化算法”。更准确地说，本项目研究的是：
>
> **在真实 evaluator 调用次数有限的条件下，如何利用搜索过程中已经产生的证据，控制 LLM 在程序空间中的后续生成，使有限次算法设计实验产生尽可能好的最终算法。**
>
> 因此，**表层优化对象是算法程序，真正的科学研究对象是“产生算法的搜索过程”本身。**
>
> 最准确的学术定位是：
> **有限评价预算下的 LLM 驱动序贯算法设计（Budgeted Sequential Algorithm Design）：研究搜索历史应如何表示为状态证据，并分别用于控制“下一次做什么实验”和“这次实验怎样生成候选”。**
>
> TraceAAD 是对这个大问题提出的一组具体假设：**算法的形成轨迹是一类关键的局部搜索状态；不同搜索行为需要不同的轨迹条件化生成方式。**
>
> 最本质的一句话：
>
> $$\boxed{\textbf{怎样让每一次昂贵的 LLM 算法实验更值得做。}}$$

本文沉淀本项目的统一科研认识与第一性原理分析。近期机制见 [V10.5 完整机制设计](../methods/TraceAAD-V10.5完整机制设计.md)；历史演进与尝试见 [机制尝试](TraceAAD机制尝试.md)；预算分配沿价值对象演化的经验见 [预算分配经验](预算分配经验.md)；生成端沿决策相关信息提炼的经验见 [生成上下文经验](生成上下文经验.md)；行为探针校正见 [BehaveSim 行为度量校正](../experiments/机制实验/2026-08-26-BehaveSim行为度量校正/结果.md)；全局导航见 [科研文档导航](../README.md)。

## 1. 剥离机制外壳：问题的极简本质

假设我们拥有：

1. 一个固定的预训练大语言模型 $\phi$；
2. 一个待设计的算法任务 $\mathcal{T}_{\mathrm{AD}}$；
3. 一个客观、可执行的验证环境（evaluator）$\mathcal{E}$；
4. 一个由可执行程序构成的候选空间 $\mathcal{R}$；
5. 最多只能评价 $B$ 个候选程序的严格真实预算约束。

则整个系统的优化目标可极简表述为：

$$\max \; \mathbb{E}\left[\text{BestQuality after } B \text{ evaluations}\right]$$

即：

> **我只有 $B$ 次真实实验机会，下一次实验到底应该做什么，才能最大化最终找到好算法的概率？**

这表明，本项目从根本上**不是**普通的“单次 LLM 代码生成”（one-shot code generation），也**不是**无预算约束的启发式发散，而是一个严格的**序贯实验决策问题（Budgeted Sequential Experimental Decision Problem）**。

## 2. 系统的数学压缩：四步闭环

设第 $t$ 步之前所有搜索历史为：

$$H_t$$

$H_t$ 包含累积的候选程序、fitness、父子关系、Idea 意图、修改方式、成功与失败记录、形成的 trajectory/orbit 以及历史 operator 的表现。每一步搜索本质上完成四件事：

### 第一步：决定下一次“做什么实验”（Search Action）

$$a_t \sim \mu(a \mid H_t)$$

其中动作包含三元组：

$$a_t = (n_t, o_t, r_t)$$

- $n_t$：从哪个已有算法节点出发；
- $o_t$：执行哪种设计行为（Refine、Pivot 还是 Fuse）；
- $r_t$：若需要跨谱系借鉴，选择哪个 donor/reference 节点。

这就是**计算/预算分配问题**。

**关键认识**：节点（node）本身不是正确的价值单位，因为“这个节点是否有价值”根本上取决于**接下来准备对它做什么**。真正合理的价值概念是动作条件化的：

$$Q(n, o \mid H_t)$$

而非简单的无条件单节点价值 $Q(n)$。

### 第二步：决定给 LLM 看什么（Context Construction）

$$C_t = g(H_t, a_t)$$

映射 $g$ 即上下文构造机制。对于 Refine，上下文需要呈现局部 orbit 以支持渐进修正；对于 Pivot，上下文需要指明应跳出的机制模式；对于 Fuse，上下文需要呈现互补机制。

**关键认识**：**历史存在，并不意味着历史有用。只有进入 prompt 并改变生成分布的信息，才真正参与了搜索。** 搜索状态（search state）的边界不是孤立存储在内存中的 population，而是“所有能够进入 prompt 并系统性影响后续生成分布的信息”。

### 第三步：LLM 根据条件产生候选（Conditioned Proposal）

$$x_t \sim K_\phi(x \mid C_t, o_t)$$

**这是理解本研究的最关键公式。**

LLM 并不是直接求解算法空间的优化器（optimizer），其本质角色是：

> **一个高度复杂、由上下文与指令联合控制的候选生成核（proposal kernel）。**

同一个模型 $\phi$，给定不同的 seed、trajectory、operator、reference 和 instruction，诱导出的候选程序分布完全不同。我们关心的不是主观上的“Prompt 好不好看”，而是：

$$P(\text{生成一个有价值的算法} \mid C_t, o_t)$$

能否被系统性提高。

分配策略 $\mu$ 决定机会给哪里，生成核 $K_\phi$ 决定获得机会后能产生怎样的候选。二者紧密耦合，缺一不可：一个好的分配无法拯救坍缩的生成器，一个优质的生成器在错误的分配下也只会空耗昂贵的预算。

### 第四步：购买一次真实反馈（Evaluation & Update）

$$y_t = \mathcal{E}(x_t)$$

更新搜索历史：

$$H_{t+1} = U(H_t, a_t, x_t, y_t)$$

随后进入第 $t+1$ 轮循环。

### 统一抽象架构

整个 TraceAAD 的底层机制闭环可以凝练为：

$$\boxed{H_t \overset{\mu}{\longrightarrow} a_t \overset{g}{\longrightarrow} C_t \overset{K_\phi}{\longrightarrow} x_t \overset{\mathcal{E}}{\longrightarrow} y_t \longrightarrow H_{t+1}}$$

## 3. 两个解耦的核心科学问题

在有限预算的序贯搜索中，所有机制演进最终收敛为两个正交但相互作用的科学问题：

### A. Search Control：下一次实验做什么？

$$\mu(a_t \mid H_t)$$

即：在有限 evaluator budget 下，下一次应该从哪个已有算法出发，用什么类型的搜索行为继续？

**核心负面认识**：
> **当前质量不是潜力；历史趋势不是潜力；子树最好成绩不是潜力；“没试过”也不等于“有价值”。**

过去版本（V2–V10）尝试过的大量人工代理指标（slope、momentum、credit、delayed gain、UCB、$G_1/G_2/G_4$ 等），本质上都是在没有充足反事实（counterfactual）数据时强行捏造的“潜力分数”。历史 trajectory 应作为证据（evidence）保留和呈现，而不是强行压缩为一个虚幻的标量潜力。

### B. Generation Control：决定以后，怎样让 LLM 做好这一次？

$$K_\phi(x \mid C_t, o_t)$$

即：给定具体的搜索决策后，怎样组织上下文与指令，使 LLM 的生成分布向高价值区域倾斜？

**核心学术洞见**：

$$\boxed{K_\phi(x \mid C, \text{Refine}) \neq K_\phi(x \mid C, \text{Pivot}) \neq K_\phi(x \mid C, \text{Fuse})}$$

不同的搜索行为不仅 instruction 不同，**所需要的 evidence 结构本身也必须不同**：
- **Refine**：依赖当前局部 orbit，判断是继续深入、修正局部缺陷还是微调策略；
- **Pivot**：必须理解来时路以便“有意识地摆脱既有机理假设”，避免换向退化为另一次微调；
- **Fuse**：核心在于机理互补性（mechanism complementarity），需要理解两个 parent 各自的机制特征，而非简单拼接代码片段。

因此，这远远超越了普通的提示词调优（prompt engineering），它是严格的**算子条件化生成分布设计（Operator-Conditioned Proposal Distribution Design）**。

## 4. Trajectory 的本质：局部设计实验的状态表示

**Trajectory 不是本研究的最终目的，而是对过去局部设计实验的一种状态表示。**

给定一条演化链路：

$$(x_i, o_i, \Delta_i) \longrightarrow x_{i+1}$$

它显式记录了：
1. 当时试图改变什么（意图与算子 $o_i$）；
2. 实际代码做出了什么修改（$\Delta_i$）；
3. 在哪个具体算法基底上修改（$x_i$）；
4. 真实验证环境反馈了什么好坏结果（evaluator feedback）。

单纯将历史算法罗列给 LLM，只是静态的种群（population）；而 Trajectory 额外注入了因果演化的维度——**算法是怎样一步步形成的**。它提供了一种局部的干预/效应证据（intervention/effect evidence）。

**固定锚点实验的硬支撑**：
在相同 anchor 上对比“仅有代码（code-only）”与“包含父代路径（parent-path）”，四任务上的配对差方向全部为正，72 个 anchor 中 58 个更好；其核心收益并非每一步带来神奇的跳跃，而是**显著降低了灾难性偏离，减少无意义的代码重构与策略倒退**。

> **Trajectory 的第一价值在于约束 proposal distribution，使 LLM 清晰感知当前设计的来龙去脉，从而在合理的搜索边界内展开探索。**

## 5. TraceAAD 的两层核心假设

TraceAAD 绝非笼统的“用轨迹改进进化”，而是建立在两层精确的科学假设之上：

### 假设 1：状态表示假设（State Representation Hypothesis）
> **算法的局部形成轨迹包含了对下一步算法设计至关重要的状态信息，单纯依赖当前算法代码与其单点 fitness 无法充分表示当前搜索状态。**

即局部轨迹所构成的扩展状态 $H_t^{\mathrm{orbit}}$ 相比纯静态的 $\{x_t, f(x_t)\}$，能对后续设计实验提供显著的额外预测性与约束信息。

### 假设 2：动作条件化生成假设（Action-Conditional Generation Hypothesis）
> **轨迹的价值并非全局静态不变，而是强依赖于下一步所执行的设计行为。**

$$I(H^{\mathrm{orbit}}; x_{t+1}^{\mathrm{good}} \mid o_t)$$

会随着 operator 产生系统性变化。轨迹证据必须根据算子类型进行定向投影和剪裁。

## 6. 预算认知的演进：从复杂 Heuristic 转向可辨识性与证据

在长期的版本迭代中，本项目经历了一次关键的科研范式收敛：

- **早期误区**：试图在缺乏反事实观测的情况下，显式构造一个潜变量——“节点/路线的未来潜力”，引入了岛模型、credit assignment、subtree UCT、delayed gain 等极度复杂的启发式控制器。
- **理论困境**：想要在线精确估计 $Q(n, o \mid H_t) = \mathbb{E}[\text{marginal gain} \mid n, o, H_t]$，但在有限的序贯搜索中，对节点 $n$ 执行了 Refine 就无法同时知道执行 Pivot 或 Fuse 的收益，反事实数据严重缺失。
- **范式转变**：**从“设计越来越复杂的 heuristic value function”，转向“首先审视该 value 是否具备可辨识性、是否有真实证据支持”。**

在尚未获得足够反事实配对数据前，强行构造复杂的在线控制器只会导致变量混杂和假性收敛。将轨迹和历史作为证据直接服务于生成，是更为可靠的第一性原理选择。

## 7. 机制设计的阶段性逻辑：机理辨识优先

在当前阶段（如 V10.5），系统采用了明确的算子固定比例与分立的选父机制：

$$P(\text{Refine}) = 0.50, \quad P(\text{Pivot}) = 0.15, \quad P(\text{Fuse}) = 0.35$$

- Refine 与 Pivot 从已验证的高质量活跃节点出发，分别承担同谱系深挖与跳出局部极值；
- Fuse 定向连接不同谱系，寻求机制层面的互补。

从工程表面上看，固定概率似乎不如自适应控制器“高级”；但从严谨的科研角度，这是极为必要的**机理辨识（Mechanism Identification）阶段**：

$$\boxed{\text{上下文构建} + \text{算子语义} + \text{形成轨迹} \longrightarrow \text{生成分布质量}}$$

如果在此阶段频繁扰动动作分配策略 $\mu_t$，整个搜索过程将沦为多变量混合系统，根本无法解耦性能增益究竟来自 prompt、trajectory、operator 比例还是 allocation 策略。先在固定的宏观框架下彻底摸清生成端机理，才能为后续学习或自适应调度奠定坚实的因果证据。

## 8. 学术谱系与领域定位

TraceAAD 横跨多个计算学科，其精确的理论母概念是：

> **算法程序空间上的有限预算序贯实验设计（Budgeted Sequential Experimental Design over Algorithm Space）**

其与经典领域的异同与边界如下：

| 领域 | 承袭与关联 | 本质差异 / 局限 |
| :--- | :--- | :--- |
| **Evolutionary Computation (EA)** | 借用 population、parent selection、variation、lineage 等演化骨架 | 经典变异/交叉算子是无语义的随机扰动；此处 variation 是高语义、具推理能力的 LLM 条件生成 |
| **Genetic Programming (GP)** | 搜索对象同为符号化可执行程序 | GP 通常基于 AST 语法树变异，缺乏高维上下文语义先验与自然语言设计意图的交互 |
| **Multi-Armed Bandit (MAB)** | 对应有限预算下不同节点/算子的 exploration–exploitation 取舍 | 传统 Bandit 假设臂的奖励分布固定或缓慢漂移；此处的每个“臂”是一次高维开放代码修改，状态转移高度非平稳 |
| **Bayesian Optimization (BO)** | 面对昂贵黑盒评价的序贯决策哲学一致 | 程序空间极度离散、高维且非欧氏，传统高斯过程难以直接构建可靠的全局代理模型（surrogate） |
| **Sequential Experimental Design** | **理论抽象上最吻合**：以最小实验成本最大化最终期望收获 | 实验候选的生成不是数值插值，而是由自然语言与代码条件化的 LLM 生成核驱动 |
| **In-context Learning (ICL)** | 轨迹与上下文让固定权重的模型在搜索中展现动态在线适应 | 并非泛泛的few-shot prompt，而是将演化干预历史结构化为定向推理链条 |
| **Prompt Engineering** | 具体的上下文实现载体 | 仅代表实现手段，不足以支撑起“搜索状态表示”与“序贯实验决策”的理论体系 |
| **Reinforcement Learning (RL)** | 整体流程可严格形式化为序贯马尔可夫决策过程 | 当前阶段未在大规模策略网络上更新权重，属于启发式驱动的序贯搜索，不应硬性贴上 RL 标签 |

## 9. 二层优化系统视角：搜索过程才是评价对象

整个系统可清晰解构为二层优化（Bi-level Optimization）：

### Object Level（对象层）
针对具体组合优化或算法任务，寻找高质量的可执行程序：

$$r^\star = \arg\max_{r \in \mathcal{R}} f(r)$$

### Meta Level（元优化层）
设计一个在有限预算 $B$ 下表现最优的自动搜索器：

$$\pi^\star = \arg\max_\pi \mathbb{E}\left[\max_{t \le B} f(r_t)\right]$$

其中搜索策略由决策与生成两部分构成：

$$\pi = (\mu, g, K_\phi) \approx (\text{Search Policy}, \text{Context Policy})$$

模型 $\phi$ 参数固定，我们真正设计和优化的正是这对策略 $(\mu, g)$。

**科研视角校准**：
> **我们不是在设计某个具体的 TSP 或 CVRP 启发式，而是在研究“算法应当怎样被自动设计”。**

TSP、CVRP、OP、OBP、VRPTW 等经典组合优化问题只是我们用来检验自动设计器性能的**实验基准环境（Testbeds）**。论文真正评价和验证的客体，是 TraceAAD 这一序贯搜索机制本身的有效性、稳健性与泛化能力。

## 10. 论文级核心科学问题与 TraceAAD 的回答

本项目面向学术界正式提出的核心问题：

> **Given a fixed LLM and a limited number of executable evaluations, how should an automated algorithm designer represent prior search experience and condition subsequent generation to maximize the value of each new algorithm experiment?**
>
> （在预训练语言模型固定且真实代码评价预算受限的条件下，自动算法设计系统应如何将已有的搜索经验表示为状态证据，并据此对后续生成进行条件化控制，使每一次新的算法实验具有最高的期望价值？）

对此，TraceAAD 给出的核心回答是：

1. **状态表示层面**：以与当前设计基底严格对齐的局部形成轨迹（Orbit / Parent-Path）作为核心状态，注入干预与效果证据，有效约束候选分布，抑制盲目的大幅重写与性能倒退；
2. **生成控制层面**：建立动作条件化机制，根据 Refine、Pivot、Fuse 的不同语义需求，实施差异化的上下文剪裁与提示引导，使有限的计算预算精确兑现为高质量的算法候选；
3. **全局决策层面**：解耦生成验证与预算调度，以机理清晰的实证数据为基础，逐步迈向自适应的 $(n, o, r)$ 联合实验选择。

## 11. 任务对象形式化与实验基准

为确保算法设计过程具有严谨的数学定义，自动算法设计任务统一规范为：

$$\mathcal{T}_{\mathrm{AD}} = (d_{\mathcal{T}}, K, \mathcal{E})$$

1. **问题描述 $d_{\mathcal{T}}$**：规定业务逻辑、输入输出规范、解的合法性边界与优化目标极性；
2. **程序模板与接口契约 $K$**：提供可运行的执行骨架，严格限定允许 LLM 修改的核心算法函数 $r$（如装箱的 `priority`、路由的 `select_next_node`）；
3. **可执行评估器 $\mathcal{E}$**：组装完整程序 $P_r = K[r]$，在训练实例集 $S_{\mathrm{train}}$ 上运行并返回可比的质量标量：

$$q(r) = \mathcal{E}(P_r; S_{\mathrm{train}})$$

### 严格的泛化验证准则
- 搜索与进化严格限制在训练实例集 $S_{\mathrm{train}}$ 上运行（如小规模实例），受限于总预算 $B$（如 1,000 次真实调用）；
- 最终胜出的最佳算法 $r^\star$ 必须在独立、未见的测试集 $S_{\mathrm{test}}$（尤其是更大规模、跨分布的复杂实例）上进行一次性盲测，验证其真正的算法结构优势，杜绝过拟合。

## 12. 执行行为与停滞诊断：求解过程与形成轨迹的双重观测

在程序演化过程中，**代码文本变化 $\neq$ 算法行为变化 $\neq$ 搜索路线变化**。为了突破“代码变了但逻辑没变”或“提示意图良好但实现失真”的盲区，系统引入了执行行为探针（如 BehaveSim / PSTraj）：

1. **改进轨迹（Formative Trajectory）**：
   记录算法候选“是如何一步步写出来的”（代码变更、算子类型、演化祖先、成败历史），负责**组织生成上下文与指导后续改写**；
2. **执行轨迹（Problem-Solving Trajectory, PSTraj）**：
   记录算法候选在固定探针实例上“是如何一步步求解具体问题的”（决策步骤、选择序列、状态转移），负责**诊断实际求解策略的重访与分散**。

通过在固定探针上度量 PSTraj 的归一化编辑距离或 DTW，系统能够在离线诊断中精准识别两类典型停滞：
- **低行为距离且无质量突破**：实质性重复停滞（实现失真或死锁，尽管代码字符串可能不同）；
- **高行为距离且无质量突破**：无效发散探索（机制变了但未产生有效求解增益）。

双重观测体系使我们能够穿透表面代码文本，将算法的设计意图、代码表征与实际运行时行为深度解耦，为 TraceAAD 搜索过程的诊断、优化和科学解释提供坚实的经验证据。
