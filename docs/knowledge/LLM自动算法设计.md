# LLM 自动算法设计：研究认识

## 一、任务本质：针对一类问题设计算法

算法设计面向一类问题：给定问题定义和一组代表性实例，构造一个能够反复求解该类新实例的算法，并使其解质量、运行效率或其他目标尽可能好。最终产物是可复用的算法；单个实例上的解是评价算法的结果。

这一过程通常依赖领域专家理解问题结构、提出算法思想、完成实现，再通过实验反复调整，因而耗时且需要经验。No Free Lunch（NFL）定理说明，在其假设下，当性能对所有可能问题等权平均时，任何算法的优势都会在其他问题上被抵消；一个算法的实际优势来自它对目标问题结构的利用。自动算法设计的目标，就是降低这种面向特定问题的设计成本。

LLM4AD 使用大语言模型提出和实现算法思想，再通过可执行评价与多轮搜索持续改进候选算法。算法设计确定最终要得到什么，evaluator 驱动的进化过程决定怎样逐步得到它。

## 二、把算法设计任务变成可执行环境

一个可交给 LLM 自动设计的任务需要三部分：

1. **问题描述 $d_{\mathcal T}$**：用简短自然语言说明要解决的问题、输入与输出、有效结果的条件和评价方向；必要的公式、约束或示例只用于澄清语义。
2. **整体程序模板与可编辑部分 $K$**：提供完整程序或可运行骨架，标明允许修改的函数或代码块，并通过函数签名、调用关系和初始实现说明这些代码怎样参与求解。
3. **evaluator $\mathcal E$**：在给定实例上构建并运行完整程序，检查程序和输出是否有效，再返回用于比较候选的分数或指标。

可以将任务简写为

$$
\mathcal T_{\mathrm{AD}}=(d_{\mathcal T},K,\mathcal E).
$$

给定候选代码 $r$，模板将其放入完整程序：

$$
P_r=K[r].
$$

evaluator 随后返回 $\mathcal E(P_r;S_{\mathrm{train}})$。其中 $S_{\mathrm{train}}$ 是设计过程中反复使用的训练实例或运行条件。

固定程序结构可以承载数据读取、状态维护、主循环和已有算法框架，让 LLM 把生成能力集中在决定性能的关键逻辑上。可编辑范围由任务决定，既可以是一个函数，也可以是多个相互关联的代码块；初始实现只需能够运行，随后由 LLM 逐步改进。

以在线装箱为例：问题描述要求按到达顺序放置物品并尽量减少使用的箱子；程序模板固定物品到达和放置流程，只开放 `priority(item, bins) -> scores`，由它为当前可用箱子计算优先级；evaluator 在多组物品序列上运行完整装箱程序，检查返回值和装箱结果，并按平均使用箱数评分。设计对象是可复用于不同物品序列的优先级算法。

## 三、evaluator 驱动的逐步进化

LLM 能够利用预训练得到的算法与代码知识提出新方案，但单次生成难以稳定得到高质量算法：候选可能不可执行、违反约束、性能较差，也可能只是在已有方案附近做无效改写。因此，代表性 LLM4AD 方法把生成放入一个反复评价和改进的闭环：

$$
\text{选择候选与历史}
\rightarrow
\text{LLM 生成或修改代码}
\rightarrow
\text{运行完整程序}
\rightarrow
\text{evaluator 评价}
\rightarrow
\text{更新候选与历史}.
$$

在这个循环中，搜索个体是候选算法 $r$。候选算法在实例上产生的路线、装箱方案或其他结果，是 evaluator 判断该算法质量的依据。搜索机制为每轮请求选择当前候选、参考历史和改进任务，LLM 根据这些上下文生成修改建议或候选代码。变异、重组和精炼等操作由搜索机制通过候选选择、参考信息和提示词具体化，LLM 负责完成本轮生成任务。

这里的“进化”是广义的程序进化：候选算法经过生成、评价、选择和继承，在多轮中逐步变化。种群、树或轨迹等结构负责保存和选择搜索历史，决定有限预算继续投入哪些设计路线、组合哪些信息以及何时探索新方向。

evaluator 为进化提供外部事实。语法错误、接口错误、不可行输出和超时会被转化为可观察的失败信号，性能变化会被转化为可比较的分数，使搜索能够淘汰、修正或选择候选。evaluator 的检查范围同时构成反馈边界：未被检查的错误仍可能漏过，评价目标与真实目标不一致时，搜索会持续优化错误的方向。因此，可行性约束、时间与内存限制以及性能指标都应在 evaluator 中明确落实。

多轮设计需要搜索预算，通常用候选评价次数、LLM 调用次数、总运行时间或计算资源限制能够尝试的改进次数。

## 四、训练实例与泛化评价

设计过程在 $S_{\mathrm{train}}$ 上反复评价、选择和修改候选，这可以理解为在一组实例上“训练”一个算法。这里的训练发生在算法候选的搜索过程中，LLM 参数通常保持不变。

| 实例集 | 用途 |
| --- | --- |
| $S_{\mathrm{train}}$ | 反复评价候选并驱动算法改进 |
| $S_{\mathrm{test}}^{\mathrm{ID}}$ | 在同分布、同规模的未见实例上评价泛化 |
| $S_{\mathrm{test}}^{\mathrm{OOD}}$ | 在规模或分布发生变化的实例上评价泛化 |

例如，可以在一组 TSP50 实例上设计启发式，再用另一组 TSP50 实例评价同分布泛化，并用 TSP100、TSP200 实例评价规模外泛化。运行自动设计循环只需要训练实例；当研究需要声称算法能够泛化到未见实例时，应使用独立测试实例。参与候选生成、评价、选择、流程调整或停止判断的实例都已进入训练过程，不能再承担独立测试的作用。

## 五、核心研究问题：把单次生成能力累积为逐步改进

LLM4AD 要解决的核心问题，是怎样通过多轮搜索让 LLM 持续产生更好的算法。这里的“逐步改进能力”属于整个系统：搜索机制反复组织上下文并调用 LLM，LLM 每次只根据给定上下文完成一个明确任务，例如提出一个修改方向或实现一项指定修改。系统效果取决于 LLM 能否高质量完成本轮任务，也取决于搜索与上下文机制能否为它提供合适的任务和信息。

### 5.1 LLM 完成本轮任务所需的能力

1. **理解问题与当前算法**：理解任务、待设计函数的作用、当前代码及约束。
2. **利用给定上下文**：从轨迹中识别已有改进、失败尝试和当前可用信息。
3. **产生高质量的下一步输出**：按照本轮明确指令，提出算法修改或完成代码实现。

这三项能力共同决定一次 LLM 请求的质量。搜索对象、参考候选、相关历史、改进方式和提示词由外部机制确定；LLM 的职责是充分利用这些输入，完成本轮指定任务。

### 5.2 搜索与上下文机制的本质职责

探索与利用、搜索算子、种群管理、上下文组织和轨迹机制共同服务于一个目标：为 LLM 构造更有价值的请求，并把多次单步生成累积为持续的算法改进。

| 组成部分 | 本质任务 |
| --- | --- |
| evaluator | 执行候选，检查可行性并提供真实性能反馈 |
| 轨迹机制 | 保存算法怎样被修改以及修改产生了什么结果 |
| 上下文组织 | 从已有信息中选择与本轮任务相关的内容并呈现给 LLM |
| 搜索算子与提示词 | 规定本轮要进行的修改类型和具体任务 |
| 种群管理与候选选择 | 在有限调用和评价次数下分配搜索机会，兼顾发展已有路线与尝试新路线 |

借用足球类比，LLM 是负责完成射门的前锋，搜索与上下文机制负责组织推进并把球送到合适位置。每项机制都应说明它改善了哪一环：信息保留、上下文选择、任务设定、反馈质量或搜索机会分配；其价值最终要由候选质量、最终算法性能和搜索成本验证。

### 5.3 TraceAAD：在线搜索与能力内化

TraceAAD 首先研究如何利用算法改进轨迹构造更高效的在线搜索。轨迹记录候选从何而来、经历了什么修改以及得到什么评价；搜索机制据此选择设计路线和相关经验，再把它们组织成单次 LLM 请求，使有限评价预算能够产生更好的代码。

进一步的研究路线，是把搜索过程中形成的任务、上下文、修改行为、候选代码和评价结果转化为可学习信号，通过强化学习把有效的算法改进策略内化到模型中，使模型用更少的在线搜索提出更好的候选。

[待验证] 长期目标是在相同任务和评价条件下，使较小模型达到或超过较大模型的算法设计性能，同时降低模型调用与搜索成本。该目标需要通过跨任务实验、独立测试和完整成本核算验证。
