## 三、错误处理链是否正常

### 已正常工作的部分

- parser 允许 import、helper、常量和额外顶层依赖，同时仍严格要求目标函数恰好一个、函数名正确、签名正确、代码可编译。
- `invalid_output` 不消耗 evaluator budget；调度器会用同一个父/ donor 上下文发起一次 repair。
- `runtime_error`、`timeout`、`invalid_result`、`nonfinite_fitness` 被列为可修复 evaluator failure；repair 失败后不会无限重试，而是记录失败并继续搜索。
- 所有 evaluator 失败的原始 `error_type`、`error`、`traceback` 都保存在 `evaluations.jsonl`，因此事后诊断证据完整。

### 当前仍有问题的部分：repair 反馈丢失详细异常

`_evaluate_pending` 得到的详细异常只写入 `evaluations.jsonl`。随后 `_advance` 写入 `events.jsonl` 时只保存 `reason`，没有把 `error_type` 和 `error` 放进事件；`repair_prompt()` 又只读取 event。因此模型实际看到的 repair 失败段落是：

```text
# Failure
Error: runtime_error
```

或 `Error: invalid_result` / `Error: timeout`，而看不到真正的 `ValueError: kth(=2) out of bounds`、数组维度不匹配、`the heuristic returned the depot while already at the depot` 等细节。

这意味着“repair 被触发”是正常的，但“repair 获得足够诊断信息”目前不正常。一次 repair 的成功不能证明反馈链路完整。

### repair 统计

| 模型 | 解析失败→repair 成功 | runtime→repair 成功/总已配对 | timeout | invalid_result |
|---|---:|---:|---:|---:|
| qwen3.6 | 42/42 | 5/9 | 1/1 | 0/3 |
| qwen3.8 | 33/33 | 21/27 | 6/8 | 3/5 |

repair 多数能恢复，但仍有 runtime/timeout/invalid_result 的二次失败；这些失败在当前设计中会被记录并跳过，不会卡死搜索。这是一个合理的容错策略，但应先修复详细异常没有进入 prompt 的问题，再判断模型的真正修复能力。

### 代表性真实 evaluator 错误

- CVRP：`TypeError: float object cannot be interpreted as an integer`、NumPy boolean indexing 维度不匹配、`einsum` 维度不匹配、变量未定义。
- TSP：`kth out of bounds`、数组 truth value 歧义、索引越界和超时。
- VRPTW：当前节点已经是 depot 时又返回 depot、局部函数参数数量不匹配、数组索引/解包错误。

### 上下文观察与最终处理决定（源代码已更新，运行批次仍使用原 frozen runtime）

1. 快照中的 Output 指令只说 Idea 是“一段简短的话”，parser 则以 500 tokens 为硬上限。按用户决定，源代码中的提示已改为不超过 200 words，解析继续使用 500 tokens 上限。
2. VRPTW 有在 depot 再次返回 depot 的失败。此前把补充 evaluator 说明当作必要修正，超出了用户希望的任务上下文范围。按用户决定，现已撤回新加的 VRPTW design_notes，并从 V10.11 中删除对所有任务 design_notes 的注入；不保留 Evaluator Semantics，也不改名保留 Interface Notes。新的任务上下文只使用公共问题说明和目标函数 stub。

repair 详细错误传递修复保留；新启动的运行会把实际失败的异常类型和消息传入 repair prompt。VRPTW 的评估行为没有改动。下面的 prompt 是修正前的历史原文，仍保留以供复核；现有 frozen runtime 没有在运行中替换。

## 五、中文审阅版上下文

以下是与上面英文原文逐段对应的中文版本。它用于人工审阅；本批次实际发送的是英文，中文没有作为额外 system/user message 发送。Python 模板代码必须原样保留，不能翻译函数名、参数名或数组字段。

### 通用上下文

**任务与模板**：模型要研究任务和已有候选，设计一个有竞争力的算法。公共模板给出目标函数名、参数签名、文档字符串和最小基线；目标函数以及它需要的 import、helper、常量属于模型设计空间。公开上下文中没有 evaluator 的完整实现，evaluator 在外部进程中执行。

**搜索上下文**：适应度越高越好。首次 Init 从任务与基线开始；后续操作会看到当前算法。Formation history 只包含有限条“操作、父代适应度→子代适应度、Idea”记录；Fuse 还会看到 donor 算法。

**设计操作**：
- Init：研究任务和已有初始算法，提出一个有竞争力的新候选。
- Refine：根据当前代码和形成历史做一次连贯的机制改进。
- Tune：保留决策方法和计算结构，只调整少量系数、阈值、指数或 schedule。
- Pivot：围绕不同的主要决策机制构造竞争性替代方案。
- Fuse：比较 host 与 donor，把 donor 的相关计算融合进 host 的一个连贯机制。

**输出**：严格输出 `Idea:` 一段说明和 `Code:` 一个完整 Python 程序；目标函数名和签名必须精确，允许 import/helper，但目标函数必须存在。实际 parser 另外施加 Idea 不超过 500 token 的限制，英文 Output 没有把这个数值告诉模型。
