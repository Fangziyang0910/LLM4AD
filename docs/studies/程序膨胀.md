# 程序膨胀

> 研究问题：怎样区分必要复杂化与无收益代码增长，并在不压制算法质量的前提下控制后者？
>
> 状态：v4 现象已经确认；V5.1 的生成提示与完全同分择简已有正式过程数据，独立贡献尚未消融。
>
> 当前判断：质量优先、完全同分时择简仍是温和候选，但它会真实改变搜索锚点，需要独立消融。`refine` 应聚焦证据支持的机制修正，不在提示中罗列替换、删除、合并和简化操作。
>
> 影响设计：[TraceAAD v5：最小程序膨胀控制](../methods/TraceAAD-v5完整机制设计.md#8-最小程序膨胀控制)。

本文研究一个具体问题：在 LLM 驱动的程序搜索中，为什么候选程序可能随搜索持续变长，以及现有自动算法设计方法是否显式控制这种倾向。这里把“程序长度膨胀”（program/code bloat）定义为：程序规模持续增加，但新增代码没有带来相称的适应度、泛化性或可解释性收益。

文献结论很明确：程序变长不是新现象，也不能自动视为算法思想变丰富。遗传编程已经长期观察到，可变长度表示、性能平台上的中性变异、冗余代码的保护作用，以及只按任务性能选择，都会让“更长但同样好”的程序在搜索中积累。LLM 生成把语法变异替换成语义修改，但只要候选长度可变、评价只看任务分数、修改提示偏向“增加/组合新机制”，同一类选择偏置仍然可能出现。

## 1. 遗传编程中的已知现象

### 1.1 什么是 bloat

经典遗传编程使用可变长度程序，因此会自然出现“不必要的解规模增长”。理论研究直接把 bloat 定义为 unnecessary growth，并指出它会拖慢优化；不加控制与加入长度控制时，优化时间界也会不同。[Doerr et al., *Bounding Bloat in Genetic Programming*](https://arxiv.org/abs/1806.02112)

这一定义包含两个部分：

1. 程序确实变长；
2. 变长没有带来相称的功能或适应度收益。

因此，单看代码行数上涨还不能证明 bloat；需要同时看长度与训练分数、测试分数、运行时间和语义变化。反过来，如果更长程序确实实现了必要的新机制并稳定提高泛化性能，也不应仅因长度增加而淘汰。

### 1.2 为什么只按任务性能选择会偏向更长程序

早期工作提出了两类重要解释：一类是 fitness causes bloat，即搜索进入难以继续提升的平台后，同等适应度的程序中，结构更大的等价表示数量可能更多；另一类是 neutral code is protective，即冗余或不生效的代码可以缓冲后续变异，使较大程序更不容易被破坏。模拟研究观察到了两种机制的预测。[Banzhaf & Langdon, *Some Considerations on the Reason for Bloat*](https://doi.org/10.1023/A:1014548204452)

Langdon 与 Poli 更早通过理论分析、人工蚂蚁实验和 Price theorem 研究了“fitness-based selection leads to bloat”：当搜索后期大量程序与当前最好程序同 fitness，而同一行为有更多长表示时，没有规模偏好的选择会更常遇到并保留长表示。[Langdon & Poli, *Fitness Causes Bloat: Mutation*](https://doi.org/10.1007/BFb0055926)

另一些研究强调修改位置带来的存活偏置。树的深层局部修改较少破坏整体行为，移除大子树比添加新子树更容易损害 fitness，因此存活下来的后代会偏向保留旧结构并增加局部结构。[Luke, *Modification Point Depth and Genome Growth in Genetic Programming*](https://doi.org/10.1162/106365603321829014) 这对 LLM 搜索的对应仍是**机制推断**：在完整父程序上追加局部保护逻辑，通常比重写核心机制更容易保持代码可执行和原有分数，于是“低风险追加”可能在筛选中胜过“高风险简化”。

对 LLM 程序搜索可以作如下**机制推断**：

- 如果选择只看任务分数，那么“同分但更短”和“同分但更长”没有选择差异；
- LLM 的改进提示通常要求引入新思想、组合多个机制或继续优化，新增分支、参数和辅助量比删除已有逻辑更容易满足这一表面要求；
- 新代码即使没有贡献，也可能不影响训练分数，因而能沿父子链保留下来；
- 后续提示再次把完整长程序当作父代，模型通常在其上继续增量修改，形成路径依赖；
- 搜索越久，等价或近等价的冗余逻辑越可能累积。

这不是说 LLM 搜索与树形遗传编程的具体原因完全相同，而是说二者共享三个足以产生长度偏置的条件：可变长度表示、只按性能选择、缺少删除或简约压力。

### 1.3 经典控制方法及其边界

遗传编程常见的控制思路包括：

- **硬限制**：限制树深、节点数、代码字符数或输出 token 数。它能阻止失控增长，但阈值过小会截断真正需要复杂机制的候选。
- **简约压力（parsimony pressure）**：在适应度中加入规模惩罚，或在性能相同/近似相同时优先短程序。验证集与简约压力实验表明，它能显著降低平均树规模，同时保持测试准确率。[Gagné et al., *Genetic Programming, Validation Sets, and Parsimony Pressure*](https://arxiv.org/abs/cs/0601044)
- **词典序简约**：先比较任务性能，只在同分或落入容差带时比较长度。这比固定线性惩罚更不容易牺牲真实质量，但仍要设计“多接近才算等价”。[Kötzing et al., *Destructiveness of Lexicographic Parsimony Pressure and Alleviation by a Concatenation Crossover in Genetic Programming*](https://arxiv.org/abs/1805.10169)
- **多目标搜索**：把任务性能与运行时间、代码长度、圈复杂度或可读性作为不同目标，保留 Pareto 解，而不是事先把它们压成一个固定权重的标量。
- **显式简化**：定期删除冗余分支、合并等价表达式，或让生成器执行“在不损失功能的前提下简化”。数值/代数简化已有专门的 bloat-control 研究。[Kinzett et al., *Numerical Simplification for Bloat Control and Analysis of Building Blocks in Genetic Programming*](https://doi.org/10.1007/s12065-009-0029-9)
- **动态惩罚或动态上限**：根据当代 score–size 关系校准简约系数，或让允许规模跟随当前最好解变化，避免固定阈值过紧或过松。动态简约系数可以控制种群平均规模；Dynamic Limits 在不改变 fitness 的情况下取得了接近 baseline 的质量和更小的树。[Poli & McPhee, *Parsimony Pressure Made Easy*](https://doi.org/10.1145/1389095.1389340)；[Silva & Costa, *Dynamic Limits for Bloat Control in Genetic Programming and a Review of Past and Current Bloat Theories*](https://doi.org/10.1007/s10710-008-9075-9)

这些方法共同表达的原则是：长度不应成为独立优化目标，简洁性应在保持任务质量的条件下发挥作用。过强的长度惩罚会偏向欠拟合的小程序，完全没有长度信号则会让搜索免费累积复杂度。

词典序规则还有一个重要边界：如果几乎每次增加结构都能带来极小但非零的训练分数提升，那么“只在完全同分时选短程序”可能几乎从不触发。跨四类 GP 问题的比较研究观察到了这一失败模式，同时发现 depth limit 与惩罚式方法组合通常比单独使用其中一种更稳。[Luke & Panait, *A Comparison of Bloat Control Methods for Genetic Programming*](https://doi.org/10.1162/EVCO.2006.14.3.309) 因此，AAD 中更合理的是“统计上近同分择简”或温和的动态复杂度成本，而不是只处理浮点数完全相等。

## 2. LLM 自动算法设计方法逐项核对

### 2.1 FunSearch：短程序具有显式采样优势

FunSearch 是最值得直接对照的方法。论文不只说输出程序“往往简洁”，还在附录给出了实际选择规则：程序先按分数向量聚类，在选中的簇内以程序字符长度构造概率，短程序更容易被选入下一次 prompt。附录算法标题也直接写明“giving higher probability to shorter programs”。作者进一步把这种偏置解释为对低 Kolmogorov complexity 程序的隐式鼓励，并认为它有助于扩展到大实例。[FunSearch 论文 PDF，正文与附录 A.1/F.16](https://storage.googleapis.com/deepmind-media/DeepMind.com/Blog/funsearch-making-new-discoveries-in-mathematical-sciences-using-large-language-models/Mathematical-discoveries-from-program-search-with-large-language-models.pdf)；[Google DeepMind 作者代码](https://github.com/google-deepmind/funsearch)

关键点是：FunSearch 没有用长度覆盖任务分数。它先按表现组织程序，再在相同表现区域偏向短程序。这更接近“等质择简”，而不是“越短越好”。

本地 `../papers/` 与 `../reference_code/` 当前都没有 FunSearch 的论文源码或作者实现，因此这一项保留官方论文 PDF 与 Google DeepMind 仓库作为一手来源，不能声称已完成本地 paper–code 对照。本地 MEoH/HSEvo 对 FunSearch 的转述只用来定位方法，不作为上述结论的证据。

### 2.2 EoH：有简化算子，但主选择仍由适应度决定

EoH 的五种提示算子中，M3 明确要求识别冗余组件并简化代码。论文把 modification operators 概括为修改机制、调整参数和删除冗余部分。[EoH 论文，Section 3](https://arxiv.org/abs/2401.02051)；[EoH 作者代码中的 M3 prompt](https://github.com/FeiLiu36/EOH/blob/main/eoh/src/eoh/eoh/evolution.py)

但是 EoH 的父代选择和种群更新主要按任务适应度排序。由此得到的**机制推断**是：M3 能偶尔产生更短候选，却没有让“同分更短”的候选持续占优。若简化候选因评估噪声略差，还可能直接被淘汰。因此，M3 是生成侧的简化机会，不是搜索侧的复杂度控制。

本地论文与作者代码把这个边界显示得更清楚。论文在 `../papers/EoH/3-method.tex:71-85` 明确写出“removing redundant parts”和 M3；当前本地作者代码在 `../reference_code/EoH/eoh/src/eoh/eoh/evolution.py:223-235` 实现了简化，并把目标具体化为识别可能对分布内实例过拟合的组件、简化以改善 OOD 泛化。然而，`../reference_code/EoH/eoh/src/eoh/config.py:23-29` 和 `../reference_code/EoH/eoh/src/eoh/run.py:104-105` 的默认算子只有 `e1/e2/m1/m2`，没有 M3；种群管理在 `../reference_code/EoH/eoh/src/eoh/eoh/eoh.py:37-47` 只按 objective 保留个体。因此，**作者明确提出了 anti-bloat 生成机制，但当前本地参考实现默认并不会调用它**。论文主张与代码能力基本一致，默认运行行为比论文机制集合更弱。

### 2.3 ReEvo：反思提供语义反馈，不提供简约压力

ReEvo 通过短期反思比较较优/较差候选，再用反思生成 crossover 候选，并用长期反思指导精英变异。论文讨论了 sample efficiency、token efficiency 和 verbal gradients，但没有把代码长度、复杂度或可读性纳入选择。[ReEvo 论文](https://arxiv.org/abs/2402.01145)；[作者代码与 prompts](https://github.com/ai4co/reevo)

“反思可能指出冗余”只能算**机制推断**。如果 prompt 没有明确要求在同等质量下删除无效逻辑，且 fitness 不含复杂度信号，反思仍可能不断建议添加新因素。

本地一手资料支持这一判断。论文把个体定义为除函数签名外不受表示约束的代码片段（`../papers/ReEvo/sections/04_evolution.tex:29-46`），流程是 selection、短期反思、crossover、长期反思、精英变异，没有规模变量。作者 prompt 只要求按反思写出 “improved” 或 “mutated” 函数（`../reference_code/ReEvo/prompts/common/crossover.txt:1-15`、`../reference_code/ReEvo/prompts/common/mutation.txt:1-11`），父代排序、elite 和 best 更新都只比较 `obj`（`../reference_code/ReEvo/reevo.py:249-299`）。所以论文与代码一致：反思是任务质量的语义信用，不是复杂度信用。

### 2.4 HSEvo：代码多样性与代码简洁性是两个维度

HSEvo 使用代码嵌入和多样性指标研究种群的探索—利用平衡，并通过和声搜索调整搜索状态。论文核心变量是 objective score、semantic/code diversity 和 token budget，没有报告程序长度随迭代的变化，也没有复杂度惩罚。[HSEvo 论文](https://arxiv.org/abs/2412.14995)；[作者代码](https://github.com/datphamvn/HSEvo)

因此不能把 diversity control 当作 bloat control。两个程序语义差异很大时可以都很长；同一个程序不断加入无效逻辑时，embedding 甚至可能把这种增长误认为新颖性。这一点是**机制风险推断**，需要实验验证。

具体而言，论文先去注释与 docstring、格式化代码，再用 code embedding 计算 SWDI/CDI（`../papers/HSEvo/aaai25.tex:250-290`），并把目标明确写成平衡 diversity 与 objective performance（`../papers/HSEvo/aaai25.tex:483-524`）。作者实现的 elite 更新、反思排序与 harmony replacement 仍只看 `obj`（`../reference_code/HSEvo/hsevo.py:326-376`、`../reference_code/HSEvo/hsevo.py:598-624`），默认最大输出为 32768 tokens（`../reference_code/HSEvo/cfg/config.yaml:13-25`）。论文与代码一致地控制“搜索分布是否多样”，没有控制“单个程序是否过大”。“embedding 可能奖励由冗余增长造成的表面差异”是本文的机制风险推断，不是 HSEvo 作者的主张。

### 2.5 MEoH：复杂度应成为独立设计标准

MEoH 对此问题的表述最直接：现有单目标 LLM 启发式搜索主要优化任务表现，忽略了效率、启发式复杂度和代码可读性。它把启发式设计表示成多目标优化，搜索非支配解；论文还保留了 EoH 的 M3 简化算子，并在三目标实验中用 Halstead difficulty 衡量代码可读性。[MEoH 论文](https://arxiv.org/abs/2409.16867)

需要准确区分三种量：

- 运行时间衡量执行效率；
- Halstead difficulty 近似衡量代码可读性/认知难度；
- LOC、字符数或 AST 节点数衡量结构规模。

它们相关但不等价。MEoH 证明了框架可以把非性能标准纳入 Pareto 搜索，但不能据此说它默认惩罚代码长度。若要专门研究 bloat，仍需把长度或结构复杂度显式加入目标和日志。

本地论文的精确边界是：引言把 heuristic complexity 和 code readability 列为被单目标方法忽略的标准（`../papers/MEoH/MEoH.tex:150-174`），形式化部分允许目标向量包含 complexity（`../papers/MEoH/MEoH.tex:209-233`）；正文两目标实验实际使用 optimal gap 与运行时间（`../papers/MEoH/MEoH.tex:309-327`）；附录三目标实验才加入 Halstead difficulty 可读性（`../papers/MEoH/MEoH.tex:1250`）；M3 仍负责消除冗余（`../papers/MEoH/MEoH.tex:990-1010`）。因此“MEoH 已解决 code bloat”会过度解读论文。更准确的说法是：它提供了让复杂度获得独立选择压力的框架。`../reference_code/` 中没有 MEoH 作者实现，无法核对论文主张与代码默认行为。

### 2.6 MCTS-AHD：树路径会保存增长历史，但价值函数不看规模

MCTS-AHD 用树保存所有生成程序，以 UCT、渐进扩展和六种 action 分配预算；s1 action 利用根到叶的程序序列生成下一步。论文没有给代码长度、复杂度或简化 action。thought-alignment 的“三句话”约束只限制自然语言描述，不限制生成的程序。[MCTS-AHD 论文](https://arxiv.org/abs/2501.08603)；[作者代码](https://github.com/zz1358m/MCTS-AHD-master)

由机制可以推断：如果沿树路径持续进行局部增强，子节点容易继承父节点全部逻辑再增加新逻辑；UCT 只要看到任务分数提高就会奖励该路线。树结构使长度增长更容易审计，但本身不会抑制长度增长。

本地论文和代码完全支持“规模不进入价值”的判断。论文令节点质量直接等于 heuristic performance（`../papers/MCTS-AHD/icml2025.tex:257-265`），thought-alignment 只把语言描述限制在三句（`../papers/MCTS-AHD/icml2025.tex:249-251`）。作者代码的节点 reward、Q 和 UCT 只由 objective 构成（`../reference_code/MCTS-AHD-master/source/mcts.py:11-23`、`../reference_code/MCTS-AHD-master/source/mcts.py:51-70`），active population 也只按 objective 保留（`../reference_code/MCTS-AHD-master/source/pop_greedy.py:3-16`）。

同时，作者 prompt 揭示了两个真实的膨胀通道：m1 明确要求引入 “more novel mechanisms and new equations or programme segments”（`../reference_code/MCTS-AHD-master/source/evolution.py:125-139`）；s1 要从路径上的全部算法提取有益思想并生成更强算法（`../reference_code/MCTS-AHD-master/source/evolution.py:157-177`）。相对地，m2 只改参数、e1 要求不同结构，可能产生替换而非追加。由此能下的结论是：MCTS-AHD 同时存在增长型和重写型 action，但没有机制判断新增复杂度是否值得。树最大深度 10（`../reference_code/MCTS-AHD-master/source/mcts.py:32-37`）只限制单条父子链深度，不限制每个节点的代码规模。

### 2.7 PathWise：已观察到复杂度差异，但只形成软纠偏

PathWise 在 limitation 中明确写到，不同 LLM backbone 会产生不同 implementation style，包括代码复杂度和抽象层次差异，且这种差异对不同问题域的影响可能不同（`../papers/PathWise/example_paper.tex:2649`）。论文还给出一个更细的观察：world-model critic 经常通过删除冗余计算来降低算法复杂度和改善执行效率（`../papers/PathWise/example_paper.tex:856`、`../papers/PathWise/example_paper.tex:2486`）。这说明作者确实观察到了基于语义反思的“软简化”现象。

但这仍不是显式 anti-bloat。作者代码的 world-model critic prompt 只比较好坏代码并要求给出改善任务 objective 的设计原则，没有要求删除冗余或限制长度（`../reference_code/PathWise/prompts/common/user_world_model_critic.txt:1-18`）；world model 只要求生成更优完整函数（`../reference_code/PathWise/prompts/common/user_world_model.txt:1-13`）。论文所谓“to control search complexity”的父节点删除规则控制的是蕴含图 state 的节点数（`../papers/PathWise/example_paper.tex:212`；实现见 `../reference_code/PathWise/pathwise.py:1443-1478`），不控制节点内代码规模。选择与补位仍按 fitness（`../reference_code/PathWise/pathwise.py:210-250`、`../reference_code/PathWise/pathwise.py:1836-1850`）。

因此 PathWise 的底层秘诀只能表述为：**比较式 critic 有机会从“更好代码为什么更好”中抽取删除与替换经验，再把它反馈给下一轮生成**。这是比普通增量 prompt 更有利于简化的结构，但没有保证；其探索扰动还会要求引入新程序段（`../reference_code/PathWise/pathwise.py:119-130`），形成相反的增长压力。论文主张与代码基本一致：简化是 critic 的经验性产物，不是硬编码目标。

### 2.8 ShinkaEvolve：当前实现有复杂度设施，但默认不会使用

ShinkaEvolve 论文的核心是父代采样、代码新颖性拒绝采样和 LLM bandit，没有把代码长度作为论文主目标。[ShinkaEvolve 论文](https://arxiv.org/abs/2509.19349)

当前作者仓库已经比论文描述更进一步：

- 对 Python 计算圈复杂度、Halstead 指标、LOC、逻辑 LOC、可维护性和最大嵌套深度；
- archive ranking 支持 `loc`、`lloc`、`complexity`、`maintainability` 和 `nesting`；
- 负权重表示越低越好。

本地代码证据是：Python 分析计算圈复杂度、Halstead、LOC、逻辑 LOC、可维护性与嵌套深度（`../reference_code/ShinkaEvolve/shinka/database/complexity.py:43-104`），入库时自动记录这些指标（`../reference_code/ShinkaEvolve/shinka/database/dbase.py:813-827`），多准则 archive 可用负权重表达“越低越好”（`../reference_code/ShinkaEvolve/shinka/database/dbase.py:98-104`、`../reference_code/ShinkaEvolve/shinka/database/dbase.py:1958-2042`）。但默认 `archive_criteria` 是 `{"combined_score": 1.0}`（`../reference_code/ShinkaEvolve/shinka/defaults.py:49-50`），而且当前 `_is_better` 只在准则数大于 1 时进入多准则排名（`../reference_code/ShinkaEvolve/shinka/database/dbase.py:2142-2164`）。因此若要启用复杂度压力，应把任务分数与复杂度共同配置为多准则；只把单个 `loc` 写成唯一准则在当前实现中并不足以改变比较路径。[复杂度分析实现](https://github.com/SakanaAI/ShinkaEvolve/blob/main/shinka/database/complexity.py)；[archive 多准则实现](https://github.com/SakanaAI/ShinkaEvolve/blob/main/shinka/database/dbase.py)；[默认配置](https://github.com/SakanaAI/ShinkaEvolve/blob/main/shinka/defaults.py)

这提供了一个重要经验：**记录复杂度不等于控制复杂度**。只有当它进入选择、淘汰、Pareto 保留或同分 tie-break 时，搜索分布才会改变。

论文与代码并不冲突，但代码能力明显超出论文明确主张。论文只说明评估返回 scalar fitness、public metrics 和文本反馈（`../papers/ShinkaEvolve/sections/03_method.tex:53-74`），以及 novelty rejection 避免近重复程序（`../papers/ShinkaEvolve/sections/03_method.tex:27-48`）；它没有宣称默认进行 LOC/complexity 优化。当前本地作者仓库的复杂度分析与多准则 archive 应视为后续工程能力，而非论文已验证的 anti-bloat 结论。

### 2.9 CALM：直接识别增长机制，并用简化算子对冲

CALM 是本地论文库中对程序膨胀表述最直接的 LLM-AAD 工作。作者先把 injection、replacement、crossover、simplification 和 initialization 列为生成算子（`../papers/CALM/main.tex:184-192`），随后明确指出：反复 injection、crossover 和 replacement 会使 heuristic structure 越来越复杂，累积冗余或不必要的冗长组件；simplification operator 的职责就是生成更简洁且有效的版本来对冲这一趋势（`../papers/CALM/main.tex:226`）。这与 GP 的 bloat 定义高度一致，虽然论文没有使用 “program bloat” 这一术语。

CALM 还提供了实验层面的作者证据。消融中，移除 simplification 在两个任务上造成最大性能下降；作者将原因解释为其它算子倾向于增加复杂度或长度，而 simplification 独自负责减少冗余、促进简洁表示（`../papers/CALM/main.tex:524-525`）。这不是“短代码一定更好”的结论，而是说明定期去除无收益结构既可控制增长，也可能改善搜索质量。

CALM 的底层逻辑有两点值得 TraceAAD 借鉴：

1. 它把**新思想注入**与**已有结构简化**设为职责不同的算子，使搜索既能增加必要复杂度，也有专门通道删除失效结构；
2. 它使用 fine-grained injection/replacement，让修改更容易归因于具体组件，而不是每轮只对完整程序做无边界增强（`../papers/CALM/main.tex:188-192`）。

需要保留证据边界：本地 `../reference_code/` 没有 CALM 作者实现，无法核对 simplification 的真实调度概率、选择规则与默认启用状态；当前只能确认论文主张和消融报告。

### 2.10 跨方法的隐含控制逻辑

将作者明说与本文推断分开后，现有方法可以归纳成四层控制：

- **选择层择简**：FunSearch 在同分簇内偏向短程序。这直接改变长、短等质候选的繁衍概率，因果链最短。
- **生成层删减**：EoH/MEoH 的 M3 与 CALM simplification 提供删除通道。它们能产生短候选，但若不进入默认调度，或简化后轻微掉分就被淘汰，作用会受限。
- **目标层权衡**：MEoH 的 Pareto 目标与 ShinkaEvolve 的可配置多准则 archive 让复杂度获得独立信用。其优势是保留“更长但确实更强”的解，代价是需要定义正确的复杂度指标与选择口径。
- **语义层反思**：PathWise critic 有时能总结“删除冗余计算”的经验；ReEvo/HSEvo 的反思也理论上可能做到。但只要 prompt 和 fitness 都不要求简化，这只能视为不稳定的涌现行为。

相反，以下机制会隐含放大膨胀：

- 完整父程序进入下一轮上下文，并要求 improved/mutated version；
- injection、crossover、组合多父代思想、沿路径汇总有益思想；
- 把新程序段、不同结构或 embedding 差异当作 novelty；
- 只按任务分数更新 elite、Q、archive 或 global best；
- 用输出 token 上限、描述字数上限或图节点数上限替代代码规模控制。

底层原因是一致的：增加复杂度通常有明确动作和新颖性奖励，删除复杂度却缺少独立动作、信用与存活保证。有效 anti-bloat 机制的共同点，是让删除获得生成机会，并让近同质的简洁候选在选择中有真实优势。

## 3. 对 TraceAAD 长度现象的研究含义

以下不是对当前 TraceAAD 代码的结论，而是从上述文献得到、需要结合其真实 prompt、选择规则和实验日志验证的假设。

### 3.1 最可能的因果链

如果 TraceAAD 同时满足以下条件，就会存在明确的长度增长通道：

1. 轨迹中的下一步以已有完整程序为基础；
2. 提示更常要求改进、组合、增强或引入新机制，较少要求替换或删除；
3. 评估只奖励任务分数，不记录或比较代码规模；
4. 同分或近同分时，没有优先选择更短程序；
5. 生成侧最大 token 上限足够宽；
6. 较长程序不会因执行时间、错误率或测试泛化而受到间接惩罚。

那么搜索会形成“父程序继承 → 局部加法修改 → 新逻辑免费保留 → 长程序成为下一代上下文 → 继续加法修改”的正反馈。轨迹历史会让这一过程比无父代的独立采样更可见；如果使用方式偏向继承全部旧逻辑，也可能让它更稳定。

### 3.2 `max_tokens` 不是 anti-bloat

多篇 AAD 论文和作者配置都设置了 LLM 最大输出 token 数，但这只是防止单次响应无限长或超过模型上下文。只要上限远高于当前候选长度，搜索仍可在每一代逐渐接近上限。真正的复杂度控制需要比较候选之间的长度或复杂度，并让比较结果影响搜索。

### 3.3 最稳妥的机制方向是“等质择简”

文献更支持以下原则：

> 任务质量仍是首要目标；当两个候选性能相同或落在统计上难以区分的容差内时，优先保留和继续发展更短、更快或更易读的候选。

FunSearch 的同分簇内短程序采样、遗传编程的词典序简约，以及 MEoH 的多目标思路都支持这一方向。它避免把“越短越好”变成新的错误目标，也能切断无收益代码的代际累积。

这里的“容差”不能随意设为一个固定小数。更可靠的口径可以来自重复评估方差、置信区间、候选在多个训练实例上的成对差异，或当代 score–size 协方差。经典 GP 研究也显示，固定重罚或过小硬上限会把种群压向过小程序并牺牲性能，因此 anti-bloat 应当是温和、可观测且可消融的机制。[Soule & Foster, *Effects of Code Growth and Parsimony Pressure on Populations in Genetic Programming*](https://doi.org/10.1162/evco.1998.6.4.293)

### 3.4 应先补齐的观测

在决定惩罚方式前，应至少对每个候选记录：

- 非空 LOC、字符数、token 数和 AST 节点数；
- 圈复杂度或最大嵌套深度；
- 训练分数、测试分数、执行时间和失败率；
- 相对父程序的长度增量与分数增量；
- 操作类型和轨迹深度。

应分别画出：

1. 全部候选的长度随 sample/generation 变化；
2. 每代父代、子代、存活者和全局最优程序的长度；
3. 分数增量与长度增量的联合分布；
4. 同分或近同分候选中的长度分布；
5. 各生成算子的平均长度增量和有效改进率；
6. 训练最优与测试最优程序的长度差异。

只有这些证据能区分三种不同现象：必要复杂化、无收益 bloat、训练集过拟合。

### 4.1 变长没有表现出更高的直接改进率

从 v4 checkpoint 的单父代边直接比较子程序与锚点程序：

| task | 父子边数 | 子代变长占比 | 变长子代改进率 | 子代变短占比 | 变短子代改进率 |
| --- | ---: | ---: | ---: | ---: | ---: |
| TSP | 2195 | 65.3% | 14.7% | 31.1% | 17.0% |
| CVRP | 1704 | 67.0% | 18.0% | 29.8% | 18.3% |
| KP | 1970 | 74.8% | 3.7% | 22.9% | 5.3% |
| OBP | 2643 | 67.6% | 8.1% | 25.6% | 12.1% |
| OP-ACO | 2742 | 59.5% | 9.4% | 36.7% | 11.9% |

五个任务中，变长子代的直接改进率都没有超过变短子代。`trace_ideate` 的单步长度增量中位数在五个任务中为 +10 至 +22 行，`trace_refine` 也为 +2 至 +9 行。KP 提供了最清楚的无收益增长例子：三次 v4 run 分别在 sample 33、41、51 就找到相同训练最好分数，对应程序只有 55、71、46 行；搜索继续后，后 20% 候选的平均中位长度达到约 382 行。

这些事实说明当前现象已经不只是“必要的新机制让代码适度复杂化”。搜索分布系统性地产生更长程序，其中大量增长没有转化成相对父程序的即时改进。

### 4.2 当前实现中的长度正反馈

实际代码与 prompt 构成了以下闭环：

1. `trace_ideate` 明确要求提出新思想；`trace_refine` 要求保留已有价值思想并继续细化。两个算子都没有要求删除被替代逻辑或维持复杂度预算。
2. code prompt 把锚点完整代码交给模型，并要求输出新的完整实现。它没有“优先替换而非叠加”“删除已失效组件”或“无直接收益时不得增加复杂度”的约束。
3. 最大轨迹长度 8 只限制历史文字和节点后缀，不限制锚点程序本身。旧逻辑一旦进入代码，就可以在后续每一代继续被完整继承。
4. v4 的 `ProgramNode` 和 `ValueVec` 不再记录 compactness；父代选择、生存管理和 global-best 更新只看 fitness、路径趋势、访问次数与少量路线差异，没有近同分择简。
5. TSP 三次 v4 run 的 code prompt 前后 20% 中位字符数从 7438/7955/10221 增至 17463/25166/17383；prompt 长度与 response 长度相关为 0.771/0.860/0.663。越来越长的父程序直接成为越来越长的生成上下文。
6. 首轮实验配置允许单次输出 16384 tokens，远高于实际回复规模，却把 32K 上下文的一半预留给输出，间接压缩了长程序和双轨迹输入。V5.1 根据 12,000 个历史成功回复的真实 tokenizer 计数把上限与预留统一为 8192；这仍不构成 LOC 简约压力，只修正输入/输出预算失衡。

历史版本还提供了关联证据。v2 曾有只在高复杂度端点触发的 `simplify` 算子，并在价值中给 compactness 权重 0.08；TSP/CVRP v2 的增长比分别只有 1.29×/1.41×。后续核心收缩删除了复杂度状态和简化算子，v3 已出现更强增长，v4 又用持续继承父程序的两个语义算子替换旧组合。由于版本间模型、种群和其它配置也不同，这一对比不能单独证明因果；它与当前 prompt、选择规则和父子边统计共同支持“删除简约压力后，累积式生成失去制动”的判断。

代码 token Jaccard 差异 reserve 理论上可能把新增标识符视为新颖，但当前三个 TSP v4 snapshot 中，长度与相对精英的代码 novelty 相关并不一致。因此它至多是次要风险，不是当前主因。

## 5. 当前可下的结论

1. 程序随搜索变长是遗传编程中已经被系统研究的 bloat 现象；LLM 程序搜索具备相同的基本发生条件。
2. 在所核对的 AAD 方法中，FunSearch 对短程序施加了最明确的选择偏好；EoH/MEoH 与 CALM 有显式简化算子，其中 CALM 还直接描述了其它算子促使代码增长的风险并给出消融证据。
3. EoH 的本地作者代码虽然实现 M3，默认算子列表却不启用它；“论文中存在简化算子”不能等同于“默认实验具有简约压力”。
4. ReEvo、HSEvo 和 MCTS-AHD 没有发现直接的代码长度惩罚。PathWise 报告 critic 经常产生简化经验，但原始 prompt 和 fitness 没有把它变成稳定约束。
5. MEoH 能把复杂度、效率和可读性纳入 Pareto 权衡；ShinkaEvolve 当前作者实现也能记录并配置复杂度准则，但默认仍只按综合任务分数选择。
6. 最大输出 token、简短自然语言描述、代码新颖性、代码多样性和搜索状态规模控制都不能替代程序复杂度控制。
7. TraceAAD v4 已经出现跨任务、跨重复的显著程序膨胀；当前父子边没有显示变长能提高直接改进率。
8. 主因是“完整父程序继承 + 加法式语义任务 + fitness-only 选择 + 无删除/简约压力”形成的代际正反馈；最大轨迹长度没有约束程序长度。
9. 修复目标不应是让程序越短越好，而应让新增复杂度与真实收益相匹配。当前版本保留完全同分择简与紧凑最好锚点，但 `trace_refine` 只要求聚焦修正一个有证据的机制或弱点，不在提示词中列举增、删、替换和合并操作；统计近同分与独立简化算子只作为后续候选。
10. V5.1 正式版本不在线拒绝重复程序；代码哈希与唯一率只用于过程诊断。严格更高 fitness 的长程序仍优先于短程序，长度只在 fitness 数值完全相等时打破平局。
11. 修订前 V5.1 的 `refine` 曾明列 replace/delete/merge/simplify，属于生成层提示；完全同分择简属于选择层规则。操作清单可能把注意力从一个具体机制目标分散开，因此当前提示已删除该清单；同分择简则在正式运行中频繁改变 global-best 身份，仍需单独消融，不能用整体代码变短证明其净效果。
