# 程序膨胀

> 研究问题：怎样限制无收益的代码增长，同时允许必要的算法复杂化？
>
> 状态：已形成最小控制原则，净效应仍需消融。
>
> 当前判断：程序长度不是算法质量代理。控制应服从 fitness，只在质量完全
> 相同时偏向更短实现。

V4 证明了不限制增长会让程序逐渐叠加分支、常数和特殊规则，增加上下文成本与
后续修改难度。但固定长度惩罚会混淆任务分数尺度、合理复杂度和算法质量；硬性
拒绝长程序也可能丢掉真正更好的机制。

正式 V5 记录非空 LOC，并采用 fitness-first 比较：任何严格更优程序都优先；
只有 fitness 完全相同时，较短程序成为 compact best 或 global best。代码哈希、
相似度和长度变化用于过程诊断，不作为在线拒绝条件。

这条规则是温和控制，却会改变后续繁殖锚点，尤其在 OP、OBP 这类离散评价面上。
因此后续应分别报告输出程序复杂度与繁殖行为，并检验“同分择简作为输出规则”
和“同分择简改变锚点”两种作用。测试选样必须与方法内部比较规则一致。
