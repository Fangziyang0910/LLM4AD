# TraceAAD V5 开发复盘

> 研究问题：V5 定稿过程中哪些设计造成了搜索损耗，哪些认识应保留？
>
> 状态：开发阶段已结束；结论用于解释正式 V5 的取舍和指导后续研究。
>
> 正式版本：当前 `traceaad_v5` 及 `version5` 实验。中间代码和实验见
> [`archive/traceaad-v5-development/`](../../archive/traceaad-v5-development/)。

## 最终决定

正式 V5 采用原开发快照 V5.3 的实现：保留四个经过轨迹适配的语义算子、最长
8 节点轨迹、Action/Code 共享历史、双轨迹直接参考、\(0.8Q+0.2P\) 调度、
compact best 和完全同分择简；在线共享全局经验关闭。后续联合修改没有改善
整体结果，因此不进入正式 V5。

## 踩坑与原因

1. **结构化 Action 增加了无效搜索损耗。** 早期五字段 JSON 契约使大量正常
   响应因格式问题不能形成候选。改为两条自然语言 Action 后，候选供给和代码
   唯一率明显恢复。高频算法决策应使用最小输出契约，审计信息由系统记录。

2. **设置错误的共享全局经验会扩散局部误判。** 反思文本曾把有限样本中的现象
   写成强结论，也出现 fitness 方向判断错误和过早宣布方向饱和。所有路线重复
   读取这些文字后，局部错误变成共同偏置。关闭该机制后，多个任务的路线推进、
   后半程最好更新和重复下限恢复。该结果否定的是当时的设置，不证明全局经验
   天然无效。

3. **Action 与 Code 的证据不对称会造成实现断层。** Action 能看到主轨迹和
   参考轨迹，Code 却只看到压缩后的建议时，跨轨迹思想容易被不完整实现。两阶段
   共享同一段有界历史，并在双轨迹算子中共享参考程序后，决策与实现的因果链
   更完整。现有证据不支持把重复代码简单归因于 Code 看到了相同上下文。

4. **把父子局部趋势加大权重并没有恢复整体性能。** 后续联合修改把趋势权重
   提高到 0.4，并恢复更强的局部修改提示。局部 improve 和有效候选数增加，
   被选父代的平均质量与严格 global-best 更新却下降。当前趋势只记录父子变化
   的方向，容易奖励较差 endpoint 的回弹，不能直接等价为继续繁殖价值。

5. **双轨迹能力不自动等于有效多样性。** `synthesize/transfer` 多次表现出
   较好的路线推进能力，说明四算子值得保留；但固定等概率会在优质路线尚未形成
   时消耗大量预算，高相似参考之间的重组也常缺少新信息。更合理的方向是在已有
   优质、互补局部解后提高跨轨迹算子概率。

6. **同分择简会影响繁殖，不只是结果展示。** 离散评价面上，大量不同程序可能
   fitness 相同；更短程序替换 compact best 后会改变后续锚点。正式 V5 保留
   这一轻量控制以避免无边界膨胀，但它的净效应仍需单独验证。测试选样也必须与
   方法内部的 fitness-first、同分择简规则一致。

## 形成的研究认识

V5 的问题主要发生在“历史怎样转化为下一步预算和修改”这一段，而不是轨迹没有
信息或四算子不能生成候选。下一步不应继续堆叠记忆层和控制器，应缩短因果链：
先用质量确定值得发展的局部区域，再用可靠的路线进展和访问不确定性分配预算，
最后只在优质且互补的路线之间引入多样性。

LLM 作为进化算子时，稳定的小步改进比偶发的大跨度跃迁更重要。这里的小步指
保留已验证结构、围绕明确弱点做可归因修改，不等于限制代码长度。未来最值得
验证的是基于搜索状态的算子调度：前期以可靠的单轨迹利用为主，形成多条成熟
路线后，再增加迁移与重组。
