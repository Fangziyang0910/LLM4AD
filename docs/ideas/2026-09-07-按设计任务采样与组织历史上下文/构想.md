# 按设计任务采样与组织历史上下文

日期：2026-09-07。状态：已确定的研究方向，具体机制与收益待验证。本文整理[原讨论](讨论原文.md)中的研究安排，不表示已完成实现或实验。

## 研究问题

在有限评价预算下，下一次算法生成应该看到哪些已有程序，以及怎样的排列和对照？真实祖先链可能提供形成关系，也可能主要提供实现对照或优质样例。需要通过实验区分这些作用。

区分两个角色：父代是继续修改的实现底座，参考材料为本次生成提供设计经验。参考材料可以来自更广的历史，不必先获得额外评价机会。

## 机制构想

材料使用已有的 `idea + code`；fitness、形成关系和生成时间用于筛选、排序与来源标注，不假设另有可靠的失败原因或潜力标签。

| 设计任务 | 候选的上下文组织 |
| --- | --- |
| Refine | 当前程序完整展示，配少量匹配祖先或实际代码变化对照 |
| Pivot | 减少对单条祖先链的依赖，提供其他来源的已有尝试 |
| Fuse | 以父代和 donor 两份程序为主体，历史只补充必要对照 |

以上是后续机制空间；首轮先识别材料来源的作用，不把算子提示、donor 规则和调度一起改变。

## 首轮验证

比较三种材料来源：少量匹配祖先、全局 best 更新序列、全树质量分层样例。三组保持相同的呈现方式、历史条目数量和 token 上限；原始八代历史另作工程基线，用于区分减少长度与改变来源的效果。

父代选择、算子比例、摘要生成协议保持一致，暂不加入新节点保活或固定连续开发。先检查实际提示、代码完整性与成本，再比较完整评价预算下的搜索表现，不以单步超父率或两步收益作为进入完整搜索比较的硬门槛。

全局 best 更新序列只取生成时已经出现的程序，覆盖较早、中间和较新的阶段，至多三个不同程序。按发现顺序呈现，说明它们可能来自不同分支；不将质量排序或发现顺序写成虚构的父子关系。代码过长时减少参考数量，记录选中的节点和呈现顺序。

## 如何解释结果

如果全局 best 序列有效，再对同一组材料打乱顺序，区分样例集合与序列组织的贡献。若打乱后没有损失，可保留更简单的样例采样；若顺序有增益，再研究进展序列。

历史 best 也可能集中在相近实现，并遗漏未登顶但有用的程序。匹配祖先、进展序列和质量分层样例均为待比较方案，不预先赋予其中一种特殊地位。

材料来源的作用明确后，再分别验证扩大 donor 来源与停滞触发的采样调整。相关方法先例与更详细的算子方案保留在[讨论原文](讨论原文.md)，其中的文献与实现判断沿用讨论时口径，未在本次归档中重新核验。
