# TraceAAD V5.1 大模型请求全链路审计

> 状态：实现与首轮 V5 运行证据审计；2026-07-25 完成所列 V5.1 接口修正
> 与真实模型小预算冒烟。第 3–8 节保留修正前证据，第 11 节记录修正结果。
>
> 本文检查每一次大模型请求实际看到了什么、被要求输出什么、程序怎样解析，
> 以及失败怎样进入搜索。第 3–8 节冻结修正前行为，不把首轮旧 V5 的输出直接
> 当成 V5.1 修正后的真实模型表现。

## 1. 核心结论

TraceAAD V5 运行时只有四类大模型请求：

1. 初始程序生成；
2. Action 生成；
3. 根据 Action 生成代码；
4. 周期性全局反思。

旧结构化 Action 是损耗最大的已发生故障，但不是唯一的接口问题。全面审计
又确认了三项需要在 V5.1 正式重跑前处理的高优先级问题：

- 当前自然语言 Action parser 会把前言、解释行或旧 JSON 内部字段静默当成
  action，并可能丢掉真正的第二条 action；
- 代码生成同时收到“执行已确定 Action”和“再次提出/提炼算法思想”两套
  指令，且 parser 固定选择第一个代码围栏；这会在日志显示解析成功时执行
  模型早期示例或草稿；
- 全局反思的 validator 仍含模型不可见的 800 字符总上限和代码哈希独立性
  条件，一个条目不合法会使整次更新全部失败。

此外，Action 可实现性、`Idea` 长度、历史中的实际修改信息、上下文 token
计量以及初始化失败策略会持续影响有效搜索空间。它们不会像旧 Action 一样
立即造成大面积 `parse_failed`，却会造成不可实现建议、重复实现、静默上下文
裁剪和初始 frontier 不足。

因此，当前两项 V5.1 修正的准确状态是：

- **自然语言 Action 的职责方向已经修正，parser 与真实模型验收尚未完成；**
- **全局经验的输入和调用预算已经修正，输出契约与真实模型验收尚未完成。**

公开行为测试证明机制调用链可以运行，不足以证明真实模型输出能够稳定通过
当前接口。

## 2. 审计范围与判据

证据包括：

- `llm4ad/method/traceaad_v5/` 当前实现；
- 六个正式实验入口的模型、上下文和输出配置；
- `20260724_220827` 批次四个 task、每个三个重复，共 12 个旧 V5 run；
- 12 个 run 的 `llm_calls.jsonl`、`method_events.jsonl`、错误日志和样本；
- 当前 V5.1 public-run smoke test；
- 针对 parser 和 validator 的最小确定性复现。

每类请求按同一条链检查：

```text
系统已知状态
→ prompt 实际展示的信息
→ 模型可见的输出契约
→ parser/validator 的真实验收条件
→ 失败是否消耗评价预算
→ 失败是否改变轨迹、访问和 frontier
```

审计区分三类结论：

- **确认缺陷**：当前实现可以确定性复现错误或与权威设计直接冲突；
- **运行证据**：首轮旧 V5 日志中已经发生；
- **设计风险**：因 V5.1 尚无真实模型运行，只能在冒烟中验证。

## 3. 全局调用与配置

本审计冻结时，六个正式入口使用相同的 OpenAI-compatible 适配器和关键配置：

- 模型上下文：32768；
- 常规输出上限与预留：16384；
- 全局反思输出上限：1024；
- temperature：1.0；
- thinking：关闭。

入口之间没有发现某个 task 单独漏传 prompt、使用另一套输出格式或反转
fitness 方向。常规代码与 Action 调用的 16384 输出上限也足以解释首轮长输出，
不存在类似旧全局反思那样把 16K 预留错误叠加到短结构化输出的问题。

共享问题是 token 计量。当时适配器没有 `count_tokens()`，方法退化为 UTF-8
字节数：

```text
len(prompt.encode("utf-8"))
```

首轮 24,981 次非反思调用全部记录为 `utf8_byte_upper_bound`。这不是模型的
真实 token 数。按本审计时 V5.1 的 16,384 输入“token”预算，首轮 Action prompt
中 3,466/12,949（26.77%）、代码 prompt 中 3,416/11,671（29.27%）会被判为
需要裁剪；双轨迹算子最明显：

| 算子 | Action prompt 超过 16,384 字节 |
| --- | ---: |
| `trace_ideate` | 4.71% |
| `trace_refine` | 3.57% |
| `trace_synthesize` | 48.22% |
| `trace_transfer` | 48.94% |

字节上界能够防止溢出，却会把“真实 16K token 上下文”收缩为更小的字节窗口，
并系统性裁掉更多双轨迹历史。这是上下文保真度问题，不是服务请求失败。

## 4. 第一步：初始程序生成

### 4.1 模型看到和输出什么

输入包括任务描述、空目标函数契约和一个多样性提示。输出要求为一条简短
`Idea` 和一个完整目标函数。多样性提示只读取最近六个已接受初始程序的
`Idea`，每条截断到 100 字符。

### 4.2 已发生的表现

首轮共 361 次初始生成：

| 结果 | 次数 |
| --- | ---: |
| 程序解析成功 | 360 |
| 程序解析失败 | 1 |
| 解析后评价成功 | 323 |
| 解析后评价失败 | 37 |

因此，初始生成没有发生 Action 规模的格式崩溃，解析成功率为 99.72%。37 次
评价失败也不能全部归为 prompt 缺陷；生成无效程序本来就是开放式搜索可能
产生的结果。

### 4.3 确认缺陷：有效初始数量与评价次数混用

权威流程要求“生成并评估最多 M 个有效初始程序”。当前循环却以总评价次数
达到 `n_init=30` 为停止条件。无效初始程序已经消耗评价次数，但不会形成
轨迹，也不会继续补足。

12 个 run 实际建立的有效初始路线为：

```text
CVRP: 26 / 28 / 29
OBP:  25 / 26 / 25
OP:   27 / 24 / 29
TSP:  29 / 30 / 25
```

初始 frontier 因而从 24–30 条路线不等量开始。所有有效初始代码在各 run
内部均具有不同代码哈希，所以这里的不足来自失败策略，不是初始化重复代码。

### 4.4 风险：`Idea` 并不简短

360 条已解析初始输出的 `Idea` 长度中位数为 762.5 字符，90 分位约 1,247，
最长 4,703；343 条超过 400 字符。parser 只提取第一条 `Idea:` 行，不设
长度或内容边界。多样性提示会截断它，但后续把当前/参考节点作为上下文时会
放入完整 `Idea`。

结论：初始化的紧急问题是 frontier 补足语义和 `Idea` 污染后续上下文，不是
输出格式。

## 5. 第二步：Action 生成

### 5.1 V5.1 当前契约

输入包括任务与目标函数契约、主锚点完整代码、主轨迹 formation history、
锚点后的 tested-after 边、全局经验、算子约束，以及双轨迹算子下的参考
程序和历史。输出要求为恰好两条编号、单行、自包含的自然语言修改建议。

这个职责已经与用户原始设想和 V4 的“两阶段生成”方向对齐。

### 5.2 确认缺陷：自然语言 parser 仍会静默拿错 Action

当前正则把“编号”“Action 标签”和项目符号全部设为可选，因此实际上接受
任意非空普通文本行。以下确定性输入会被错误处理：

```text
Here are two actions:
1. actual action one
2. actual action two
```

parser 返回前言和第一条 action，数量恰好为 2，错误列表为空，真正第二条被
静默丢弃。若模型在第一条 action 后增加实现解释，这一解释也会占用第二个
位置。旧 JSON 响应中的 `change` 与 `novel_difference` 文本行同样可能被
当成两条新 Action。

这比显式 `parse_failed` 更危险：日志会显示成功，代码阶段却执行错误文本。
现有测试只覆盖理想编号输出，没有覆盖前言、多行解释、旧 JSON 或多余条目。

### 5.3 设计风险：Action 没有明确约束可用运行状态

当前 prompt 要求“具体、自包含”，但没有明确要求保持目标函数签名不变、
只能使用函数参数和可由这些参数推导的状态、不能假设隐藏的跨调用状态或
求解器内部变量。

首轮旧 V5 的 11,677 条已提取 Action 中，至少 181 条显式依赖函数不可见
状态，例如 `current_route_load`、当前 ant path、`count_usage`、`cur_dist`
或 previous node。代码模型只能拒绝、近似替代或保持原程序。结构化格式修正
不会自动消除这一问题。

### 5.4 设计风险：两条 Action 的差异只由语言要求保证

系统没有检查两条 Action 是否实质独立、是否已经存在于锚点代码或参考代码，
也没有在生成代码前判断拟议机制可执行。首轮代码响应中“already
implemented/present”类表述在 `trace_transfer` 尤其多，说明参考路线和
Action 可能把已有思想再次送回主程序。

结论：Action 的职责修正是正确的，但当前 parser 还不能作为真实模型接口
验收；可实现性与两条建议的差异性也需要进入 prompt 和冒烟指标。

## 6. 第三步：根据 Action 生成代码

### 6.1 模型看到和输出什么

代码请求接收任务描述、主锚点 `Idea` 和完整代码、与 Action 阶段相同的
主轨迹历史、可选参考节点及参考历史、已确定的 Action、算子语义约束和空目标
函数契约。输出要求一个简短 `Idea` 和一个完整目标函数。

主/参考历史没有在 Action 到代码之间意外丢失；全局经验有意只进入 Action，
代码阶段依赖 Action 自包含地传递决定。这一职责边界与 V5 设计一致。

### 6.2 已发生的表现

首轮代码请求：

| 结果 | 次数 |
| --- | ---: |
| 解析成功 | 11,640 |
| 解析失败 | 31 |
| 合计 | 11,671 |

解析成功率为 99.73%。因此代码阶段没有出现旧 Action 那样的大面积格式拒绝。
12,000 次程序评价中 11,767 次成功、233 次失败；按来源为：

| 来源 | 成功 | 失败 | 失败率 |
| --- | ---: | ---: | ---: |
| init | 323 | 37 | 10.28% |
| ideate | 2,558 | 108 | 4.05% |
| refine | 2,660 | 52 | 1.92% |
| synthesize | 2,521 | 20 | 0.79% |
| transfer | 3,705 | 16 | 0.43% |

评价失败是候选有效性的结果，不能直接当成 LLM 接口错误；下面两项才是确认
的接口缺陷。

### 6.3 确认缺陷：Action 决策指令被重复用于代码执行

同一个 `operator.build_constraint()` 同时进入 Action prompt 和代码 prompt。
例如 `trace_ideate` 在 Action 阶段要求“提出一个真正新的思想”，代码阶段
又收到同一句话，同时还收到“精确实现已经确定的修改”。

代码模型由此承担两个相互干扰的职责：重新判断下一步应该改什么，同时执行
上一步已经确定的 Action。首轮响应中可以观察到模型重新论证、拒绝不可实现
要求、认为主程序已经包含该思想、改写 Action 或输出基本不变程序。

代码阶段应只保留执行约束；算子的决策语义已经由 Action 阶段完成。

### 6.4 确认缺陷：固定选择第一个代码围栏

parser 使用响应中的第一个 fenced code block。若模型先给示例或草稿，随后
给出“最终实现”，系统仍评价第一段。

首轮代码响应中：

- 11,638 次只有一个已闭合代码块；
- 31 次包含多个已闭合代码块；
- 2 次没有匹配到闭合块；
- 多块响应中有 18 次最终仍被 parser 判为成功；
- 这 18 次中，15 次第一块与最后一块不同。

一个 CVRP 样本的第一块是含 `...` 的讨论片段，后面才给完整实现；parser
记录成功并把前一块送入评价，最终评价失败。另一些样本虽然能够评价，也是在
评价模型较早的备选实现，而不是其最后声明的方案。

该问题发生频率低，但属于静默语义错误；`program_parse_success=true` 只说明
选中的文本可被裁成程序，不说明选中了模型意图的最终程序。

### 6.5 风险：`Idea` 把推理过程带入后续历史

11,640 条已解析代码输出的 `Idea` 长度中位数为 356 字符，90 分位约 568，
最长 5,230；4,272 条超过 400 字符，153 条超过 1,000 字符。还有少数空泛
占位说明。

这些文本会原样进入未来 Action 和代码 prompt。`Idea` 本来只是简短实现声明，
实际却常混入模型的推理、保留意见、替代解释和长篇机制描述。它既占用上下文，
又可能被后续模型误当成已经实现的算法事实。

### 6.6 风险：历史只保留“想改什么”，没有概括“实际改成什么”

轨迹边在 prompt 中显示 Action、fitness、outcome 和 LOC，不显示 child
`Idea`、机械代码变化比例或简短实际差异。对于 tested-after 失败，后续模型
看到的是当时计划实施什么，而不是代码模型实际实施了什么。

完整代码事实仍保存在节点和工件中，当前锚点/参考程序也会展示；问题在于被
压缩进历史的非当前边可能让 Action 声明代替实际实现。该项属于历史表示风险，
不是已证明必须增加另一个 LLM judge。

## 7. 第四步：全局反思

本次审计发现，旧实现把一项开放式反思思考变成了结构化表单与在线认证：
JSON、类别、引用、来源分组、代码和结果一致性中的任一条件不满足，整次响应
都会被拒绝。这与旧 Action 的问题相同，也偏离了全局经验只需指导下一步的
职责。

V5.1 最终实现已经删除全部内容门禁，改为：

```text
上一版全局反思
+
最近 40 个已评价子程序的 Action、实现 Idea 和 fitness 结果
→
最多 5 点自然语言反思，响应直接保存
```

反思不再解析 JSON，也不进行内容合法性、独立来源或重复程序判断。调用失败
时保留旧文本与待处理批次，后续重试。公开行为测试证明第 40 个已评价子程序
后可以更新，下一轮 Action 可以读取，详细修正见
[07-全局反思复杂门禁移除](07-全局反思复杂门禁移除.md)。

## 8. 请求之外但会改变搜索的失败语义

Action、代码解析和反思失败不直接消耗程序评价预算；只有进入 evaluator 的
程序才计数。这一预算边界正确。Action 批次为空却仍记录一次父轨迹访问，因此
旧 Action 格式服从性已经污染 UCB 访问语义。

当前日志中的 `ok` 只分别表示 Action 至少提取到文本、code/init parser 得到
一个程序，或 reflection 整份 validator 通过。它不代表 Action 可实现、选中
了最终代码块、Action 与代码一致、`Idea` 与代码一致或候选评价成功。后续
过程分析不能把 `ok` 当成端到端成功。

## 9. 修正优先级

正式 V5.1 真实模型冒烟前，优先处理：

1. **Action parser**：只识别明确编号的 action 项，处理前言、续行、额外项和
   旧 JSON；不能用“任意非空行 + 截前两条”恢复数量。
2. **代码阶段职责**：算子约束只负责 Action 决策；代码 prompt 只执行确定的
   Action、保持主程序和函数契约。
3. **代码块选择**：拒绝歧义或选择能够唯一确定的完整目标函数，并记录代码块
   数量与选择理由，不能固定取第一块。
4. **全局反思可观察契约**：模型可见规则与 validator 完全一致；代码哈希
   去重由系统在证据展示/分组时完成，validation failure 记录具体原因。
5. **真实模型小预算冒烟**：必须实际经历初始化、四种 Action、代码生成、第
   20 轮反思和第 21 轮经验使用，不能只依赖手写 deterministic LLM。

随后处理：

6. 在 Action 契约中明确函数签名、可用输入和禁止隐藏运行状态；
7. 限制或确定性压缩 `Idea`，避免把模型推理继承为历史事实；
8. 为历史边加入无需额外 LLM 的简短实际修改摘要；
9. 使用真实 tokenizer 或适配器 token counter；
10. 明确 `n_init` 表示有效根节点目标，还是初始化评价预算，并让文档、实现与
    实验报告一致。

这些修正应先恢复请求接口的语义正确性，再讨论重复代码去重、active frontier
资源规则和受控消融。否则，新实验仍会把接口噪声与搜索机制效果混在一起。

## 10. 重新实验的最低验收

真实模型冒烟至少报告：

| 阶段 | 最低验收 |
| --- | --- |
| init | 有效根数量与设定语义一致；无静默选错代码块 |
| Action | 两条真实修改稳定提取；前言/解释不成为 Action |
| feasibility | Action 只使用目标函数可见输入 |
| code | 实现已确定 Action；无再次选题；多代码块被显式处理 |
| Idea | 长度受控，并明确只是实现声明 |
| reflection | 至少一次真实模型输出通过；失败有具体原因 |
| handoff | 第 21 轮 Action 确实读取第 20 轮新经验 |
| context | 报告真实 token 与裁掉的主/参考历史 |
| evaluation | 分开报告 parse success、eval success、unique code 和有效改进 |

只有这些条件通过，V5.1 才具备检验全局经验、双轨迹算子和 active frontier
机制效果的干净前提。

## 11. V5.1 修正结果

本轮按第 9 节顺序完成：

1. Action parser 只接受从 1 开始连续编号的文本项，前言、续行和旧 JSON
   不再成为 Action；
2. Action prompt 明确修改只能使用目标函数参数和局部计算值；
3. 代码阶段只读取任务、当前程序、自包含 Action 和函数契约，不再读取算子、
   轨迹或参考程序；
4. 程序 parser 从后向前选择最后一个完整目标函数，并兼容未闭合的最终围栏；
5. `Idea` 改为最多 300 字符的一句实现说明，历史同时显示 Planned、
   Implemented、机械代码变化和 LOC；
6. 全局反思删除隐藏的 800 字符上限，以 `resulting_program` 标签向模型公开
