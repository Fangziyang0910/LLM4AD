# TraceAAD v5 全局经验失效诊断与修正方案

> 冻结对象：2026-07-24 启动的 TSP Construct、CVRP-ACO、OP-ACO 与
> Online Bin Packing 共 12 个 TraceAAD v5 run。
>
> 读取时间：2026-07-25 14:14（Asia/Shanghai）；12 个 run 均已结束。
>
> 本文区分直接观察、机制解释与拟议修正。拟议修正尚未由新实验验证。
> 后续进一步删除了结构化反思的全部内容门禁；当前方案以
> [07-全局反思复杂门禁移除](07-全局反思复杂门禁移除.md) 为准。

## 1. 核心判断

这批运行中的全局经验并非“形成了但没有帮助搜索”，而是一次也没有形成。
直接故障是模型真实上下文为 32K，而实验把方法内部窗口配置成 131K，并为
每次反思请求预留了 16K 输出。更深一层的问题是，反思 prompt 把 60 条边的
完整运行元数据直接展开；一次只需要输出最多 6 条、约 800 字符的经验，却
沿用了代码生成调用的 16K 输出上限。

因此，全程空经验由四个环节共同造成：

```text
错误的 131K 窗口假设
        +
60 条完整 edge facts 直接展开
        +
反思仍请求 16K 输出
        ↓
服务端在第一次更新时返回 32K context HTTP 400
        +
失败批次已从 pending 中删除且不重试
        ↓
后续批次重复失败，全局经验始终为空
```

配置不一致解释了 HTTP 400；输入和输出组织解释了为什么反思极易越界；失败
批次的生命周期解释了为什么一次故障最终演变成整个 run 都没有全局经验。

## 2. 可复现的直接证据

冻结工件中共找到 184 次 `global_experience` 调用失败。12 个 run 的每次
失败均满足：

```text
model maximum context length = 32768
requested output tokens = 16384
input tokens >= 16385
total tokens >= 32769
```

每个 run 的最终 checkpoint 中
`global_experience_entries == []`。下面的工件重放检查能够稳定复现这一
结论：

```bash
uv run python - <<'PY'
import json
from pathlib import Path

runs = sorted(
    Path("experiments").glob(
        "*/traceaad_v5/version5/*/logs/errors.jsonl"
    )
)
checked = 0
for errors_path in runs:
    rows = [
        json.loads(line)
        for line in errors_path.read_text().splitlines()
        if line
    ]
    reflections = [
        row for row in rows
        if row.get("stage") == "global_experience"
    ]
    if not reflections:
        continue
    assert all(
        row.get("error_type") == "BadRequestError"
        and "maximum context length is 32768" in row.get("error", "")
        and "requested 16384 output tokens" in row.get("error", "")
        for row in reflections
    )
    state = json.loads(
        (errors_path.parent / "checkpoints/latest.json").read_text()
    )
    assert state["global_experience_entries"] == []
    checked += len(reflections)

print(checked)
PY
```

当前输出为 `184`。

首批反思都包含 60 条 edge facts，prompt 长度约为 74K–82K 字符。以 TSP
rep1 为例：

```text
完整 prompt                  79,709 字符
Evidence Facts              78,624 字符
其中 change_claim            18,838 字符
其中 novel_difference         7,740 字符
```

证据区几乎占据全部输入。除了修改说明，当前视图还重复传入完整哈希、
trajectory/program id、reference 元数据、多种 delta 和其它审计字段。它们
适合保存在图与日志中，却不都是形成全局认识所需的最小信息。

## 3. 四个原因的证据等级

### 3.1 已确认：真实窗口与配置不一致

实验入口把 `max_context_tokens` 默认为 131072，运行所用服务实际只接受
32768。方法的发送前检查因此以错误上限放行 prompt，最终由服务端拒绝。

这是本批 HTTP 400 的直接原因。把配置改成真实窗口后，当前完整 edge facts
会在本地预算检查中被拒绝，说明只改配置仍不足以让现有反思输入正常工作。

### 3.2 已确认：全量运行元数据不是紧凑反思输入

当前反思每次读取 60 条边的完整字典。这里混合了两个职责：

- 图和日志需要保存可复现、可审计的完整事实；
- 反思器只需要能够归纳“在什么条件下，声称做了什么，实际得到什么结果”
  的最小信息。

把存储真相源直接当作 LLM 上下文，导致完整审计字段进入每次反思。这不是
全局经验思想本身要求的行为，而是事实存储与推理接口没有分层。

### 3.3 已确认：反思错误复用了代码输出预算

全局经验最多 6 条，总说明与条件不超过约 800 字符，却调用与代码生成相同
的 `max_tokens=16384`。在 32K 模型上，这等于先把一半窗口保留给不会用到
的输出，再尝试放入大批输入。

反思需要独立、较小的输出预算。其上限应由经验 schema 决定，而不是由代码
生成可能需要的长度决定。

### 3.4 已确认：失败批次被永久消费

实现先从 `pending_experience_edge_ids` 中删除最早 60 条边，再检查上下文并
调用模型。context overflow、LLM failure 或 validation failure 都不会把
该批次放回。因此，错误配置没有只造成一次暂时失败，而是每 60 条新边永久
丢弃一次经验更新机会。

当前设计文档曾把“失败后跳过批次”作为避免阻塞搜索的恢复策略。首轮实验
证明这条策略缺少一个前提：系统性配置错误必须在冒烟阶段被阻止，且可通过
缩短输入恢复的失败不能直接当作已处理事实。

### 3.5 后续确认并已删除：结构化输出门禁

本批调用在得到模型响应前已经失败，因此旧门禁不是这 184 次失败的原因。
后续真实运行确认，JSON、分类、引用、来源分组、代码和结果一致性检查会大量
拒绝已经生成的反思。该设计现已整体删除，最终修正见
[07-全局反思复杂门禁移除](07-全局反思复杂门禁移除.md)。

## 4. ReEvo 真正传入了什么

ReEvo 的长期反思没有读取完整种群、代码历史或历史 prompt。默认
`pop_size=10` 时，每轮形成 10 组父代比较：

1. 每个短期反思读取一份 worse code 与一份 better code；
2. 白盒任务把比较压成少于 20 词的提示，黑盒任务少于 50 词；
3. 长期反思只读取上一版长期反思、本轮 10 条短提示和问题描述；
4. 输出少于 50 词并整体覆盖旧长期反思；
5. 下一轮不会重新读取以前保存的短期反思或完整代码。

其结构是：

$$
\text{局部代码比较}\rightarrow\text{短期提示},\qquad
(G_k,\text{本轮短提示})\rightarrow G_{k+1}.
$$

这正是 ReEvo 所说的“积累经验但不造成 memory blowup”。详细一手资料核对
见[ReEvo 长期反思的真实上下文与压缩机制](../../surveys/reevo-long-term-reflection-context.md)。

ReEvo 的边界也很清楚：长期反思不知道刚生成的 crossover offspring 是否
真的改善，只总结既有父代的相对差异。TraceAAD 不应照搬这一信息单元，因为
轨迹已经保存 action、父子结果、路线位置和后续影响。

## 5. 面向 TraceAAD 的最终最小修正

每条已评价修改边已经包含一项局部试错。V5.1 每积累 40 个已评价子程序，
把上一版全局反思与这 40 项 Action、实现 Idea 和父子 fitness 结果交给模型，
直接生成最多 5 点的自然语言反思：

$$
G_{k+1}=\mathcal R(G_k,H_k).
$$

不传入完整程序、代码哈希、轨迹编号、来源分类、全部分叉或运行元数据。模型
响应直接覆盖旧文本，不经过结构化 parser 或内容 validator。新文本只进入
后续 Action 决策，不进入 fitness、轨迹评分、父代选择或种群生存。

## 6. 修复后的验收条件

在重新启动正式实验前，最小冒烟必须同时证明：

1. 第 40 个已评价子程序后触发反思；
2. 输入恰好包含这 40 项修改及其结果；
3. 模型响应不因内容格式或判断方式被拒绝；
4. 下一轮 Action 读取更新后的文本；
5. 调用失败不会消费待处理批次。

满足这些条件只能证明全局经验机制已经真实运行。它是否减少重复试错、提高
后半程唯一程序比例和 global-best yield，仍需与同模型、同协议的重复实验
比较。
